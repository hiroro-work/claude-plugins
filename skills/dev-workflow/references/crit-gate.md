# Crit gate

Read from `commits.md` § Procedure at Interactive Commits, and from `mob-mode.md` § Per-unit review at Implement. The wrapper, the launch, and the reading of its result apply to both. So do the split between a `scope: "line"` comment, applied as an edit, and a `scope: "review"` body, read as a typed reply, and answering every comment in the browser. The candidate derivation, the story, the commit step, and the routing of a reply through `commits.md` § Approval tokens are for the commit gate only: a unit review's range is `<prev>..<snapshot>`, it attaches no story, and `mob-mode.md` § Per-unit review governs what its verdict means.

crit is driven through `node "<base dir>/scripts/crit/gate.mjs"`, which prints one JSON line on stdout. The first call of a run that answers `status: "unavailable"` puts the whole run on the chat presentation, with its `reason` in one note.

Per commit: on the chain path the candidate is the chain commit itself and `<parent>` = `<commit>^` (not HEAD), or `<S_k>` when mob mode presents the post-review delta. On the cohesion path `<parent>` = `git rev-parse HEAD`; build the candidate without moving HEAD: `git write-tree` on the staged group, then `git commit-tree <tree> -p <parent>` with the subject and body on stdin. Then attach the **story**, which carries the body the browser never shows:

1. `gate.mjs prep --range <parent>..<candidate>` prints crit's authoring guide with the JSON shape it accepts, then the hunk listing; each `--- (<file_path>, <old_start>) [<status>]` line is one hunk id (`old_start` is `0` for a new file).
2. Write `.claude/plans/<slug>.story.json` in that shape: `prologue` from the subject and the body, `chapters` grouping hunks by theme (one or two per commit), `support` for mechanical hunks (lockfiles, generated output, version bumps) with a `reason`. Every hunk goes in a chapter or in `support`; prose follows the resolved language. Reuse the first round's wording on later rounds while the subject and body are unchanged; re-derive only the hunk references.
3. `gate.mjs story --range <parent>..<candidate> --story-file <that file>`. When its `error` names hunks by id, correct their placement and run it once more; nothing else is retried. `auto_repaired: true` is not a failure. A story still `rejected` is reported in one line with its `error`, and the review runs without it.

Run `gate.mjs review --range <parent>..<candidate>` in background Bash with a status line, adding `--no-open` when the story call returned a `daemon_url` (put that URL in the status line). Read its JSON when the process exits. `approved` → commit per `commits.md` § Procedure's accept. `changes` with no `comments` and no `comments_raw` → same candidate, new round. `changes` with comments (a `comments_raw` is read as the comments; skip any marked `answered`) → apply the `scope: "line"` comments as edits (or refuse the ones that would change a commit already on the branch), run `check_commands` once if anything changed, then treat each `scope: "review"` body as a typed reply through `commits.md` § Approval tokens (cancel wins over adjust over accept); the commit stays pending and is rebuilt and re-reviewed. On the commit gate's chain path the candidate cannot be rebuilt: the answers say the edits go into the post-commit extra commit, and the new round opens on the same candidate unless the routing committed or cancelled it. Before the next round, commit, or cancel, answer each comment with an `id` in the browser: pipe `[{"id","body"}]` to `gate.mjs reply` in a quoted heredoc, each body saying what was done, or why not, in the resolved language. Not `replied` → answer in chat with its `reason`. `broken` → chat presentation for this commit only, with its `reason`; crit stays enabled for the next.
