# Interactive Commits (Step 10) — Procedure

Single canonical home for the Step 10 (Interactive Commits) procedure body — `SKILL.md` § Step 10 keeps only the entry conditions, the `landed_count` cross-step contract, the **Approval token closed list**, and the **Localized summary tokens**, and points here for the procedure; do not duplicate this content back into `SKILL.md`. Only four unqualified `§` references below resolve to `SKILL.md`, where those definitions stay: `§ Approval token closed list`, `§ Localized summary tokens`, `§ Phase naming in user-facing output`, and `§ Workflow artifacts`. All other `§` references resolve within this file.

If the current plan explicitly deferred bookkeeping edits to the commit stage — for example, CHANGELOG entries or version-bump lines whose content was deferred until the implementation is confirmed complete — apply those edits now, before Procedure 1 collects the working tree, so they are captured in the commit grouping. Use the plan's deferral language (e.g. "will add the CHANGELOG entry at commit time", "version bump deferred to Step 10") as the trigger. Apply these deferred edits autonomously, with no user gate before Procedure 1. If any edit call fails, stop Step 10 and report the failure to the user.

**Procedure**:

1. **Collect changes**: `<base-commit>` referenced throughout this Procedure is the value recorded by Step 2's opening sub-step (`git rev-parse HEAD` at workflow start — see `SKILL.md` § Step 2: Create Plan's first numbered item); Step 10 reuses that captured value verbatim, never re-resolves it. Run `git status --porcelain=v1 --untracked-files=all -z` once (the `=v1` form pins format; `--untracked-files=all` overrides any user-side `status.showUntrackedFiles=no` config; `-z` emits NUL-separated entries with no C-style quoting so filenames containing spaces, quotes, or non-ASCII characters are recoverable verbatim). Parse the NUL-separated output: entries prefixed `??` are untracked, others are tracked changes. If the output is empty, mark `Step 10: Interactive Commits` as `completed` and proceed to Step 11 (nothing to commit since base-commit). Otherwise keep the parsed path list in memory as the canonical roster — Procedure 3 (§ Propose commit plan) groups it on the chain-absent path, and its Plan-scope cross-reference scans it for changes touching declared no-change areas. `Post-commit auto-modify cycle bound` does **not** read this roster; it compares its own before/after porcelain pair, for the reason stated there. **Capture no per-file diff here**: each commit's diff comes from its own candidate at `Per-commit loop` sub-step `a`, so a `git diff <base-commit>` capture at this point would be wider than any single commit and — for a file that several commits touch — wrong for every one of them
2. **Deduce commit style**: run `git log -n 10 --format=%s` and infer the project's conventional commit style (presence of type prefix, imperative mood, etc.) — used as a runtime hint when drafting subjects, never hard-coded
3. **Propose commit plan**: Before grouping, run the default-branch guard and plan-scope cross-reference below, then group changes into 1+ logical commits, each `{subject, body (optional, may be empty), tree source}` — `tree source` being what the commit's tree is built from at `Per-commit loop` sub-step `a`. Which of the two grouping origins applies depends on whether Step 5 recorded a **Build-order boundary chain** (`implementation_boundaries` — see `SKILL.md` § Step 5's "Build-order boundary chain (sub-step 2.5)" paragraph):

   **Chain present** (`implementation_boundaries` is non-empty **and every recorded object still resolves** — probe each with `git rev-parse "<object>^{tree}"` and require a zero exit for all of them; a non-zero exit anywhere means the objects were reclaimed, which is the chain-absent cause below rather than a tree-derivation failure at sub-step `a`): propose **one group per boundary**, in chain order, each labelled with that boundary's Build order heading and taking that boundary object as its `tree source`; then add a **final group** covering everything not yet landed by the boundary groups — derived, not enumerated: `git diff --name-only` from the last boundary to the working tree, unioned with Procedure 1's untracked (`??`) paths — which that command never lists — minus the § Workflow artifacts set. That is usually the Step 6–9 quality-gate fixes plus any deferred bookkeeping applied above, but it also picks up anything the working tree carried that no Build order step staged. **Cohesion-split it** where its contents differ in kind, each part taking the pathspec derivation; in particular propose the release bookkeeping (the version bump and the CHANGELOG entry) as its **own** group, since a bookkeeping commit's pathspec is required to stay a closed set rather than absorbing whatever else the gates touched. Omit any group whose delta against its predecessor is empty — the final group when the quality gates changed nothing, and equally a boundary group for a Build order step that edited no in-scope path (a verification-only step, or one whose only writes were § Workflow artifacts). An empty group would otherwise spend a round-trip at the per-commit gate on a commit with no content. Adjacent groups MAY be merged where their concerns do not differ, but **do not merge by default** — the user approved this sequence at the Step 4 plan-approval gate, so the chain order is the proposal's spine and the `Mid-loop adjust` file-regrouping branch is where the user collapses it further. Because each group's tree comes from its boundary rather than from a pathspec, **two groups may both touch the same file**; the file-level staging constraint that used to force such groups together does not apply on this path (the condition is spelled out in [`simplicity-self-audit.md`](simplicity-self-audit.md)'s **Commit-split boundary alignment with file-level staging** item).

   **Chain absent** (`implementation_boundaries` is empty or its objects no longer resolve — `interactive_commits` was enabled after Step 5 had already run, a boundary build failed and abandoned the chain per that sub-step's "On failure" paragraph, or the run resumed in a session that no longer holds the objects): group the collected change set **by cohesion** instead (concerns that differ → separate commits; typical case is a single commit), each group taking **its own pathspec** as the `tree source`. On this path a group's tree is built by staging that pathspec, so the groups must be file-disjoint — the file-level staging constraint applies exactly as it did before the boundary chain existed. Say so in one line above the presentation, in the resolved `language` (see `SKILL.md` § Configuration's `language` bullet), e.g. `no Build-order boundary chain for this run — grouping by cohesion`, so the coarser grouping is not mistaken for a chain-derived one.

   **Cross-layer split check**: when the collected change set spans multiple clearly-separable architectural layers (e.g. a new backend endpoint plus its test, a thin frontend wrapper that calls it, and the UI change that consumes that wrapper), do not default to bundling the whole set into one commit — surface a layer-based split as an explicit alternative grouping in the commit-plan presentation, so the granularity choice is made before commits land rather than raised after the fact.

   **Default-branch guard**: before proposing any commit plan, check whether the current branch is the repository's default branch. First run `git symbolic-ref -q HEAD` — if it exits non-zero, HEAD is detached; skip the guard and continue. Determine the default branch name, resolving it **locally first**: run `git symbolic-ref -q --short refs/remotes/origin/HEAD` and strip the leading `origin/` (e.g. `origin/main` → `main`). That reads a local ref only, so it succeeds offline and without remote authentication (git never refreshes this ref on its own, so an old clone can still name a since-renamed default branch; the guard does not refresh it either — that is the user's `git remote set-head origin -a` to run). **Only when it exits non-zero** (the ref is unset in this clone) fall back to `git remote show origin` and read the branch name off its `HEAD branch:` line. That fallback reaches the remote, so treat a non-zero exit or a missing `HEAD branch:` line alike as failure — it is unfit as the primary resolution precisely because a silent skip here lands commits on the default branch. If both resolutions fail (including `origin` not being configured), skip the guard and continue — but say so in one line above the commit-plan presentation, in the resolved `language` (see `SKILL.md` § Configuration's `language` bullet), e.g. `default branch could not be resolved — branch guard skipped`, since the whole point of the local-first order is that this skip stops being silent. Compare the resolved name against the output of `git rev-parse --abbrev-ref HEAD`. If they match — the current branch IS the default branch — create and switch to a new feature branch (`git switch -c <branch-name>` where `<branch-name>` is a kebab-case slug derived from the task; if that name is already taken, append a short disambiguator such as `-2` and retry once; if the second attempt also fails, stop and report the branch-creation failure to the user) before the commit-plan presentation. Rationale: landing commits directly on the default branch in PR-based workflows requires post-commit branch surgery to recover a clean base. If the user indicates they intentionally want to commit on the default branch (e.g. a personal repo without PR workflows), skip the branch creation and note the choice in the commit-plan presentation.

   **Plan-scope cross-reference**: scan the approved plan for explicit "no-change" declarations — files, sections, or regions the plan stated would not be modified (phrasings like `"no changes"`, `"leave as-is"`, `"unchanged"`, `"not modified"`, `"read-only"`, or equivalent intent). Cross-reference against the collected change set from Procedure 1. If any collected change touches a declared no-change area, surface those paths as **unplanned changes** at the top of the commit-plan presentation — above the numbered commit list — naming each affected path and quoting the relevant plan text verbatim. Do not silently include unplanned changes in the proposed grouping; the user resolves them via the existing commit-plan approval gate's `adjust` (move to a separate commit with explanation, or exclude the path from every commit) or `cancel` branches. **Excluding a path** works by leaving it out of the group's intended path set, which moves a chain-present group onto `Per-commit loop` sub-step `a`'s **Stale boundary → pathspec derivation**. Do **not** use `git checkout HEAD -- <path>` to exclude, as that destroys existing uncommitted changes to the file. When no declared no-change areas exist in the plan, or no collected change overlaps with them, skip this cross-reference and proceed directly to the grouping.

   Present the plan to the user as a numbered list — per group, its subject plus what that group covers (the Build order heading(s) behind it on the chain-present path, its path set on the pathspec-derived ones) — and wait at the **commit-plan approval gate**. Per-file detail comes later, at each commit's own gate, where the candidate makes it exact. Before waiting, run `git diff --cached --name-only`: when it is non-empty, name that pre-run staging in one line here — sub-step `c. Land the candidate` replaces the index wholesale, and on the chain-present path those entries already rode into the boundary trees Step 5 recorded, so their content lands inside the first boundary group's commit. Where the first group takes the pathspec derivation instead, its `git read-tree HEAD` discards the staging at sub-step `a` — before any commit — so a run cancelled at the very first per-commit gate has already lost it. Approval is judged per § Approval token closed list.
4. **Per-commit loop** (`landed_count` was initialized to `0` at Step 10 entry in `SKILL.md`; no re-initialization is needed here — the counter is incremented only at sub-step `c. Land the candidate`, on its zero-exit `git commit`): process each commit in order:
   - **a. Build the candidate, then present it**: first build this commit's **candidate** — a dangling commit object carrying exactly the tree this commit will land, chained onto the current `HEAD`. Nothing lands and no hook runs here; the candidate exists so that the user (or crit) reviews the real object before `c. Land the candidate` moves the branch onto it. Capture the parent SHA once as `<candidate_parent>` (`git rev-parse HEAD`) — the `crit` gate reads it rather than resolving `HEAD` again. Two steps:

     **(i) Obtain the group's tree** from its `tree source` (Procedure 3 § Propose commit plan). Two derivations serve three kinds of group:

     - **From a boundary object** — a chain-present group still tracking what its boundary recorded: the tree is `<boundary>^{tree}`, and nothing is staged. A group that merged several adjacent boundaries takes the **last** boundary of that run: a boundary tree is cumulative, so an earlier one would drop the later steps' content.
     - **From a pathspec** — the chain-absent path, the chain-present **final group**, and any group the rule below moves here. First `git read-tree HEAD`, so the snapshot below is scoped to this group alone — `git write-tree` reads the **whole index**, not a pathspec, so without this anything else already staged rides into the candidate. Then stage this group's paths per [`diff-presentation.md`](diff-presentation.md) § Detached review object step 1 and `git write-tree` per its step 2. The staged set **excludes the § Workflow artifacts set**, so the plan document and the decomposition state file never land. What this stages is normally cleared by `c`'s commit, which replaces the index — but several exits leave before that commit (`c`'s empty-tree skip, `d`'s stop, § Mid-loop cancel, the normal completions at § Mid-loop adjust branches **c** / **d**, and branch **g**'s option (2) re-verification stop). On each of them, `git reset -- "<the paths staged here>"` before leaving, so the run does not abandon its own bookkeeping in the user's index (the obligation Step 5's exit unstage carries for its own staging). A chain-absent group stages exactly the path set Procedure 3 assigned it, and so does each part of a cohesion-split final group — Procedure 3 assigned those parts closed sets precisely so the release-bookkeeping part's pathspec stays closed instead of absorbing the rest of the gates' work. Every other group here derives its own: `git diff --name-only` from the group's start point to its end point — start = the previous group's candidate, or `<base-commit>` for the first group; end = this group's boundary, or the working tree for the final group — minus any path the Plan-scope cross-reference excluded from this group, since the frozen boundary the range ends at still lists it. Where the end point is the working tree, union in the untracked (`??`) paths Procedure 1's roster recorded: `git diff --name-only` never lists an untracked path, so a file the quality gates added would otherwise be dropped from every group.

     **Stale boundary → pathspec derivation.** A boundary object is frozen at the moment Step 5 recorded it and its tree is cumulative, so a group whose tree must differ from what its boundary recorded **leaves the chain and takes the pathspec derivation** — and because every later boundary carries that same content, **so does every group after it**. Triggers (closed list): a path excluded at the Plan-scope cross-reference; a file edited **during Step 10's own gates** — `Mid-loop adjust` branch **g**, a `crit` round whose `scope: "line"` comment changed code, or a `fold` in `Post-commit auto-modify cycle bound`; and a group produced by splitting or reordering the chain (branch **b**), which a cumulative tree cannot express at all. **A Steps 6–9 quality-gate edit is not a trigger**: those edits belong to the final group by design, and counting them as staleness would move every group off the chain and defeat the mechanism. The sites that reach these conditions point here rather than restating them.

     **(ii) Wrap it** per [`diff-presentation.md`](diff-presentation.md) § Detached review object step 3, with `<base>` = `<candidate_parent>` and this commit's subject and body as the piped message → `<candidate>`. When a chain-present group merged several boundaries, the body is where the **constituent Build order step headings** go — one bullet per heading, so merging groups never silently drops what each step was.

     **Diff-review mode branch**: when `commit_review_gate` resolves to `"crit"` and crit is available for this run (`references/crit-commit-review.md` § Procedure step 1 — checked and cached once per run, independently of Step 4's own reachability probe), the Diff element below is obtained via `references/crit-commit-review.md` instead — skip the rendering-mode decision and the Diff bullet's verbatim / condensed / skeleton rendering for this commit, and follow that reference's Procedure; its decision mapping resolves this sub-step's presentation / accept-gate pair directly (see sub-step **b** below). Subject / Body / Files / Verification below still render in chat regardless of this branch — crit reviews the code content, not the commit metadata. Otherwise (`commit_review_gate: "diff"`, the default, or crit unavailable / unreachable for this run per that reference's step 2), continue with the presentation below unchanged.

     Read [`diff-presentation.md`](diff-presentation.md) once when this loop starts — nothing in it varies per commit. Then, for **each** commit, before rendering the five presentation elements, measure that commit's diff and pick one mode per [`diff-presentation.md`](diff-presentation.md) § Rendering ladder, holding it for every file in that commit's Diff element. The measurement input is `git diff "<candidate_parent>" "<candidate>"`, sliced per file on its `diff --git a/<path> b/<path>` boundaries. That single range replaces the tracked / untracked split the pre-candidate presentation needed: a file this commit adds is already committed **inside** the candidate's tree, so the range prints it as a new-file hunk and no `Read` fallback is required. The skeleton trailer's full-diff command is correspondingly uniform — `git diff "<candidate_parent>" "<candidate>" -- "<path>"` for every slice, whatever the file's tracked status in the working tree.

     Then show the five presentation elements as a **closed list** — Subject / Body / Files / Verification / Diff — each rendered in its own block as the user's approval basis:
     - **Subject**: render in a dedicated fenced code block (single line, no surrounding prose).
     - **Body**: render in a dedicated fenced code block. When the commit has no body, render the placeholder `(no body)` inside the block — a prose statement like "body included" / "no body needed" without an actual rendered block is **forbidden**, because the user's approval must be anchored to the material content itself, not a promise of it.
     - **Files**: render as an explicit path list (one path per line, prefixed with `- `) — the paths the range measured above already names, read off its `diff --git` slice boundaries. On the `crit` path, where no chat range was captured, take them from `git diff --name-only "<candidate_parent>" "<candidate>"` instead.
     - **Verification**: render a one-line Step 7 outcome summary from memory (the result recorded when Step 7 ran earlier in the session). The rendered label is `Check / Test`, not the step number (§ Phase naming in user-facing output's "drop the number" option). Format: `Check / Test: <checks-result> / <tests-result>` when both were attempted but not both passed (e.g. `Check / Test: checks passed / tests skipped`, `Check / Test: checks passed / tests failed — see the check/test output above`); use the combined form when both passed (e.g. `Check / Test: all checks passed and tests passed`); use the slash form for all other outcomes. When the check/test phase did not run (Trivial difficulty skip, or no `check_commands` / `test_commands` configured), render `Check / Test: skipped`. Always include this slot — the user must never have to ask whether tests passed.
     - **Diff**: render the actual per-file hunks from the `git diff "<candidate_parent>" "<candidate>"` range measured above, using the mode decided there. A file this commit adds arrives as a new-file hunk from the range itself, so no separate capture is needed — but keep the added-vs-modified distinction explicit in the per-file label, so the user can still tell "added file" from "modified file" before approving.

     Prose-only summaries such as "body 含め、diff full preview" / "subject and body included" without actually rendering the corresponding blocks are forbidden — they leave the user without the material content needed to judge approve / adjust / cancel and trigger an immediate re-render request
   - **b. Per-commit accept gate**: wait for the user. Categorize the response per § Approval token closed list. **When sub-step a's diff-review mode branch used crit for this commit**: this gate's disposition comes from `references/crit-commit-review.md` § Procedure step 5's decision mapping instead — do not re-derive that mapping here. Set `gate_origin` to this sub-step (**b**) regardless of which path obtains the decision, so any later `Mid-loop adjust` re-entry stays consistent
   - **c. Land the candidate**: first, if `<candidate>^{tree}` equals `HEAD^{tree}`, this group has no content left to land (a re-derivation or a reverted gate edit emptied it) — **skip it, leaving `landed_count` untouched**, and move to the next group; committing an empty tree would exit non-zero and route a normal outcome into `d`'s stop path. Otherwise take **both** pre-commit captures § Post-commit auto-modify cycle bound compares against — `git status --porcelain=v1 --untracked-files=all -z` and `git diff --name-only "<candidate_parent>"` — immediately before the commit (the second cannot be reconstructed once the ref has moved), then set the index to the candidate's tree and commit that index with the candidate's message:

     ```bash
     git read-tree "<candidate>^{tree}" && git commit -F - <<'EOF'
     <subject>

     <body>
     EOF
     ```

     Issue both commands in a **single Bash invocation**, so nothing can touch the index between them. `read-tree` without `-u` writes the **index only**, so the working tree is untouched: the remaining groups' content stays where it is, and so does anything the run never staged (the § Workflow artifacts set among it). It does replace the index wholesale, so any staging the user had before the run is lost — their content stays in the working tree, but a partially-staged hunk (`git add -p`) is not recoverable from it. Procedure 3's gate reports that pre-run staging before any of this runs. Hooks run on the `git commit`, before the ref moves — a `pre-commit` / `commit-msg` hook keeps its veto, and a non-zero exit leaves `HEAD` where it was with nothing landed. On zero exit, **increment `landed_count` by 1**. Do **not** `git switch` / `git checkout` to the candidate instead — git judges checkout eligibility by working-tree dirtiness, not tree equality, so it aborts, and forcing it discards the unstaged artifacts
   - **d. Non-zero-exit retry (candidate-build or commit failure)**: if any of `a`'s tree-derivation / `git commit-tree` calls or `c`'s `read-tree` / `git commit` pair exits non-zero, retry that one command once after a 1–2 second sleep. On the second non-zero exit, render `candidate-build-failed (<reason>)` when the failure was in `a` (no commit was attempted — the gate had not even opened) or `commit-failed (<reason>)` when it was in `c`, where `<reason>` is the last non-empty line of stderr truncated to ≤ 80 characters; when stderr is empty or whitespace-only, render the same token with `(no stderr)`. Then **stop Step 10**. `landed_count` moves only where `c` sees a zero exit, so this step never changes it. Do not auto-recover (no force, no reset, no rebase, no amend). **Restore the index whenever the failure was in `c` after its `read-tree` had already succeeded**: that `read-tree` replaced the index wholesale with the candidate's tree, so run `git read-tree HEAD` before stopping. Undoing this step's own bookkeeping is not auto-recovery, and skipping it leaves a whole group's content staged in the user's index — the obligation `a`'s pathspec derivation carries for the paths it staged, which a boundary-derived group has no staged set to discharge (this call discharges both). For pre-commit hook rejections, instruct the user to fix the hook out-of-band and restart `/dev-workflow` in a new session — nothing landed and the working tree is untouched
5. **Post-commit auto-modify cycle bound**: run `git status --porcelain=v1 --untracked-files=all -z` **immediately before** `c. Land the candidate` and again after its zero-exit commit, and compare the two. Do **not** compare against Procedure 1's roster instead: a chain-present commit lands one step's tree while later steps and the quality gates have already edited the same paths, so those paths stay modified after it lands and a roster comparison cannot tell a hook's edit from the run's own remaining work. The comparison is path-level, so it also cannot see a hook edit to a path that was **already** dirty before the commit — that edit stays in the working tree and is absorbed by a later group instead of reaching this gate. It must also not mistake a moved `HEAD` for a hook: on the chain-present path a path whose working tree matches `HEAD` but whose boundary tree does not — a step's edit a later step reverted, or a file a step added and a quality gate deleted — turns dirty the moment its group lands, with nothing having written to the working tree. Since the commit touches only the index and the ref, **only a hook can change the working tree**, so compare `git diff --name-only "<candidate_parent>"` before and after the commit (unioned with each porcelain run's untracked `??` entries) and treat only paths that entered that set as hook-modified — that fixed left endpoint is unaffected by the ref moving, so it drops these false positives while leaving the already-dirty blind spot above exactly as stated. If the post-commit run shows changes the pre-commit run did not (a pre-commit hook auto-fixed the tree), ask the user a fold-or-defer question with explicit semantics — **`fold` (= staple the hook's edits into the just-landed commit)** or **`defer` (= leave them in the working tree for a later commit-plan iteration)**. Map the response per the **dedicated 5-branch → `fold` / `defer` / `cancel` / re-present-as-`adjust` classifier below** — the 5 input branches extend § Approval token closed list's 4 buckets (`accept` / `adjust` / `cancel` / `NOT approval`) with a 5th `defer-direction` branch specific to this gate, mapping to 4 distinct dispositions (explicit per-branch mapping — no `everything else` catch-all, so ambiguous / interrogative responses cannot silently land in `defer`):
   - **accept** (affirmation of folding — "fold" / "amend" / "現コミットに含める" or any semantic equivalent for incorporating the hook's edits) → `fold`
   - **adjust** (specific revision request — "defer just foo.ts but fold bar.ts" / "rename the subject before folding" / any concrete change demand that is neither a clean fold nor a clean defer) → re-present the gate via § Mid-loop adjust branch **f** `Ambiguous / un-classifiable adjust request` (clarifier); do **NOT** silently route to `defer`
   - **cancel** / **stop** → `Mid-loop cancel` per its canonical route
   - **NOT approval** (interrogative or non-committal — "look good?" / "どう？" / "これでいい？") → treat as `adjust` per § Approval token closed list and re-present the gate; do **NOT** silently route to `defer`
   - Otherwise — an unambiguous defer-direction response ("defer" / "後で" / "leave it" / "skip" / "later" or any semantic equivalent for postponing the hook's edits) → `defer`

   On `fold`: `git add -- "<file-1>" "<file-2>" ...` with **exactly the paths the post-commit run shows that the pre-commit run did not** — the hook-modified set as this Procedure's comparison derives it, not the whole post-commit run (which also lists every later group's still-uncommitted content), not the original commit's file list, and not the Procedure 1 roster; without this stage step `--amend` would silently keep the pre-hook tree. Then `git commit --amend --no-edit` (or `git commit --amend -F -` with the original subject + body) to incorporate them. The amend re-commits the same logical commit — `landed_count` is **not** re-incremented. On `defer`: leave the working tree as the hook left it; the next iteration of `Per-commit loop` (or a subsequent plan re-render via the `Mid-loop adjust` file-regrouping branch) will surface them. Re-commit is allowed at most once per logical commit; if a second commit attempt on the **same logical commit** also triggers auto-modify, abort Step 10 with `pre-commit hook unstable (commit <#k>: hook re-modified <files>)` where `<files>` is the porcelain-reported file list at the time of abort. Emit the partial-completion summary (same retry-once + stop policy as the `Per-commit loop`'s `Non-zero-exit retry (candidate-build or commit failure)` step). Surfacing the file list gives the user actionable context — they typically need to disable / fix the offending hook out-of-band before resuming
6. **Landed-commits invariant**: once a commit has zero-exit landed, it is **immutable**. The `adjust` flows below apply only to the un-landed commits starting from `#landed_count + 1`. Landed commits are shown in the numbered list as history for context but cannot be re-edited from inside Step 10
7. **Mid-loop adjust — closed-list branches** (treat any user response categorized as `adjust` per § Approval token closed list).

   **Gate-of-origin tracking**: every time Step 10 dispatches one of its three gates — commit-plan approval gate (Procedure 3), per-commit accept gate (Procedure 4 sub-step `b`), or fold-or-defer gate (Procedure 5) — set `gate_origin` to that gate's identifier before waiting for the user response. Branches **e**, **f**, and **g** below read `gate_origin` to know which gate to re-enter; without this tracking, an adjust-request raised at the fold-or-defer gate could silently fall back to the per-commit accept gate (or vice versa), losing the gate-specific framing (e.g. the in-flight just-landed commit's identity for `fold` decisions).

   - **a. Subject / body change only** on the in-progress un-landed commit: update the field, then jump back to `Per-commit loop` sub-step `a` for the same commit (do not move the per-commit pointer). The candidate must be **rebuilt** there, not reused — the message is baked into the commit object, so reusing the old candidate would land the pre-edit subject/body. Its tree is unchanged, so the rebuild is just a fresh `git commit-tree` over the same tree
   - **b. File regrouping** (merge / split / reorder / add / remove — **including splits or merges that change the un-landed commit count**, since both operations rebuild the un-landed portion and re-render): rebuild the un-landed portion of the plan, **re-render the numbered list in full** (with the landed prefix shown as history), and re-enter the commit-plan approval gate. On re-approval, the per-commit pointer resets to `#landed_count + 1` and execution resumes at `Per-commit loop` sub-step `a` for that pointer, which rebuilds that commit's candidate from the regrouped plan — a split or a reorder puts the affected groups on that sub-step's **Stale boundary → pathspec derivation**, since neither is expressible against a cumulative boundary tree
   - **c. Un-landed portion drops to 0 commits** (the user's adjust removed everything that was still pending): mark `Step 10: Interactive Commits` as `completed` and proceed to Step 11 — this is a normal completion, not a cancel
   - **d. Merge absorbs the un-landed remainder into an already-landed commit** → un-landed = 0: same disposition as the **Un-landed portion drops to 0 commits** branch above (normal completion)
   - **e. Adjust request targets an already-landed commit** (e.g., "change the subject of commit #1 (already landed)", "move file X from commit #1 to commit #3"): reject the request, surface the landed-commits invariant explanation (`landed commits are immutable inside the interactive-commit phase — exit and use git rebase -i / commit --amend outside the workflow if needed`), and re-enter the gate identified by `gate_origin`
   - **f. Ambiguous / un-classifiable adjust request**: ask the user a clarifying question and re-enter the gate identified by `gate_origin` (do not fall through silently)
   - **g. Actual-code changes made during the gate** (the user's adjust response indicates they edited a file in the commit's proposed set since its candidate was built): distinguish metadata-only edits (comment rewording, documentation text, non-functional spacing) from actual-code edits (logic, function signatures, types, control flow, or any change that could affect behavior). For metadata-only edits: rebuild the candidate in `a`, update the commit description if appropriate, and re-enter the gate identified by `gate_origin`. For actual-code edits: rebuild the candidate in `a` first — whose **Stale boundary → pathspec derivation** covers the edited group — so the updated diff comes from its `git diff "<candidate_parent>" "<candidate>"` range rather than a capture Procedure 1 no longer takes; surface that diff and require an explicit choice — **(1) continue without re-verification** (user acknowledges the change is a targeted fix consistent with the plan and no re-test is needed) or **(2) stop for re-verification** (stop Step 10, leave working-tree changes as-is, and instruct the user to re-run the check/test phase before continuing)
8. **Mid-loop cancel**: a response categorized as `cancel` per § Approval token closed list stops Step 10 with all landed commits preserved and all un-landed changes left in the working tree as-is. **The workflow does not revert** — the user is free to `git reset` / `git stash` / continue manually.
