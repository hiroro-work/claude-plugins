# Step 3 — Plan Review (extracted review-pass procedure)

Deep reference for `SKILL.md` **Step 3: Plan Review**. The heading, the internal-review purpose, the **Disabled-phase exception** (the `plan_review_enabled == false` skip and its closed list of causes), the **Always run (when `plan_review_enabled`)** closed list, the "No actionable findings" semantic-skip note, the pass framing ("Mark `Step 3: Plan Review` `in_progress` and run the single review pass"), the **No re-review loop here** paragraph, and the closing "Mark `Step 3: Plan Review` `completed`" line stay inline in `SKILL.md`. This file holds the pass itself — sub-step 1 (reviewer dispatch payload + the three review groups covering categories a–d), sub-step 2 (semantic judge → complete), sub-step 3 (apply improvements / reject + the approach-reconsideration self-audit + the prose-integrity self-check), the Return-point no-stall reminder, and sub-step 4. Unqualified `§ No-Stall Principle` / `§ Step N` references and `sub-step N` references resolve to `SKILL.md`.

1. Call the reviewer skill resolved in Step 1 (e.g. `Skill(ask-peer)`): Review the plan. **`subagent_model` propagation (inline reviewer)**: when the resolved reviewer is Claude-family (per Step 1's reviewer-family classification) and `subagent_model` is a model id, propagate it — pass `Model: <subagent_model>` to `ask-peer`, or include `--model <subagent_model>` in the dispatch instruction to `ask-claude`. External-CLI reviewers and an `inherit` resolution carry no model (current behavior). Step 3 is always inline, so there is no background-launch path to double-apply against here.
   **Pre-dispatch dispatch-boundary reminder**: Issue the `Skill(<reviewer>)` call in the same turn as any accompanying status prose — never produce a standalone status turn before the `Skill()` call, as that creates a stall point. Reading the reviewer's SKILL.md is preparation, not dispatch; the `Skill()` call is the dispatch.

   **Three independent review groups.** Declare the request as **three independent review units** and ask for one reviewer per group, run in parallel; a reviewer with no parallel dispatch runs all three in one sequential pass. **State in the request that the reviewer for a group reads only that group's Reads column and reports only the checks in its Covers column** — the whole request text reaches every reviewer, so without that line each one reads every group's references and re-reports every group's checks (G1a and G1b both read the whole of category (a), so each sees every sub-check in it). The split is by reading weight, not by category identity: category (a) carries both heavyweight references, so it is the one category served by two groups.

   | Group | Covers | Reads |
   | --- | --- | --- |
   | **G1a — Rules & premises** | a. **Scope & feasibility**, its dependencies / risks / `.claude/rules/` compliance leg, plus its **Premise challenge**, **Runtime/language major version upgrades**, **Generated-artifact regeneration on major upgrade**, **Shell content portability**, **External CLI behavior verification**, **External library primary-source verification** and **Internal convention citation verification** sub-checks | [`references/review-categories.md`](review-categories.md) § Plan review categories, category (a) only; the `.claude/rules/` files selected per the bullet below |
   | **G1b — Step 2 audit & structural sweeps** | a. **Scope & feasibility**, its "verify the author's Step 2 simplicity self-audit" leg, plus its **Cross-component sibling coverage**, **Closed-list extension audit** and **Internal cross-reference stability** sub-checks | [`references/review-categories.md`](review-categories.md) § Plan review categories, category (a) only; [`references/simplicity-self-audit-express.md`](simplicity-self-audit-express.md) and [`references/simplicity-self-audit.md`](simplicity-self-audit.md), which together hold the Step 2 audit checklist that leg verifies |
   | **G2 — Design & content** | b. **Approach & alternatives**, c. **Completeness**, d. **Presentation & attention allocation (content quality)** | [`references/review-categories.md`](review-categories.md) § Plan review categories, categories (b) / (c) / (d) only; [`references/plan-authoring.md`](plan-authoring.md) for the Decisions (a)+(b) criterion and § Step 3 (d) content-quality rubric; [`references/plan-format.md`](plan-format.md) § Empty-Decisions fixed sentences |

   **Merge order**: by category — G1a's and G1b's findings both belong to (a) and merge into one (a) block, then (b), (c), (d). The order does not depend on how the groups were drawn.

   Resolve every `references/*.md` link above to a concrete readable path when composing the request — the reviewer lacks the skill-directory context. Neither G1 group is handed `plan-authoring.md`, so where category (a) tells the reviewer to write a finding into a Decisions item's `Alternative` field, state the field shape in the request instead: each Decisions item carries `**Question**` / `**Recommendation**` / `**Alternative**`, the last omitted when there is no second option.

   On a `dev-workflow` run whose tier put it on the express lane ([`tier-assessment.md`](tier-assessment.md) § Lanes — Step 3 reaches this on Simple), G1b is handed `simplicity-self-audit-express.md` alone — that lane audited against it alone. Every other caller hands it both.

   - **`.claude/rules/` scope (G1a only)**: list the `*.md` files under `.claude/rules/` first, then read every one **directly under** that directory — those are the project-wide rules and always apply — and one under a **subdirectory** (`languages/` / `frameworks/` / `integrations/` / any custom directory) only when that subdirectory's domain matches what the plan touches. The plan has no changed-file list yet, so this is a prospective judgment on what the plan will touch.
   - **Every group receives**: the full plan body; `custom_instructions` when configured (have the reviewer verify alignment and report conflicts); and the instruction to report only actionable findings, explicitly stating "No actionable findings" when there are none. Every plan section, decision, and cited reference is in scope of the three groups taken together — this is a full-coverage pass.
   - **Apply only the sub-checks this plan triggers (every group)**: each sub-check in the rubric opens with the condition that fires it ("when the plan introduces a new state variable", "if the plan contains shell commands"). Tell the reviewer to decide that condition first and move on immediately when it does not hold, rather than reasoning about a check the plan cannot trip. Bias toward applying when the condition is genuinely uncertain: a wrongly-skipped check is a missed finding, a wrongly-applied one costs a few seconds.
   - **Express-lane plan shape (every group)**: on a `dev-workflow` run whose tier put it on the express lane ([`tier-assessment.md`](tier-assessment.md) § Lanes — Step 3 reaches this on Simple), tell the reviewer the plan was authored from [`references/step2-create-plan.md`](step2-create-plan.md) § Compact plan template rather than `plan-authoring.md` § Template, so the compact shape — the shorter Overview, the fixed-sentence Decisions, the absent `> Review guide` line — is not reported as a § Template / § Sizing guidance violation. Omit this item on every other run.
   - **If a state file is active** (executing a subtask from a decomposition), include the current subtask's scope in **every** group's request: list the subtask's `title` and `description`, then list what the other subtasks cover (to define out-of-scope). Instruct the reviewer that missing functionality belonging to other subtasks is **not** an actionable finding for this review — only findings scoped to the current subtask qualify. Omit this when no state file is active (single-task execution has no defined out-of-scope boundary).
2. Judge the reviewer's response semantically: if the reviewer reports nothing actionable — no actionable findings, no improvements to apply, no review points raised, or any other "nothing to report" outcome regardless of exact wording — mark `Step 3: Plan Review` as `completed` and proceed to Step 4 automatically. Per the No-Stall Principle, do not wait for user input and do not rely on exact-phrase matching; trust semantic judgment since the reviewer skill's phrasing varies (especially `Skill(ask-peer)` and other free-form-prose reviewers whose verdicts are natural-language Markdown rather than a fixed token).
3. Otherwise: autonomously apply improvements or reject inapplicable points with reason — do not ask the user for judgment on individual review findings.
   - **Approach-reconsideration self-audit (fires at most once per run)**: immediately after judging the reviewer's findings and **before** applying them individually, count them by severity. If either threshold trips — **Critical ≥ 3** OR **(Critical + Major) ≥ 10** — additionally scan the findings list for any item that surfaces an **approach-level alternative** (typical phrasings: "X の方が筋がよい", "existing X と統合できる", "switch to <sibling>", "use <existing-mechanism> instead", or any equivalent "the plan should adopt a different overall approach" framing). If at least one such approach-alternative finding is present, do **not** proceed with mechanical apply-and-continue — instead, treat the findings cluster as a signal that the plan's Approach selection itself is the root cause. Rewrite the plan with the approach-alternative finding's direction promoted into the Decisions section (Recommendation / Alternative swap or insertion-direction new Decision item, per the rewrite class), then **re-dispatch this same review pass once** against the rewritten plan, carrying the remaining findings forward as context for that reviewer. When the threshold trips but no approach-alternative finding is present (mechanical-fix-level findings only), proceed with the usual per-finding apply path. **This audit fires at most once per run** — a second trip of the threshold on the rewritten plan's own review does not re-fire it; approach reconsideration after that point is the Step 4 user-gate's responsibility.
   - **Prose-integrity self-check (post-fix)**: apply the same procedure as Step 8 sub-step 3's "Prose-integrity self-check (post-fix)" paragraph — re-read the surrounding paragraph as a single unit, verify no sentence is cut mid-word and no logical connective is broken — to the plan prose being edited (Decisions / Build order / Test plan / Risks / Unknowns paragraphs) in place of code / doc content.
   - Once the findings are applied (or rejected with reason), mark `Step 3: Plan Review` as `completed` and proceed to Step 4. Do **not** re-dispatch the reviewer to re-check the applied fixes — the plan's next review surface is Step 4's approval gate (see `SKILL.md` Step 3's **No re-review loop here** paragraph for why, and for the one audit-driven exception above).

   **Return-point no-stall reminder**: When the reviewer returns (regardless of outcome — findings reported, "No actionable findings", any non-error result), the next action — applying the findings, or the Step 4 transition — must be issued in the **next tool call**. Do not insert an interstitial summary or acknowledgment turn; the abstract enumeration in `§ No-Stall Principle` is intentionally duplicated here so the rule fires at the decision moment.
4. If actionable feedback still remains after the pass (points neither applied nor rejected), carry the unresolved points forward to Step 4.
