# Plan review in the browser

Read from `SKILL.md` Phase 5 (Plan Approval) when the browser gate runs, and from `plan-artifact.md` § Team-review gate. Unqualified `§` references point into `plan-approval.md`; `step N` refers to this file's list. The files it reads and writes are listed in `plan-approval.md` § Files.

## Browser gate

1. Probe `printenv CLAUDE_CODE_REMOTE`; `true` → return `fallback` and `rm -f` the served copy if one exists.
2. **Figures** (first launch only, re-authored after a figure comment, a rewrite, or an out-of-gate plan edit): write `<slug>.figures.md` with `## <section name>` blocks matching plan headings, one figure plus a one-sentence caption each, at most one per section and three per plan, plus an optional `## Hero` block rendered above the plan. Every label and number comes from the plan. Notation: a mermaid fence for a flow, a sequence, or a dependency graph; inline SVG with a `viewBox` for a position on an axis, a grid of records, or two rows compared. An inline-SVG figure is a `<figure>` wrapping the `<svg>` and its `<figcaption>`, with no blank line anywhere inside that block and no `<style>` element: colours and fonts go in presentation attributes (`fill`, `stroke`, `font-size`). Colours: strokes are `currentColor`, and a fill that carries meaning is `currentColor` under a `fill-opacity` of 0.08–0.2 set on the shape itself, never on a group holding text. Text takes no fill and inherits the reader's, except over a filled shape, where it takes the foreground that ground names. A figure that needs the viewer's palette takes its tokens from the "Figure-safe tokens" comment above `:root` in `<base dir>/scripts/plan-review/public/plan-view.css` — bare, with no fallback, each foreground over the ground named beside it, and either side of a pair usable as a fill. The caption is one sentence stating what the figure claims: a `<figcaption>`, or the paragraph directly under a mermaid fence.
3. **Compose**: if the served copy exists, `cp` it to `.plan-review.prev.md`. Write the served copy = canonical plan with figure blocks inserted (after Overview's bullets, before a Decision's first `**Question**`, before Build order's list, after a prose section's last sentence).
4. **Launch** in background Bash, with a status line in the same turn:
   `node "<base dir>/scripts/plan-review/serve.mjs" --plan ".claude/plans/<slug>.plan-review.md" --lang <language> --wait`, adding `--prev ".claude/plans/<slug>.plan-review.prev.md"` when that file exists, and `--port <n> --no-open` when a `.url` file from an earlier launch of this run gave a port (read it, then `rm -f` it first). Never pass `--timeout`. In the next turn read the `.url` file (up to 2 retries) and show the URL in one line on the first launch or when the port changed.
5. **Read the result** when the process exits: the one-line submit JSON on stdout, `{"decision": "approve" | "revise", "branch": "stay" | "new" | "stack" | null, "comments": [{"block", "section", "excerpt", "kind": "prose" | "figure", "body"}]}`. No JSON by the exit marker after 5 re-reads → `fallback`, unless the exit is non-zero and the previous launch did not also exit non-zero without JSON: then relaunch per step 4. When `branch` is set and differs from the Branch section's Recommendation, swap the two in the plan and the served copy.
6. **approve** → return `approve`; comments are advisory.
7. **revise** → apply every comment first: `prose` to the plan, `figure` and the `_hero` block to the figures file. Answer questions, apply change requests, locate blocks by `excerpt`. A comment on the Branch card (`section` `branch`) asking to work on another branch → return `wrong-branch` after recording the replies. Record each reply in `<slug>.plan-review.thread.json`, which the viewer owns: never create it — read it, fill the matching entry's `reply` and `disposition` (`answered` / `revised` / `both`), and write it back with the top-level `rounds` array and every entry's `id` / `block` / `anchor` intact (a malformed shape is dropped silently). Then: an approach-level change → return `rewrite-approach` (the plan already carries the edits); otherwise re-compose and relaunch (step 3). No iteration cap; Plan Review is not re-run for localized edits.
