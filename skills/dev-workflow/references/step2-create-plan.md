3. Analyze the task and codebase, create implementation plan. Apply `custom_instructions` to shape plan priorities and structure. **On the full lane** ([`tier-assessment.md`](tier-assessment.md) § Lanes) follow the structure defined in [`references/plan-authoring.md`](plan-authoring.md) — Overview / Decisions / Build order / Test plan required; Risks / Unknowns optional. Build order is always an ordered, numbered list of implementation steps, each shaped `N. **<heading>** — <detail>` (see that file's § Template). Section-level content rules live there; do not re-derive them here. **On the express lane** author from § Compact plan template below instead, and do not read `plan-authoring.md`.
   - **If a state file exists** (this run is executing one subtask of a decomposed parent): the "effective task" = the current `in_progress` subtask. Frame the plan around **just this subtask** while keeping the full parent task and other subtasks as background context so the plan stays consistent with the overall direction. Do not plan work belonging to other subtasks. See [`references/plan-authoring.md`](plan-authoring.md) § Subtask / Resume handling for how Decisions is scoped in this case — **full lane only**
   - **TDD-conflict resolution**: if `custom_instructions` includes a TDD-style requirement (e.g. "Always use TDD", "write tests before implementation") AND the current task is adding tests for **existing behavior** (characterization tests, coverage tests, or relocating existing tests — keywords: "add tests for", "characterize behavior", "test coverage", "move tests", "固定する", "追加する") rather than driving new implementation, declare explicitly in Plan Overview or Risks that this subtask is **TDD-loop-external**: tests describe and fix already-implemented behavior, not specification of new behavior.
   - **Version/identifier string replacement tasks**: if the core operation is replacing a specific version string, identifier, or constant across the project (e.g. version bump, rename, migration), grep the entire repository for the old value before drafting the plan. Include the complete list of affected files in the Build order section
   - **Task-relevant skill annotation** (applies to **every** plan — unconditional): scan the skills available in this session's context for any that materially help accomplish *this* task's own work, and annotate the Build order step(s) where each would be used — per [`references/plan-authoring.md`](plan-authoring.md) § Template, a Build order step's grammar carries the invoked skill as an optional element. Constraints: (i) **target task-domain skills only** — exclude any skill the workflow itself already fires at a fixed step (the reviewer, the cleanup pass, rules-review, the test skills, extract-rules are illustrative); judge exclusion by *"is this already a fixed-step callee?"*, not by matching a skill's name against that list — a task-domain skill that merely shares surface vocabulary with a callee still qualifies; (ii) annotate **only skills actually present** in the available-skills context — never invent a skill name; (iii) the annotation is a **recommendation, not a contract** — Step 5 may drop a suggested skill that turns out not to fit once implementation starts; (iv) annotate **only the step(s) where a skill genuinely applies** — most plans annotate few or no steps

   **Codebase-research delegation (optional, research-context isolation).** The default for Step 2 is main-thread analysis — the main thread reads the codebase and authors the plan directly. As an exception you MAY delegate the **codebase-research portion only** to a read-only subagent via the `Agent` tool, **only when both guards hold**: (a) the session exposes a subagent type effective for read-only codebase research — an `Explore`-class read-only researcher, or a `general-purpose` agent constrained to read-only by its dispatch prompt per (ii); (b) the task benefits from non-trivial codebase research — *research* meaning exploration to discover unknown files, patterns, or constraints; locating a known file or applying a settled mechanical change (a typo fix, a known-location edit, a routine bundle-copy sync) is **not** research and needs no delegation — plan a self-evident change of that kind with inline main-thread analysis. When delegating: (i) dispatch the read-only research subagent to return a condensed findings report (relevant files, patterns, constraints) — **plan authoring stays in the main thread** (the plan-format template, the Simplicity self-audit, the Decisions (a)+(b) criterion, and the Task-relevant skill annotation all remain main-thread work); (ii) **select the subagent type by capability — inverted from Step 5's rule**: Step 5 *excludes* read-only `Explore` / `Plan`-class agents because it needs `Edit` / `Write`, whereas this delegation is research-only, so it *prefers* a read-only research-capable type (`Explore` by default), falling back to a `general-purpose` subagent instructed to do read-only research only (its read-only scope is set by the dispatch prompt); (iii) it **propagates `subagent_model`** — pass `model: <subagent_model>` when it resolves to a model id, omit when `inherit`; Step 1.5's tier resolution settles the value before Step 2 begins; (iv) if guard (a) does not hold — the `Agent` tool is unavailable, or no read-only-research-capable type is exposed — skip the delegation and do the research inline in the main thread; (v) the returned findings report is research, not a user gate — judge it and continue per § No-Stall Principle. This delegation is one of the sanctioned `Agent` exceptions named in § Configuration's `Agent` tool usage bullet.

## Compact plan template

The **express lane's** plan shape ([`tier-assessment.md`](tier-assessment.md) § Lanes). Use the four required sections in their shortest honest form; read no part of [`plan-authoring.md`](plan-authoring.md).

```markdown
## Plan

### Overview
- **Goal**: 1 sentence — what the user gets
- **Difficulty**: Trivial | Simple
- **Scope**: N files — the files to touch
- **Approach**: 1 sentence — the chosen strategy

### Decisions
<one of the two fixed sentences below>

### Build order
1. **<heading>** — <detail, omitted when the change is self-evident>

### Test plan
<one line naming how the change is verified, or the justification for no tests>
```

- **The section set is the same four**, in the same order, at the same `###` level. `Risks / Unknowns` stays available and is omitted when empty. `Highlights` is omitted; noticing a high-impact item is an escalation signal (`SKILL.md` Step 2's "Confirm difficulty" sub-step).
- **Decisions renders a fixed sentence, always** — whichever of the two in [`plan-format.md`](plan-format.md) § Empty-Decisions fixed sentences the mode calls for. If a qualifying (a)+(b) item surfaces, escalate rather than filling the section in.
- **Build order keeps the `N. **<heading>** — <detail>` shape** even at one step.
- **The `> Review guide` line is omitted.**

**Express plan self-check** (sub-step 5, **Plan self-check**, on this lane — in place of `plan-authoring.md` § Step 2 self-check): confirm (i) the shape above holds — the four sections in order at `###`, with Decisions carrying one fixed sentence verbatim and nothing beside it; (ii) no Build order step answers a "why X over Y" or "why this specific value / boundary" question — one that does is a buried Decisions item, which on this lane is an escalation signal rather than something to promote in place; (iii) the Test plan names a verification for each Build order step, or carries in its place the no-tests justification the template allows.
