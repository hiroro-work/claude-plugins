# Interactive Commits (Step 10) — Procedure

Four unqualified `§` references below resolve outside this file: `§ Approval token closed list` and `§ Localized summary tokens` in [`finish-phase.md`](finish-phase.md), and `§ Phase naming in user-facing output` and `§ Workflow artifacts` in `SKILL.md`. All other `§` references resolve within this file.

**Output language.** Every line this Step puts in front of the user — the commit-plan presentation and the notes that join it, each commit's presentation, the gate questions, the informational notes, and the failure reports — is framed in the resolved `language` (see [`localization.md`](localization.md) § Localization granularity). It covers the framing only: content whose rendering a step below already specifies — a fenced block's contents, a path list, a diff hunk, a literally-named label — stays exactly as that step specifies it. An English example string a step offers for a line's shape fixes the shape, not the wording: that line's framing still takes the resolved `language`. Several sites below repeat the resolved-language instruction for their own output; do not read its absence at a site as putting that site outside this paragraph.

If the current plan explicitly deferred bookkeeping edits to the commit stage — for example, CHANGELOG entries or version-bump lines whose content was deferred until the implementation is confirmed complete — apply those edits now, before Procedure 1 collects the working tree. Use the plan's deferral language (e.g. "will add the CHANGELOG entry at commit time", "version bump deferred to Step 10") as the trigger. Apply these deferred edits autonomously, with no user gate before Procedure 1. If any edit call fails, stop Step 10 and report the failure to the user.

**Procedure**:

1. **Collect changes**: `<base-commit>` referenced throughout this Procedure is the value recorded by Step 2's opening sub-step (`git rev-parse HEAD` at workflow start — see `SKILL.md` § Step 2: Create Plan's first numbered item); Step 10 reuses that captured value verbatim, never re-resolves it. Run `git status --porcelain=v1 --untracked-files=all -z` once (`=v1` pins the format; `--untracked-files=all` overrides a user-side `status.showUntrackedFiles=no`; `-z` NUL-separates entries and suppresses C-style quoting, so filenames with spaces, quotes, or non-ASCII characters stay recoverable verbatim). Parse the NUL-separated output: entries prefixed `??` are untracked, others are tracked changes — and a rename (`R`) spends **two** NUL-separated fields, the new path and then the old, so consume both and keep only the new one. If the output is empty, mark `Step 10: Interactive Commits` as `completed` and proceed to Step 11 (nothing to commit since base-commit). Otherwise keep the parsed path list in memory as the canonical roster — Procedure 3 (§ Propose commit plan) groups it on the chain-absent path, and its Plan-scope cross-reference scans it for changes touching declared no-change areas. **Capture no per-file diff here**: each commit's diff comes from its own candidate at `Per-commit loop` sub-step `a`, so a `git diff <base-commit>` capture at this point would be wider than any single commit and — for a file that several commits touch — wrong for every one of them

   **Entry snapshot.** With the roster non-empty, record the whole working tree as a dangling commit. This is a single object naming the state the Step started from, not the per-commit delta the paragraph above forbids. Stage **every** path the roster holds — tracked changes and untracked alike — one explicit pathspec each, and run the whole thing as a **single Bash invocation** whose only stdout is the SHA:

   ```bash
   PRE=$(git write-tree) && git add -- "<path-1>" "<path-2>" ... && git commit-tree "$(git write-tree)" -p HEAD -m "dev-workflow Step 10 entry snapshot" ; git read-tree "$PRE"
   ```

   Separate the trailing `git read-tree "$PRE"` restore with `;` rather than `&&` so it runs even when the middle of the chain fails. Hold the printed SHA as `<step10_entry_snapshot>` — read only inside this Step (§ Propose commit plan reports it, § Per-commit loop sub-step `d` compares against it).

   **A failed snapshot never stops this Step**: on a non-zero exit, or when no SHA is printed, leave `<step10_entry_snapshot>` unset and continue, saying so in one line in the resolved `language` with a `<reason>` shaped as sub-step `d` shapes its own, e.g. `no entry snapshot recorded — no recovery point for this run (<reason>)`. Take it from the **earliest** failing command in the chain rather than the last stderr line `d` reads: when `git write-tree` fails first, `$PRE` is empty and the trailing `git read-tree ""` then writes its own `Not a valid object name` over the real cause. **One exception to unsetting the SHA**: when `git commit-tree` printed a SHA and only the trailing restore failed, keep the SHA — the snapshot is valid — and add a second line saying the index is left holding the roster's paths staged, so § Propose commit plan's staging report is not read as pre-run staging
2. **Deduce commit style**: run `git log -n 10 --format=%s` and infer the project's conventional commit style (presence of type prefix, imperative mood, etc.) — used as a runtime hint when drafting subjects, never hard-coded
3. **Propose commit plan**: Before grouping, run the default-branch guard and plan-scope cross-reference below, then group changes into 1+ logical commits, each `{subject, body (optional, may be empty), tree source}` — `tree source` being what the commit's tree is built from at `Per-commit loop` sub-step `a`. Which of the two grouping origins applies depends on whether Step 5 recorded a **Build-order boundary chain** (`implementation_boundaries` — see `SKILL.md` § Step 5's "Build-order boundary chain (sub-step 2.5)" paragraph):

   **Chain present** (`implementation_boundaries` is non-empty **and every recorded object still resolves** — probe each with `git rev-parse "<object>^{tree}"` and require a zero exit for all of them; a non-zero exit anywhere means the objects were reclaimed, which is the chain-absent cause below rather than a tree-derivation failure at sub-step `a`): propose **one group per boundary**, in chain order, each labelled with that boundary's Build order heading and taking that boundary object as its `tree source`; then add a **final group** covering everything not yet landed by the boundary groups — derived, not enumerated: `git diff --name-only` from the last boundary to the working tree, unioned with Procedure 1's untracked (`??`) paths — which that command never lists — minus the § Workflow artifacts set. That is usually the Step 6–9 quality-gate fixes plus any deferred bookkeeping applied above, but it also picks up anything the working tree carried that no Build order step staged. **Cohesion-split it** where its contents differ in kind, each part taking the pathspec derivation; in particular propose the release bookkeeping (the version bump and the CHANGELOG entry) as its **own** group. Omit any group whose delta against its predecessor is empty — the final group when the quality gates changed nothing, and equally a boundary group for a Build order step that edited no in-scope path. Adjacent groups MAY be merged where their concerns do not differ, but **do not merge by default** — the `Mid-loop adjust` file-regrouping branch is where the user collapses it further. **Two groups may both touch the same file**; the file-level staging constraint does not apply on this path (the condition is spelled out in [`simplicity-self-audit.md`](simplicity-self-audit.md)'s **Commit-split boundary alignment with file-level staging** item).

   **Chain absent** (`implementation_boundaries` is empty or its objects no longer resolve): group the collected change set **by cohesion** instead (concerns that differ → separate commits; typical case is a single commit), each group taking **its own pathspec** as the `tree source`. On this path a group's tree is built by staging that pathspec, so the groups must be file-disjoint. Say so in one line above the presentation, in the resolved `language` (see [`localization.md`](localization.md) § Localization granularity), e.g. `no Build-order boundary chain for this run — grouping by cohesion`.

   **Cross-layer split check**: when the collected change set spans multiple clearly-separable architectural layers (e.g. a new backend endpoint plus its test, a thin frontend wrapper that calls it, and the UI change that consumes that wrapper), do not default to bundling the whole set into one commit — surface a layer-based split as an explicit alternative grouping in the commit-plan presentation.

   **Default-branch guard**: before proposing any commit plan, check whether the current branch is the repository's default branch. First run `git symbolic-ref -q HEAD` — if it exits non-zero, HEAD is detached; skip the guard and continue. Determine the default branch name, resolving it **locally first**: run `git symbolic-ref -q --short refs/remotes/origin/HEAD` and strip the leading `origin/` (e.g. `origin/main` → `main`). Refreshing that ref is the user's job (`git remote set-head origin -a`), not this guard's. **Only when that local resolution exits non-zero** (the ref is unset in this clone) fall back to `git remote show origin` and read the branch name off its `HEAD branch:` line. Treat a non-zero exit or a missing `HEAD branch:` line alike as failure. If both resolutions fail (including `origin` not being configured), skip the guard and continue — but say so in one line above the commit-plan presentation, in the resolved `language` (see [`localization.md`](localization.md) § Localization granularity), e.g. `default branch could not be resolved — branch guard skipped`. Compare the resolved name against the output of `git rev-parse --abbrev-ref HEAD`. If they match — the current branch IS the default branch — create and switch to a new feature branch (`git switch -c <branch-name>` where `<branch-name>` is a kebab-case slug derived from the task; if that name is already taken, append a short disambiguator such as `-2` and retry once; if the second attempt also fails, stop and report the branch-creation failure to the user) before the commit-plan presentation. If the user indicates they intentionally want to commit on the default branch (e.g. a personal repo without PR workflows), skip the branch creation and note the choice in the commit-plan presentation.

   **Plan-scope cross-reference**: scan the approved plan for explicit "no-change" declarations — files, sections, or regions the plan stated would not be modified (phrasings like `"no changes"`, `"leave as-is"`, `"unchanged"`, `"not modified"`, `"read-only"`, or equivalent intent). Cross-reference against the collected change set from Procedure 1. If any collected change touches a declared no-change area, surface those paths as **unplanned changes** at the top of the commit-plan presentation — above the numbered commit list — naming each affected path and quoting the relevant plan text verbatim. Do not silently include unplanned changes in the proposed grouping; the user resolves them via the existing commit-plan approval gate's `adjust` (move to a separate commit with explanation, or exclude the path from every commit) or `cancel` branches. **Excluding a path** works by leaving it out of the group's intended path set, which moves a chain-present group onto `Per-commit loop` sub-step `a`'s **Stale boundary → pathspec derivation**. Do **not** use `git checkout HEAD -- <path>` to exclude, as that destroys existing uncommitted changes to the file. When no declared no-change areas exist in the plan, or no collected change overlaps with them, skip this cross-reference and proceed directly to the grouping.

   **Frozen-tree notice** (chain-present path, two or more groups — count groups, not boundaries: one boundary plus a non-empty final group still puts a frozen-tree commit ahead of another one): each boundary group's tree is what Step 5 recorded when that Build order step landed, so a per-commit gate comment on an *earlier* group cannot be answered in place — the edit lands in the working tree, which belongs to the final group, and `Per-commit loop` sub-step `a`'s **Stale boundary → pathspec derivation** then moves that group and every group after it off the chain. Say so before the user starts approving. This paragraph's header condition is the whole trigger — do **not** additionally test whether the Steps 6–9 gates touched a path an earlier group carries. One line in the resolved `language`, e.g. `each commit is a snapshot from when it was implemented — a review comment on an earlier commit cannot be fixed in place, so ask for fewer commits if you want to settle each one as you go`.

   Present the plan to the user as a numbered list — per group, its subject plus what that group covers (the Build order heading(s) behind it on the chain-present path, its path set on the pathspec-derived ones) — and wait at the **commit-plan approval gate**. Before waiting, run `git diff --cached --name-only`: when it is non-empty, name that pre-run staging in one line here — sub-step `c. Land the candidate` replaces the index wholesale, and on the chain-present path those entries already rode into the boundary trees Step 5 recorded, so their content lands inside the first boundary group's commit. Where the first group takes the pathspec derivation instead, its `git read-tree HEAD` discards the staging at sub-step `a` — before any commit — so a run cancelled at the very first per-commit gate has already lost it. **Name `<step10_entry_snapshot>` here too** when § Collect changes set it — its SHA plus the command that would restore the working tree from it (`git restore --source=<step10_entry_snapshot> --worktree -- .`) — so the user knows a recovery point exists before anything lands. **Display that command, never run it**: recovery is the user's call, and sub-step `d`'s "Do not auto-recover" line governs this Procedure throughout — subject to that same line's carve-out, since undoing this Procedure's own bookkeeping (its index restores, the `fold` amend) is not auto-recovery. Approval is judged per § Approval token closed list.

   **A caller may extend this gate** with a further way to accept. Evaluate any such extension against the plan this step has proposed, not ahead of it. This section presents no such option on its own. `Source of truth: mobpro references/m11-commit.md's Already-reviewed skip option (commit-plan gate) paragraph; keep in sync. Membership = every caller that extends this gate's accept options.`

4. **Per-commit loop** (`landed_count` was initialized to `0` at Step 10 entry in [`finish-phase.md`](finish-phase.md); no re-initialization is needed here — the counter is incremented only at sub-step `c. Land the candidate`, on its zero-exit `git commit`): process each commit in order:
   - **a. Build the candidate, then present it**: first build this commit's **candidate** — a dangling commit object carrying exactly the tree this commit will land, chained onto the current `HEAD`. Nothing lands and no hook runs here. Capture the parent SHA once as `<candidate_parent>` (`git rev-parse HEAD`). Two steps:

     **(i) Obtain the group's tree** from its `tree source` (Procedure 3 § Propose commit plan). Two derivations serve three kinds of group:

     - **From a boundary object** — a chain-present group still tracking what its boundary recorded: the tree is `<boundary>^{tree}`, and nothing is staged. A group that merged several adjacent boundaries takes the **last** boundary of that run: a boundary tree is cumulative, so an earlier one would drop the later steps' content.
     - **From a pathspec** — the chain-absent path, the chain-present **final group**, and any group the rule below moves here. First `git read-tree HEAD`, so the snapshot below is scoped to this group alone — `git write-tree` reads the **whole index**, not a pathspec, so without this anything else already staged rides into the candidate. Then stage this group's paths per [`diff-presentation.md`](diff-presentation.md) § Detached review object step 1 and `git write-tree` per its step 2. The staged set **excludes the § Workflow artifacts set**. What this stages is normally cleared by `c`'s commit, which replaces the index — but several exits leave before that commit (`c`'s empty-tree skip, `d`'s stop, § Mid-loop cancel, the normal completions at § Mid-loop adjust branches **c** / **d**, and branch **g**'s option (2) re-verification stop). On each of them, `git reset -- "<the paths staged here>"` before leaving. A chain-absent group stages exactly the path set Procedure 3 assigned it, and so does each part of a cohesion-split final group. Every other group here derives its own: `git diff --name-only` from the group's start point to its end point — start = the previous group's candidate, or `<base-commit>` for the first group; end = this group's boundary, or the working tree for the final group — minus any path the Plan-scope cross-reference excluded from this group. Where the end point is the working tree, union in the untracked (`??`) paths Procedure 1's roster recorded: `git diff --name-only` never lists an untracked path, so a file the quality gates added would otherwise be dropped from every group.

     **Stale boundary → pathspec derivation.** A boundary object is frozen at the moment Step 5 recorded it and its tree is cumulative, so a group whose tree must differ from what its boundary recorded **leaves the chain and takes the pathspec derivation** — and because every later boundary carries that same content, **so does every group after it**. Triggers (closed list): a path excluded at the Plan-scope cross-reference; a file edited **during Step 10's own gates** — `Mid-loop adjust` branch **g**, a `crit` round whose `scope: "line"` comment produced an edit — **either** branch of [`crit-commit-review.md`](crit-commit-review.md) § Round re-verification weight, since a metadata-only edit changes the group's tree just as an actual-code one does — or a `fold` in `Post-commit auto-modify cycle bound`; and a group produced by splitting or reordering the chain (branch **b**), which a cumulative tree cannot express at all. **A Steps 6–9 quality-gate edit is not a trigger**: those edits belong to the final group by design, and counting them as staleness would move every group off the chain and defeat the mechanism.

     **(ii) Wrap it** per [`diff-presentation.md`](diff-presentation.md) § Detached review object step 3, with `<base>` = `<candidate_parent>` and this commit's subject and body as the piped message → `<candidate>`. When a chain-present group merged several boundaries, the body is where the **constituent Build order step headings** go — one bullet per heading, so merging groups never silently drops what each step was.

     **Diff-review mode branch**: when `commit_review_gate` resolves to `"crit"`, resolve `crit_commit_review_available` **before reading anything** — the first time this branch is reached, run **both** probes unconditionally (run the second even if the first already failed): `crit --version` (non-zero exit / command-not-found → unavailable; do **not** substitute `command -v crit`, which sits outside the `Bash(crit *)` grant and would trip a permission dialog) and `printenv CLAUDE_CODE_REMOTE` (value `true` → the local browser is unreachable). Cache the combined result for the rest of the run; do not re-probe per commit. These are the same two probes [`crit-commit-review.md`](crit-commit-review.md) § Procedure step 1 owns. `Source of truth for the pair and for the note below: crit-commit-review.md § crit CLI contract and § Procedure steps 1–2; keep in sync. Membership = every site that runs the pair before reading that file — this branch, mobpro references/m11-commit.md's Diff surface paragraph, and mobpro references/diff-review.md § crit path.` The probes stay **independent of Step 4's own reachability probe**.

     A caller may additionally suppress crit for an individual commit; `mobpro` `references/m11-commit.md`'s **Already-reviewed skip option (commit-plan gate)** paragraph is today's only exerciser of that carve-out (`Source of truth: mobpro references/m11-commit.md's Already-reviewed skip option (commit-plan gate) paragraph; keep in sync. Membership = every caller that suppresses crit for an individual commit.`). **When both probes clear** and no caller has skipped crit for this commit, the Diff element below is obtained via [`crit-commit-review.md`](crit-commit-review.md) instead — skip the rendering-mode decision and the Diff bullet's verbatim / condensed / skeleton rendering for this commit, read that reference and follow its Procedure (its § Fallback contract still owns the launch-time failures the probes cannot foresee); its decision mapping resolves this sub-step's presentation / accept-gate pair directly (see sub-step **b** below). Subject / Body / Files / Verification below still render in chat regardless of this branch — crit reviews the code content, not the commit metadata. **Otherwise** (`commit_review_gate: "diff"`, the default, either probe failed, or a caller skipped crit for this commit per the carve-out above), continue with the presentation below unchanged. When a probe failed, additionally emit **one** informational note for the whole run — not per commit — in the resolved `language`, before this commit's chat rendering: when `crit --version` failed, name the install URL (<https://github.com/tomasz-tomczyk/crit>); when only the reachability probe failed, name that no local browser is reachable; when both failed, name the unavailability (the install URL) and leave the browser out of it. That is the whole of the note.

     Read [`diff-presentation.md`](diff-presentation.md) once when this loop starts. Then, for **each** commit, before rendering the five presentation elements, measure that commit's diff and pick one mode per [`diff-presentation.md`](diff-presentation.md) § Rendering ladder, holding it for every file in that commit's Diff element. The measurement input is `git diff "<candidate_parent>" "<candidate>"`, sliced per file on its `diff --git a/<path> b/<path>` boundaries. That single range needs no tracked / untracked split. The skeleton trailer's full-diff command is correspondingly uniform — `git diff "<candidate_parent>" "<candidate>" -- "<path>"` for every slice, whatever the file's tracked status in the working tree.

     Then show the five presentation elements as a **closed list** — Subject / Body / Files / Verification / Diff — each rendered in its own block as the user's approval basis:
     - **Subject**: render in a dedicated fenced code block (single line, no surrounding prose).
     - **Body**: render in a dedicated fenced code block. When the commit has no body, render the placeholder `(no body)` inside the block — a prose statement like "body included" / "no body needed" without an actual rendered block is **forbidden**.
     - **Files**: render as an explicit path list (one path per line, prefixed with `- `) — the paths the range measured above already names, read off its `diff --git` slice boundaries. On the `crit` path, where no chat range was captured, take them from `git diff --name-only "<candidate_parent>" "<candidate>"` instead.
     - **Verification**: render a one-line Step 7 outcome summary from memory (the result recorded when Step 7 ran earlier in the session). The rendered label is `Check / Test`, not the step number (§ Phase naming in user-facing output's "drop the number" option). Format: `Check / Test: <checks-result> / <tests-result>` when both were attempted but not both passed (e.g. `Check / Test: checks passed / tests skipped`, `Check / Test: checks passed / tests failed — see the check/test output above`); use the combined form when both passed (e.g. `Check / Test: all checks passed and tests passed`); use the slash form for all other outcomes. When the check/test phase did not run (Trivial difficulty skip, or no `check_commands` / `test_commands` configured), render `Check / Test: skipped`. Always include this slot — the user must never have to ask whether tests passed.
     - **Diff**: render the actual per-file hunks from the `git diff "<candidate_parent>" "<candidate>"` range measured above, using the mode decided there. A file this commit adds arrives as a new-file hunk from the range itself, so no separate capture is needed — but keep the added-vs-modified distinction explicit in the per-file label.

     Prose-only summaries such as "body 含め、diff full preview" / "subject and body included" without actually rendering the corresponding blocks are forbidden
   - **b. Per-commit accept gate**: wait for the user. Categorize the response per § Approval token closed list. **When sub-step a's diff-review mode branch used crit for this commit**: this gate's disposition comes from `references/crit-commit-review.md` § Procedure step 5's decision mapping instead — do not re-derive that mapping here. Set `gate_origin` to this sub-step (**b**) regardless of which path obtains the decision
   - **c. Land the candidate**: first, if `<candidate>^{tree}` equals `HEAD^{tree}`, this group has no content left to land (a re-derivation or a reverted gate edit emptied it) — **skip it, leaving `landed_count` untouched**, and move to the next group; committing an empty tree would exit non-zero and route a normal outcome into `d`'s stop path. Otherwise take **both** pre-commit captures § Post-commit auto-modify cycle bound compares against — `git status --porcelain=v1 --untracked-files=all -z` and `git diff --name-only "<candidate_parent>"` — immediately before the commit (the second cannot be reconstructed once the ref has moved), then set the index to the candidate's tree and commit that index with the candidate's message:

     ```bash
     git read-tree "<candidate>^{tree}" && git commit -F - <<'EOF'
     <subject>

     <body>
     EOF
     ```

     Issue both commands in a **single Bash invocation**. `read-tree` without `-u` writes the **index only**, so the working tree is untouched. It does replace the index wholesale, so any staging the user had before the run is lost — their content stays in the working tree, but a partially-staged hunk (`git add -p`) is not recoverable from it. Hooks run on the `git commit`, before the ref moves — a `pre-commit` / `commit-msg` hook keeps its veto, and a non-zero exit leaves `HEAD` where it was with nothing landed — though not necessarily with the working tree intact, which is what sub-step `d`'s **Working-tree survival check** is for. On zero exit, **increment `landed_count` by 1**. Do **not** `git switch` / `git checkout` to the candidate instead — git judges checkout eligibility by working-tree dirtiness, not tree equality, so it aborts, and forcing it discards the unstaged artifacts
   - **d. Non-zero-exit retry (candidate-build or commit failure)**: if any of `a`'s tree-derivation / `git commit-tree` calls or `c`'s `read-tree` / `git commit` pair exits non-zero, retry that one command once after a 1–2 second sleep — **except that a `git commit` which ran hooks takes the survival check below first, and a diverged tree cancels the retry.** That ordering is load-bearing: the content a hook failed to restore is often exactly what made the hook fail, so a blind retry can succeed, land the commit, and carry the run onward with the loss never reported. On the second non-zero exit, render `candidate-build-failed (<reason>)` when the failure was in `a` (no commit was attempted — the gate had not even opened) or `commit-failed (<reason>)` when it was in `c`, where `<reason>` is the last non-empty line of stderr truncated to ≤ 80 characters; when stderr is empty or whitespace-only, render the same token with `(no stderr)`. Then **stop Step 10**. `landed_count` moves only where `c` sees a zero exit, so this step never changes it. Do not auto-recover (no force, no reset, no rebase, no amend). **Restore the index whenever the failure was in `c` after its `read-tree` had already succeeded**: that `read-tree` replaced the index wholesale with the candidate's tree, so run `git read-tree HEAD` before stopping. Undoing this step's own bookkeeping is not auto-recovery, and skipping it leaves a whole group's content staged in the user's index. For pre-commit hook rejections, instruct the user to fix the hook out-of-band and restart `/dev-workflow` in a new session — nothing landed, though the working tree is **not** guaranteed untouched: a hook that shelves the unstaged delta and then fails to reapply its own shelf takes that content with it, which is what the check below exists to surface.

     **Working-tree survival check**. Run it at **either** point a `git commit` can fail with its hooks having run — `c`'s commit exiting non-zero, or § Post-commit auto-modify cycle bound's `fold` amend doing so — and run it **before the retry above and before the index restore**. Skip it only when `<step10_entry_snapshot>` is unset (§ Collect changes): report that no recovery point was recorded and carry on with the retry.

     Re-run § Collect changes' snapshot command over the tree as it now stands, re-deriving its roster from a fresh `git status --porcelain=v1 --untracked-files=all -z`, to get `<now>`. When **that** snapshot fails to print a SHA, the check cannot run: say so in one line and fall through to the retry, exactly as § Collect changes does for its own failure. Then compare **tree to tree**: `git diff --no-renames --name-status "<step10_entry_snapshot>" "<now>"` — `--no-renames` pins the comparison against a project `diff.renames` setting that would otherwise report a missing path as `R`. That second endpoint is what makes the check sound — a bare `git diff "<step10_entry_snapshot>"` reads the *index* on its right-hand side, which reports every path that was untracked at entry as `D` whether or not it still exists, and hides an untracked file whose contents a hook overwrote. Read the result directly:

     - **Missing** — reported `D`: the path was there at entry and is gone now.
     - **Diverged** — anything else the comparison names: the content differs. This run's own gate edits land here too (§ Mid-loop adjust branch **g**, a `crit` round's `scope: "line"` edit, a `fold`), and nothing tells those apart from a hook's damage, so report both sets rather than guessing which is which.

     **A non-empty result cancels the retry**: stop Step 10 at once rather than running the same hook a second time over a tree it has already damaged. This stop owes whichever index restore its call site owes — from `c`, the second-exit path's `git read-tree HEAD`, run before stopping whenever `c`'s `read-tree` had already succeeded; from the `fold` amend, that branch's own `git reset` over the paths it staged just before amending. Report the two sets as their own block alongside the failure line that call site renders (`commit-failed (<reason>)` from `c`, `amend failed (<reason>)` from the `fold` amend) — that wording keeps its form, so this adds a block rather than a new token — and render the restore command § Propose commit plan already reported. An empty result means the tree survived; fall through to the retry
5. **Post-commit auto-modify cycle bound**: run `git status --porcelain=v1 --untracked-files=all -z` **immediately before** `c. Land the candidate` and again after its zero-exit commit, and compare the two. Do **not** compare against Procedure 1's roster instead: a chain-present commit lands one step's tree while later steps and the quality gates have already edited the same paths, so those paths stay modified after it lands and a roster comparison cannot tell a hook's edit from the run's own remaining work. The comparison is path-level, so it also cannot see a hook edit to a path that was **already** dirty before the commit — that edit stays in the working tree and is absorbed by a later group instead of reaching this gate. It must also not mistake a moved `HEAD` for a hook: on the chain-present path a path whose working tree matches `HEAD` but whose boundary tree does not turns dirty the moment its group lands, with nothing having written to the working tree. Since the commit touches only the index and the ref, **only a hook can change the working tree**, so compare `git diff --name-only "<candidate_parent>"` before and after the commit (unioned with each porcelain run's untracked `??` entries) and treat only paths that entered that set as hook-modified — that fixed left endpoint is unaffected by the ref moving, so it drops these false positives while leaving the already-dirty blind spot above exactly as stated. If the post-commit run shows changes the pre-commit run did not (a pre-commit hook auto-fixed the tree), ask the user a fold-or-defer question with explicit semantics — **`fold` (= staple the hook's edits into the just-landed commit)** or **`defer` (= leave them in the working tree for a later commit-plan iteration)**. Map the response per the **dedicated 5-branch → `fold` / `defer` / `cancel` / re-present-as-`adjust` classifier below** — the 5 input branches extend § Approval token closed list's 4 buckets (`accept` / `adjust` / `cancel` / `NOT approval`) with a 5th `defer-direction` branch specific to this gate, mapping to 4 distinct dispositions (explicit per-branch mapping — no `everything else` catch-all, so ambiguous / interrogative responses cannot silently land in `defer`):
   - **accept** (affirmation of folding — "fold" / "amend" / "現コミットに含める" or any semantic equivalent for incorporating the hook's edits) → `fold`
   - **adjust** (specific revision request — "defer just foo.ts but fold bar.ts" / "rename the subject before folding" / any concrete change demand that is neither a clean fold nor a clean defer) → re-present the gate via § Mid-loop adjust branch **f** `Ambiguous / un-classifiable adjust request` (clarifier); do **NOT** silently route to `defer`
   - **cancel** / **stop** → `Mid-loop cancel` per its canonical route
   - **NOT approval** (interrogative or non-committal — "look good?" / "どう？" / "これでいい？") → treat as `adjust` per § Approval token closed list and re-present the gate; do **NOT** silently route to `defer`
   - Otherwise — an unambiguous defer-direction response ("defer" / "後で" / "leave it" / "skip" / "later" or any semantic equivalent for postponing the hook's edits) → `defer`

   On `fold`: `git add -- "<file-1>" "<file-2>" ...` with **exactly the paths the post-commit run shows that the pre-commit run did not** — the hook-modified set as this Procedure's comparison derives it, never the whole post-commit run (which also lists every later group's still-uncommitted content), the original commit's file list, or the Procedure 1 roster; without this stage step `--amend` would silently keep the pre-hook tree. Then `git commit --amend --no-edit` (or `git commit --amend -F -` with the original subject + body) to incorporate them. The amend re-commits the same logical commit — `landed_count` is **not** re-incremented. **When the amend itself exits non-zero**, its hooks ran, so take sub-step `d`'s **Working-tree survival check** first, then abort Step 10 the same way the hook-unstable abort below does — the partial-completion summary plus a warning line `amend failed (<reason>)`, **not** a fourth failure token: the token set stays closed at the three this Procedure already names — `candidate-build-failed` and `commit-failed` at sub-step `d`, and `pre-commit hook unstable` below. Before stopping, `git reset -- "<file-1>" "<file-2>" ...` over exactly the paths staged just above, so the run does not leave the hook's edits in the user's index. There is **no retry here**: `d`'s retry covers `a` and `c` only. On `defer`: leave the working tree as the hook left it; the next iteration of `Per-commit loop` (or a subsequent plan re-render via the `Mid-loop adjust` file-regrouping branch) will surface them. Re-commit is allowed at most once per logical commit; if a second commit attempt on the **same logical commit** also triggers auto-modify, abort Step 10 with `pre-commit hook unstable (commit <#k>: hook re-modified <files>)` where `<files>` is the porcelain-reported file list at the time of abort. Emit the partial-completion summary (same retry-once + stop policy as the `Per-commit loop`'s `Non-zero-exit retry (candidate-build or commit failure)` step).
6. **Landed-commits invariant**: once a commit has zero-exit landed, it is **immutable**. The `adjust` flows below apply only to the un-landed commits starting from `#landed_count + 1`. Landed commits are shown in the numbered list as history for context but cannot be re-edited from inside Step 10
7. **Mid-loop adjust — closed-list branches** (treat any user response categorized as `adjust` per § Approval token closed list).

   **Gate-of-origin tracking**: every time Step 10 dispatches one of its three gates — commit-plan approval gate (Procedure 3), per-commit accept gate (Procedure 4 sub-step `b`), or fold-or-defer gate (Procedure 5) — set `gate_origin` to that gate's identifier before waiting for the user response. Branches **e**, **f**, and **g** below read `gate_origin` to know which gate to re-enter; without it, an adjust-request raised at one gate silently falls back to another and loses the originating gate's framing (e.g. the just-landed commit's identity for `fold` decisions).

   - **a. Subject / body change only** on the in-progress un-landed commit: update the field, then jump back to `Per-commit loop` sub-step `a` for the same commit (do not move the per-commit pointer). The candidate must be **rebuilt** there, not reused — the message is baked into the commit object, so reusing the old candidate would land the pre-edit subject/body. Its tree is unchanged, so the rebuild is just a fresh `git commit-tree` over the same tree
   - **b. File regrouping** (merge / split / reorder / add / remove — **including splits or merges that change the un-landed commit count**, since both operations rebuild the un-landed portion and re-render): rebuild the un-landed portion of the plan, **re-render the numbered list in full** (with the landed prefix shown as history), and re-enter the commit-plan approval gate. On re-approval, the per-commit pointer resets to `#landed_count + 1` and execution resumes at `Per-commit loop` sub-step `a` for that pointer, which rebuilds that commit's candidate from the regrouped plan — a split or a reorder puts the affected groups on that sub-step's **Stale boundary → pathspec derivation**
   - **c. Un-landed portion drops to 0 commits** (the user's adjust removed everything that was still pending): mark `Step 10: Interactive Commits` as `completed` and proceed to Step 11 — this is a normal completion, not a cancel
   - **d. Merge absorbs the un-landed remainder into an already-landed commit** → un-landed = 0: same disposition as the **Un-landed portion drops to 0 commits** branch above (normal completion)
   - **e. Adjust request targets an already-landed commit** (e.g., "change the subject of commit #1 (already landed)", "move file X from commit #1 to commit #3"): reject the request, surface the landed-commits invariant explanation (`landed commits are immutable inside the interactive-commit phase — exit and use git rebase -i / commit --amend outside the workflow if needed`), and re-enter the gate identified by `gate_origin`
   - **f. Ambiguous / un-classifiable adjust request**: ask the user a clarifying question and re-enter the gate identified by `gate_origin` (do not fall through silently)
   - **g. Actual-code changes made during the gate** (the user's adjust response indicates they edited a file in the commit's proposed set since its candidate was built): distinguish metadata-only edits (comment rewording, documentation text, non-functional spacing) from actual-code edits (logic, function signatures, types, control flow, or any change that could affect behavior). For metadata-only edits: rebuild the candidate in `a`, update the commit description if appropriate, and re-enter the gate identified by `gate_origin`. For actual-code edits: rebuild the candidate in `a` first — whose **Stale boundary → pathspec derivation** covers the edited group — so the updated diff comes from its `git diff "<candidate_parent>" "<candidate>"` range; surface that diff and require an explicit choice — **(1) continue without re-verification** (user acknowledges the change is a targeted fix consistent with the plan and no re-test is needed) or **(2) stop for re-verification** (stop Step 10, leave working-tree changes as-is, and instruct the user to re-run the check/test phase before continuing)
8. **Mid-loop cancel**: a response categorized as `cancel` per § Approval token closed list stops Step 10 with all landed commits preserved and all un-landed changes left in the working tree as-is. **The workflow does not revert** — the user is free to `git reset` / `git stash` / continue manually. Record the partial state per § Localized summary tokens
9. After all commits land, or the user cancels (see `Mid-loop cancel`), or the `Mid-loop adjust` un-landed-drops-to-zero / merge-absorbs-into-landed branches complete the un-landed work, mark `Step 10: Interactive Commits` as `completed` and proceed to Step 11
