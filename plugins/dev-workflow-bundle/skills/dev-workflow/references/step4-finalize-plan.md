# Step 4 — Finalize Plan (extracted presentation procedure)

Deep reference for `SKILL.md` **Step 4: Finalize Plan (USER APPROVAL GATE)**. `SKILL.md` keeps inline: the heading + USER APPROVAL GATE designation, the sub-step 1 / sub-step 1.5 labels + delegation pointers, sub-step 2's header line, and sub-step 3's four-bucket response closed list (accept / swap-decisions / rewrite-approach / withdraw) — each bucket's name + one-line semantics — plus the read-back sub-step and the NOT-approval handling. This file holds: sub-step 2's presentation body (the plan-body prose-polish pass, the plan-document establishment, the browser-reachability probe, and the visual-gate → chat-approval routing); **sub-step 1's Step 3-completion verification procedure** (§ Sub-step 1 — Step 3-completion verification); **sub-step 1.5's Prose-language self-audit procedure** (§ Sub-step 1.5 — Prose-language self-audit); and **sub-step 3's rewrite-approach bucket runtime** — the `--fast` exception + the express-lane re-activation re-derivation (§ Sub-step 3 — rewrite-approach bucket runtime). `SKILL.md` Step 4 delegates each in its numbered position. Unqualified `§ Configuration` / `§ Workflow artifacts` / `§ No-Stall Principle` / `§ Step N` / `§ Prerequisites` references and `sub-step N` references resolve to `SKILL.md`.

   **Plan-body prose polish (runs when `polish_prose` is `true` and `fast_mode_active` is not `true`, after the plan document is written and before it is presented).** **Skip when `polish_prose` is not `true`, or when `fast_mode_active`** (the `polish_prose` case fires only when explicitly set to `false`; the default `true` and a non-boolean fall-back-to-`true` both run — see § Configuration's `polish_prose` bullet; the `fast_mode_active` case follows the same silent-skip discipline as Step 6.5's fast-mode skip — plan-body prose-polish is purely cosmetic, unlike Step 6 Tidy / Step 7.5, which fast mode keeps running): skip this `prose-polish` call **silently** and present the un-polished plan — emit no note, because the user gate immediately follows and a skip note would only clutter the attention-sensitive presentation (contrast Step 6.5's impl-file prose-polish call, whose note is its only run-signal). When both conditions allow it, once the full plan body has been written to `.claude/plans/<slug>.md` (established below) and after sub-step 1.5's **Prose-language self-audit** has brought the explanation prose into the resolved `language` (so this polish refines language-correct prose, never prose still pending translation), and **before** presenting it — before delegating to the visual gate, which copies its served file from `.claude/plans/<slug>.md`, or before the chat presentation when the probe skips the gate — invoke `Skill(prose-polish)` in **file mode**: `Files:` = the plan document path, **plus the decomposition state file's canonical path when a state file is active** ([`task-decomposition.md`](task-decomposition.md) § Canonical state-file path); `Language:` = the resolved `language`; and **no `Model:`** (see § Configuration's `subagent_model` bullet). Pass both paths in a single invocation. The state file earns its place here because its subtask `description` / `verification_hint` prose is written for the user to read and no other pass polishes it; on an undecomposed run there is no state file and `Files:` carries the plan document alone. **Its prose sits inside YAML block scalars**, so instruct prose-polish to leave each line's leading indentation exactly as found — a shifted indent breaks the schema validation every `--resume` run performs. Re-polishing the same state file on each subtask's run is harmless: prose already settled returns `no-change`. **Anti-skip guard**: do not skip this dispatch when `polish_prose` is `true` merely because sub-step 1.5's **Prose-language self-audit** returned clean or because the prose appears concise; the self-audit corrects language-level translation errors, but prose-polish refines naturalness and fluency and may still improve prose even when the self-audit passes. It rewrites only the resolved-language explanation prose in place via surgical `Edit`s, leaving headings, identifiers, code blocks, and `git`-shaped tokens verbatim; it runs on every difficulty tier (a plan is presented on every tier). **§ Workflow artifacts non-conflict**: both targets — the plan document and the state file — are workflow artifacts that Step 6.5's impl-file scope excludes, so the two `prose-polish` call sites never overlap. Judge the verdict semantically and proceed per § No-Stall Principle: on a `done` / `no-change` verdict present the (possibly-polished) plan; on `error` emit a one-line note and present the un-polished plan rather than blocking — prose-polish ran and returned this verdict, so nothing is appended to `bundle_skills_unavailable` (an `error` status is not an availability signal). A `Skill()` call failure after one retry is the distinct availability signal — the skill itself is unreachable — and additionally appends `prose-polish unavailable (plan-body polish)` to `bundle_skills_unavailable` (§ Step 1 sub-step 3's "Initialize the bundle-unavailability ledger here" bullet). The verdict is a return-point covered by § No-Stall Principle — do not pause after it.

   **Establish the plan document.** Resolve `<slug>` **once per run, then reuse it verbatim on any Step 4 re-entry** (a `rewrite-approach` re-entry must not re-resolve it). Reuse the active decomposition state file's `slug` when a state file is in play, otherwise derive a kebab-case slug from the effective task (transliterate non-ASCII where reasonable, strip punctuation, lowercase; on collision with an existing `.claude/plans/<slug>.md` **from a prior run**, suffix `-2`, `-3`, … — this collision check applies only to first resolution, never on re-entry against this run's own `<slug>.md`), mirroring `references/task-decomposition-normal.md` § B. Normal sub-mode's slug algorithm. Then write the **full** plan body to `.claude/plans/<slug>.md` (the canonical plan document that work-complete archives and that § Completion's cleanup preserves; on a decomposed parent, successive subtasks reuse the parent slug and overwrite this `<slug>.md`, which is harmless because the plan document is per-run and the separate `dev-workflow.<slug>.md` state file carries cross-subtask state). The plan was internally reviewed in Step 3 when `plan_review_enabled`; when it is `false` (`SKILL.md` Step 3's Disabled-phase exception) Step 3 was skipped, so this user-approval gate is the sole review — carry any unresolved Step 3 points into the presentation either way.

   **Run the approval gate.**

      - **Trivial-tier route.** When the assessed tier is **Trivial** ([`tier-assessment.md`](tier-assessment.md) § Lanes), go straight to the **chat approval** below **without reading** `references/visual-plan-review.md`, and skip the probe. A Trivial plan is the compact template's handful of lines (`references/step2-create-plan.md` § Compact plan template), and a browser round-trip to approve it costs more attention than the plan itself does — the same reasoning that keeps the probe from paying for a gate that cannot display. This is keyed on the **assessed tier**, never on `plan_review_enabled` being `false`: a configured `plan_review: false` or a `--fast` run produces that without the tier being Trivial (the same discriminator `references/plan-format.md` § Step 4 guidance lines' Disabled-plan-phase conditional keys on). Simple stays on the visual gate — only Trivial takes this route.
      - **Browser-reachability probe** (skipped on the Trivial route above)**.** Run `printenv CLAUDE_CODE_REMOTE`. A value of `true` (the cloud-execution marker Claude Code on the Web sets) means the local browser is unreachable and the gate can never display: go straight to the **chat approval** below **without reading** `references/visual-plan-review.md`, which would otherwise cost a full read on every such run only to return `fallback` from its own first steps. Any other value — including unset or empty — means local execution; continue with the visual gate. **Anti-skip guard**: this probe's `true` result is the *only* thing that licenses skipping the gate reference. Skipping it on a guess — including rationalizing under § No-Stall Principle that chat is faster — silently disables the gate (the reported "plan never displayed" failure) and remains a defect.
      - **Visual gate**: read [`references/visual-plan-review.md`](visual-plan-review.md) and follow it top to bottom. Following it writes the served file from `.claude/plans/<slug>.md`, launches the browser gate via background Bash, and loops internally on localized `revise`, returning one of three outcomes: **`approve`** → the gate has written the latest plan back to `.claude/plans/<slug>.md`, and the browser submit is itself the final confirmation, so proceed directly to implementation; **`rewrite-approach`** → a revise comment requested an approach-level material change; handle it exactly per sub-step 3's `rewrite-approach` bucket (the gate has written the latest plan to `.claude/plans/<slug>.md`); **`fallback`** → continue with the chat approval below (the reference's § Fallback contract still owns the launch-time failures the probe cannot foresee — a non-zero `serve.mjs` exit, a startup failure, or a blocked launch call). The visual path does **not** emit the chat condensed view / preamble / guidance line — the browser is the review surface.
      - **Chat approval** (entered on the Trivial route, when the probe returned `true`, or when the visual gate returned `fallback`): render it per [`references/plan-format.md`](plan-format.md) § Step 4 presentation order's chat output sequence, which ends on a pointer to the plan document written above and a wait for the user's chat reply. Classify that reply per sub-step 3's four buckets.

   Section headings (`Overview` / `Decisions` / `Build order` / `Test plan` / `Risks` / `Unknowns`) and the Step 4 guidance line stay English on both surfaces.

## Sub-step 1 — Step 3-completion verification

1. Before presenting, verify via `TaskList` that `Step 3: Plan Review` is `completed` — presenting the plan for approval is the effective end of internal review, so reaching it while that row is still `pending` or `in_progress` skips the review entirely. If the row is not `completed`, emit a one-line inline note to the user naming it (e.g., `Plan review found incomplete (Step 3: Plan Review still pending) — running the review pass before presenting the plan.`) then return to Step 3 to process it (do not flip the row to `completed` without doing the review work). **Exception**: when `plan_review_enabled` is `false` (`SKILL.md` Step 3's Disabled-phase exception) — so the row is already `completed` — that completed state is the intended skip, not an unrun-review bug, so proceed to the approval presentation normally.

## Sub-step 1.5 — Prose-language self-audit

1.5. **Prose-language self-audit**: Before presenting the plan for approval, verify that explanation prose in the plan body (Overview narrative, Decisions rationale, Build order descriptions, Test plan steps, Risks/Unknowns paragraphs) is written in the resolved `language`. Schema tokens (`Overview` / `Decisions` / `Build order` / `Test plan` / `Risks` / `Unknowns`), step labels, enum values, identifiers, and quoted code strings stay in their original form regardless of `language`. Audit both directions: (a) if any explanation sentences are in a different language than the resolved `language`, and (b) if concept words outside the verbatim-preserve scope — ordinary nouns, adjectives, conjunctions, verb phrases — are over-preserved in the source language rather than rendered in the resolved `language` (per [`references/localization.md`](localization.md) § Localization granularity's Negative-direction rule). Revise any failures now per [`references/localization.md`](localization.md) § Localization granularity before proceeding to sub-step 2. **Re-entry coverage**: this audit must re-run on every entry into Step 4 — both the initial entry and any re-entry triggered by sub-step 1's "return to Step 3" path or sub-step 3's material-change path — since revisions made while applying Step 3's findings may introduce prose in a language different from the resolved `language`.

## Sub-step 3 — rewrite-approach bucket runtime

The **rewrite-approach** bucket's one-line semantics (re-open Step 3, read-back, return to Step 3, re-enter Step 4 from sub-step 1) stay inline in `SKILL.md` Step 4 sub-step 3. This section holds the bucket's full runtime — the disabled-plan-phase exception and the express-lane re-activation re-derivation:

- **Base behavior**: mark the `Step 3: Plan Review` row `pending` again, run the read-back sub-step, return to Step 3 to re-review the modified plan (one further single pass), then re-enter Step 4 from sub-step 1 (so sub-step 1's completion check on the re-opened row and sub-step 1.5's prose-language re-entry-coverage audit both run before re-presenting at sub-step 2). This re-open is the plan phase's one re-dispatch path outside Step 3's own approach-reconsideration self-audit; the plan being re-reviewed is a rewritten one, not the same plan iterated.
- **Exception — the plan phase held off by a standing choice** (applies on a **full-lane** tier only; on an express-lane tier the reactivation below takes precedence): **`--fast`-forced `plan_review_enabled = false`**, or a **configured `plan_review: false`** (§ Configuration's `plan_review` bullet). In both, skip the re-open and return-to-Step-3 legs entirely — apply the revision to the plan document, run the read-back sub-step to confirm it, then re-enter Step 4 directly from sub-step 1, since `plan_review_enabled` stays `false` through the rewrite. A configured `false` on an express-lane tier therefore falls to the reactivation, whose own guard keeps Step 3's row `completed` — the tier judgment is reopened, the plan phase stays off.
- **Express-lane re-activation**: if the assessed tier put the run on the **express** lane ([`tier-assessment.md`](tier-assessment.md) § Lanes — Trivial or Simple), an Approach-level material change means the task is no longer self-evident at that tier. Keying on the lane rather than on Trivial alone matters because **Simple** also carries four pre-completed rows and a plan authored without `plan-authoring.md`: a Simple run whose approach is rewritten needs the same re-derivation, and would otherwise wait for the Step 5-completion checkpoint to get it. **Key this on the assessed tier, not on `plan_review_enabled` / `code_review_enabled` being `false`** — a configured `plan_review: false` or `code_review: false` produces that without the tier being express, so inferring the tier from a flag would fire this reactivation on a project that merely turned a review phase off. **Re-derive the tier against the rewritten plan**: reset `difficulty_skipped_steps = []` and `fast_mode_skipped_steps = []` — both are rebuilt from scratch by the re-run, so neither is amended in place (a `--fast` express run may well have a non-empty `fast_mode_skipped_steps` here, from the plan-phase forcing on a Simple tier) — then re-run [`tier-assessment.md`](tier-assessment.md) § Resolution procedure in full against the rewritten plan. **Clamp the re-assessment upward**: take `max(pre-rewrite tier, new assessment)`, so a rewrite that scopes the task *down* cannot lower the tier and re-disable a review phase mid-run — that is what keeps [`tier-assessment.md`](tier-assessment.md) § Escalation's one-way invariant true of this site too, and it is why a rewrite that leaves the run still on the express lane is admissible: nothing downstream has run yet, and the steps that would have been reopened are still ahead. It re-initializes `plan_review_enabled` / `code_review_enabled` from config and the newly assessed tier — one of the two exceptions to their monotonic-lowering invariant (`references/step1-load-settings.md` § Sub-step 4 — review-phase resolution) — re-resolves `subagent_model`, rebuilds both ledgers from scratch, and re-marks the rows the new tier skips. Re-running the whole procedure rather than just the two flags is required because every downstream gate keys on the tier: `subagent_model`, the difficulty-skip matrix, and the replacement-sentence choice in `references/plan-format.md` § Step 4 guidance lines' "Disabled-plan-phase conditional" paragraph all read it. Then **clear back to `pending`** every row the pre-rewrite assessment had marked `completed` that the clamped tier no longer skips: the top-level `Step 8: Code Review` row and its `Step 8-1` row **when the re-derived `code_review_enabled` is `true`** — it always is on a clamped tier above Trivial *unless* the project configured `code_review: false`, in which case leave their `completed` state in place; the top-level `Step 3: Plan Review` row **unless** the re-derived `plan_review_enabled` is still `false`, which happens on either of two guards — `fast_mode_active` with the re-run re-forcing it `false` for the clamped tier above Trivial (which re-marks the row `completed` and re-appends its `fast_mode_skipped_steps` entry as part of that re-run), or a configured `plan_review: false` (which adds no ledger entry — see § Configuration's `plan_review` bullet); and any of `Step 6: Tidy` / `Step 6.5: Polish Prose` / `Step 7.5: Rules Compliance Review` / `Step 11: Update Rules`. Finally, **when the clamped tier leaves the express lane**, apply [`tier-escalation.md`](tier-escalation.md) § What an escalation does' **Read what the express lane deferred** step — the plan was authored on that lane and now needs the full lane's shape. When the clamp lands the run back on the express lane, skip that step: the deferred references still do not apply. Without this re-derivation the Step 3 entry-point guard would skip the re-opened review pass (it skips whenever `plan_review_enabled` is `false`), Step 4's completion check would loop on the unprocessed row, and a stale-`completed` quality-step row would silently skip a step the higher tier now requires. This bullet's **review-phase row-clearing condition** is the source of truth for that condition; [`tier-escalation.md`](tier-escalation.md) § What an escalation does step 2 mirrors it for the escalation checkpoints and points back here — edit the two together.
- **Why the exception is safe**: the reactivation's own trigger is **the assessed tier being express-lane**, which is false whenever `--fast` forced the plan phase off on a Moderate / Complex tier and false on such a tier whose plan phase is configured `false` — in both, the Step 3 skip is a deliberate standing choice rather than a possibly-mistaken difficulty judgment about this task, so an approach rewrite does not reopen it. The `--fast` Step 6.5-only skip is re-evaluated only when `references/tier-assessment.md` § Resolution procedure actually re-runs (the express-lane reactivation case), not when the exception above fires.
