### Step 10: Interactive Commits

After hooks.on_complete (which may itself modify the working tree, e.g. via auto-formatter or apply-edit hook entries), propose **one commit per approved Build order step** — from the landing points Step 5 recorded, refreshed with the Steps 6–9 gates' own later edits to the paths that step wrote — plus a final commit for what those gates changed elsewhere, and iterate with the user one commit at a time. When no landing points were recorded, fall back to grouping the working-tree changes by cohesion. The `git push` is **never** performed by this step (or any other step): pushing commits to a remote is the user's responsibility.

**Unexpected current branch is not itself a signal to investigate**: if the current branch differs from earlier in the session, that is expected when the execution environment pre-creates or switches to a dedicated working branch before the first tool call. As long as the current branch's history contains `<base-commit>` (recorded in Step 2 — verify with `git merge-base --is-ancestor <base-commit> HEAD`; zero exit = it does), treat the difference as normal and skip any root-cause investigation. If that check exits non-zero, the branch does not descend from `<base-commit>` — not the expected pre-created-branch case: stop and surface the discrepancy to the user for direction (consistent with the No-Stall Principle's allowance for explicit step-defined stops) rather than investigating or switching branches unilaterally.

Step 10 is followed by Step 10.5 (Post-Commit Verification), which runs the verification its `crit` rounds deferred and lands the deferred queue's fixes as one additional commit.

### Step 10.5: Post-Commit Verification

The commit phase's **single** verification cycle, together with the commit that carries whatever it and the deferred queue produce. It runs once, after every commit the plan proposed has settled.

**Entry.** Mark `Step 10.5: Post-Commit Verification` `in_progress`, then run the three sub-steps below in order. **When `deferred_commit_fixes` and `commit_fix_files` are both empty, none of them fires** — fall through to the completion line at the end of this section. 1. **Apply the deferred queue.** Skip when `deferred_commit_fixes` is empty. Otherwise take its entries in the order they were queued and apply what each `request` asks for, appending every edited path to `commit_fix_files`. Two entries need no fix applied: one the tree already satisfies because an earlier entry's fix covered it, and one whose target can no longer be located because the region it named is gone. Neither is forced — say which in one line each, naming the unlocatable ones as unapplied here, since no § Completion reminder reads this queue. Then set `deferred_commit_fixes = []`.
2. **Verify once**, over the union of everything the commit phase touched. Two legs, in order — the same shape Step 8.5 (Deferred Verification) takes over `review_fix_files`. Both read `commit_fix_files` **after** sub-step 1's applies, so a fix only the queue produced is verified too.
