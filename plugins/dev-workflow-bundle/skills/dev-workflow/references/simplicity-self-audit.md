# Step 2 Simplicity self-audit

The **full lane's** half of the `SKILL.md` Step 2 sub-step **Simplicity self-audit** — read on Moderate and Complex tasks ([`tier-assessment.md`](tier-assessment.md) § Lanes). Read [`simplicity-self-audit-express.md`](simplicity-self-audit-express.md) **first**: its items are part of this same checklist and are not repeated here, and its preamble carries the (i)/(ii) remedy pair and the precedence rule that govern this file's items too. Then, before proceeding to Step 3, audit the plan against every item below.

## Checklist

- **Domain-assumption verification (externally-provided design documents)**: when the task's input includes an externally-provided design document — a specification, architecture document, requirements document, or any equivalent externally-authored artifact that names specific entities, relationships, or domain terms the plan will implement — verify that the document's core domain assumptions (which entities are involved, how they relate, what each domain term maps to in the codebase) align with the actual codebase structure before accepting them as given. Verify the alignment from primary sources (read the relevant models, schemas, or module structures) and surface any mismatch or uncertainty as a question to the user before finalizing the plan.
- **Blast-radius classification primary-source verification**: when a plan element's scope boundary or Decisions rationale rests on a classification of how broadly a change propagates — whether an artifact is distributed / public output (shipped to users, part of a public API, included in a release) or internal / local (project-internal, not distributed, not user-visible) — verify that classification from a primary source (the artifact's actual registration status, publication mechanism, and placement) rather than inferring from placement convention or prior-session assumption; if the classification is wrong, correct the scope boundary and Decisions rationale before proceeding to Step 3.
- **Decision rationale primary-source tracing**: after drafting each Decisions item's rationale, verify that the rationale derives from a **primary technical fact discovered during this run's investigation** — observed runtime or build-time behavior, an explicit constraint confirmed by reading the target file, or a requirement stated directly by the user — rather than from a secondary reference such as a sibling component's pattern or an analogy from adjacent code, whose applicability to the current target was not independently verified in this run. When the investigation surfaced a primary fact that conflicts with a secondary reference the rationale might cite, the Decision must reflect the primary fact and note the conflict explicitly. When a convention or sibling pattern is cited as the rationale, cross-check it against the current target's actual observed behavior before treating the citation as load-bearing.
- **Porting/migration parity verification**: when the task involves **porting or migrating** existing behavior, design, or implementation from a source location to a target location (adapting an established pattern, incorporating existing logic into a new variant, replicating a feature across contexts), verify each plan-level design decision — especially **"keep as source" vs "diverge from source"** split decisions — against the **actual behavior of the source** before finalizing the plan. Each decision to diverge must carry an explicit rationale classifying it as either (a) **unavoidable constraint** (the target context does not support the source's approach, or the constraint is stated in a rule / requirement) or (b) **untracked gap** (the source behavior was not replicated because it was not yet addressed). For (a), record the constraint in Decisions. For (b), surface the gap as a tracked deferral (subtask unit with state file) or a named Risks entry — do not leave it as an implicit assumption.
- **Deferred-work tracking vocabulary**: when a plan element is proposed for deferral outside the current scope (moved to Risks, a follow-up note, or a separate task), distinguish explicitly between (a) **tracked deferral** — the deferred work is queued as a subtask unit with a state file reachable via `--resume`; future progress requires no additional context reconstruction — and (b) **untracked deferral** — the work is recorded in Risks/Unknowns as a memo only; no state tracking, and starting it later requires reconstructing context from scratch. Name the deferral type and its tracking implication explicitly when presenting the plan.
- **Deferred-work surfacing in fixed location**: when a plan records a scope-out decision, surface the deferred work's (a) **what and why** and (b) **next steps** — the intended approach or follow-through path for when that work is eventually started — at a fixed, reachable location in the plan, conventionally a named Risks entry. For a tracked deferral that entry cites the `--resume` state file as the follow-through reference; for an untracked one the entry is itself the reference (see **Deferred-work tracking vocabulary** above). Do not bury this inside Decisions rationale prose.
- **Externally-blocked primary objective as first-class tracked deferral**: when the subtask's **primary objective** — the central change the subtask was created to make — is blocked by an external factor (an upstream interface not yet available, a hard dependency constraint outside the current scope), **cut the blocked work out as a tracked deferral** (queued as a subtask unit with `depends_on` linkage, reachable via `--resume`) rather than folding it into a Risks note or an optional yes/no confirmation — set this as the primary Decisions Recommendation. **Discriminator:** a blocked element is the primary objective when removing it from the current subtask's scope leaves only bookkeeping, scaffolding, or preparatory work with no standalone delivery value; if substantial independently-deliverable work remains, the blocked element is a major component rather than the primary objective, and it belongs in Risks with the **Deferred-work tracking vocabulary** classification above. After the cut-out, re-scope the current subtask's plan body to its remaining unblocked work and add a Risks entry citing the new subtask state file as the follow-through reference (per **Deferred-work surfacing in fixed location** above).
- **Commit-split boundary alignment with file-level staging**: **skipped when `interactive_commits` is `true`** — Step 5 then records a Build-order boundary per step and each commit's tree comes from its boundary rather than from a pathspec, so two commits may both touch the same file (`references/interactive-commits.md` § Propose commit plan owns the routing; when that chain turns out absent at Step 10, its chain-absent path re-imposes file-disjointness and surfaces the constraint at the commit-plan gate instead). Otherwise: verify that each proposed commit's file set is **disjoint** — if two logically separate changes both land inside the **same file**, file-level `git add -- <paths>` staging cannot separate them into different commits. At plan time, resolve the conflict with one of: (a) merge the two into a single commit, (b) redesign so the changes land in separate files, or (c) record in Decisions why a file-granularity constraint applies and how the split will be achieved outside file-level staging (e.g. the user performing hunk-level splitting out of band before resuming Step 10); at Step 10 commit approval, surface the constraint so the user can perform the split before accepting the commit.
- **Cross-component pattern alignment**: when the plan touches a structural pattern shared across sibling components (shared base classes, cross-cutting middleware, return/API contracts, mirrored services, parallel route handlers), audit three alignment directions. (i) Propagating a fix outward — if the plan fixes a structural defect in one component, check whether siblings sharing the structure carry the same defect; either expand the plan's scope to cover them or add an explicit Risks entry deferring them with a one-line rationale. (ii) Aligning a new component inward — if the plan adds a new component alongside an existing sibling group, decide explicitly in Decisions whether to follow the siblings' shared shape (iteration-loop form, responsibility-split unit, return-contract form) or intentionally diverge. (iii) Intra-patch self-duplication — if the plan itself lands the same processing pattern (shared validators, common error handling, mirrored formatting / serialization logic) at multiple call sites within this single change, treat those sites as siblings under (i): a defect at one site is likely present at the others, and a fix to one must be applied to the rest of the same-pattern sites in the patch.
- **Consistency-with-siblings as primary rationale**: when a plan element's primary rationale is "align with existing sibling implementations / for consistency" alone (i.e. not directly traceable to (a) explicit user requirement, (b) known bug or constraint, or (c) documented project rule), surface lighter alternatives alongside the consistency choice in Decisions — for example a scope-narrowed single-pass implementation, a hybrid that gates auto-application on specific conditions, or a detection-only design that delegates application to the caller. When `consistency-with-siblings` is chosen, additionally record in one line the cost of taking a different shape from the siblings.
- **Experimental feature gating overrides sibling-consistency default**: when introducing a new config flag whose gated behavior is **experimental** — the behavior was added in a recent release and the CHANGELOG / SKILL.md prose still marks it as "experimental", "recently added", "still in trial", or any equivalent immaturity signal — prefer **opt-in** (default disabled) as the Recommendation even when adjacent / sibling config flags default to enabled. Sibling-consistency is a real concern (handled by the bullet above) but yields here. Set Recommendation `<flag>: false`, place the sibling-direction `<flag>: true` as Alternative in Decisions, and cite the experimental marker (specific CHANGELOG bullet wording or SKILL.md prose) in the rationale. The override applies until the feature graduates — a later release removes the experimental marker or no further fixes target it; revisit the default in a follow-up plan at that point.
- **New-knob default vs. same-type sibling baseline**: when the plan introduces a new config flag, phase-skip gate, or behavior-toggle mechanism, scan the same skill for **existing same-type sibling mechanisms** (other flags, gates, or toggles that govern the same class of behavior). For each sibling found, note whether it is unconditional (always-active by default) or conditional (opt-in / dependent on a condition). When siblings are unconditional, the first-candidate default for the new mechanism is also unconditional; prefer asymmetry only when a positive justification applies — name the sibling, its effective default, and the justification in Decisions. The **Experimental feature gating overrides sibling-consistency default** bullet above is one recognized justification; a user-approved Decisions rationale is another.
- **Platform-capability-dependent default change**: when the plan changes default behavior to depend on a specific **execution-environment capability** — a runtime API, a host-provided tool, a platform-version-gated feature, an SDK / extension surface, or any equivalent capability whose presence is determined by the deployment / runtime environment rather than by in-repo configuration — explicitly enumerate the **target execution / distribution environments** the change must support and confirm the capability is uniformly available across all of them before adopting an **exclusive switch** (the new capability becomes the sole code path, prior method retired) as the Recommendation. If uniform availability cannot be confirmed for at least one target environment, surface a **conditional-fallback** design as a co-equal Decisions Alternative ("capability-present → new method / capability-absent → fall back to prior method"), so the Step 4 user gate surfaces the environment divergence and the user can affirm or reject the exclusive switch. Distinct from the **Experimental feature gating overrides sibling-consistency default** bullet above — that covers maturity of the feature; this covers **availability divergence across the target environment set** regardless of maturity.
- **Peer-dependency compatibility on major version bumps**: when the plan includes a **major version bump** (semver major digit increases) for any dependency or platform component, verify — using primary sources (the new version's published peer dependency range or support matrix, and the actual installed version of co-existing core dependencies) — that the updated dependency's declared peer range is compatible with every core dependency already resolved in the target environment. Perform this cross-check before finalizing the plan; when incompatibility is found, surface it as a Decisions item — Recommendation: adopt the most conservative version all resolved core dependencies safely support; Alternative: proceed with the originally-planned version and accept the incompatibility risk — so the Step 4 user gate can affirm or reject the version choice explicitly. This is the author-side counterpart to the Step 3 reviewer's `Runtime/language major version upgrades` check, answered one step earlier.
- **Upstream-handoff agreement override**: when the plan overturns a design decision explicitly stated in a prior-session-agreed upstream document (handoff materials, archived design records, decision logs), enumerate the diff (current plan's placement / value / shape vs. the upstream-agreed one) explicitly in Decisions. Set the Recommendation / Alternative pair to "uphold upstream agreement" and "overwrite upstream agreement", and annotate the chosen item with an explicit override marker (`upstream-override` for `language: en`, `先行合意上書き` for `language: ja`) so the Step 4 user gate surfaces the divergence and the user can affirm or reject the override. Distinct from the "Inherited spec files" bullet above in this Simplicity self-audit — that covers AI-authored draft elaborations from prior sessions, this covers user-agreed design decisions from them.
- **Temporary-workaround minimal coupling**: when an added plan element is explicitly declared as a **temporary workaround** awaiting a known removal trigger (upstream bug fix, feature flag rollout, deprecation window expiry, or any condition the user or upstream document names), set **minimal coupling** — local placement, a single dedicated hook point, and no intervention with the caller's other logic / state machine / counter set — as the **first-class Recommendation** in Decisions. Place deep integration (state-machine weaving, callee chains entered from multiple hook points, per-iteration record schema extension, sibling-file synchronization) as the **Alternative**, with an explicit one-line rationale on **removal cost** — how many files / sections / counter sites / cross-references must change when the removal trigger fires. Removability (deletion blast radius) must also appear as a required Risks evaluation axis for any plan element whose temporary nature is declared up-front.
- **Domain-state composition explicit decomposition**: when a plan element's feature requirement depends on a **composition of multiple independent state values** — boolean AND / OR over per-source state flags (e.g. an OS-level permission state AND a server-side user-preference flag, a build-time feature flag AND a runtime config value, a multi-source authorization state combining session / role / resource ownership) — enumerate the constituent state values explicitly in Decisions: name each, identify its source (OS / server / config layer / etc.), and document how they compose into the derived predicate (AND / OR / N-value truth table). Required Test plan companion: include a **state-space combination table** enumerating every combination of constituent values (or every equivalence-class boundary combination when the space is large) and the expected outcome per cell, so implementation cannot pass with a one-constituent gate-check.
- **Sub-skill natural-language argument minimalism**: when the plan procedure specifies passing a **natural-language argument** to a sub-skill (a free-text scope hint, an instruction prefix, a per-invocation directive), default to a **short scope-only sentence** rather than a long contextualized preamble. Three rules: (a) the argument states the **minimum scope only**; context, history, and surrounding information are **not** added by default; (b) extra context is added only when strictly required; (c) when the short form does not select the expected scope, the fallback is **state preparation before the call** (switching to the target branch, staging the working tree, pre-resolving a config value) rather than appending preamble text. This audit applies symmetrically across all sub-skill call sites in the plan body — flag and trim long defensive preambles added "to be safe".
- **Project-convention tension surfacing as binary Decisions item**: when the plan's default behavior is potentially in tension with a **project convention** that the same repo enforces (distribution rules in `CLAUDE.md` / `.claude/rules/`, auto-load scope conventions, naming or placement conventions, paired-bump or release-bookkeeping rules), **enumerate the tension as a binary Decisions item** with (i) **keep-default**: default behavior unchanged + opt-in config to enable convention-aligned behavior, and (ii) **change-default**: default flipped to convention-aligned behavior, with CHANGELOG opt-out note and explicit behavior-change signal. The Recommendation can be either side, but the Alternative field MUST be the other — never leave the convention-tension implicit in the plan's prose. Both directions are legitimate candidates: surface them symmetrically rather than hiding the change-default option.
- **Symptom-mitigation vs root-cause-fix discrimination**: when the task is a bug fix (the plan is shaped around an observed failure mode), explicitly classify each proposed change as either (a) **symptom-mitigation** — the change suppresses the firing condition of the observed symptom without correcting the underlying state-machine asymmetry / lifecycle gap that produces it (e.g. "discard stale entries on read" for a save-on-completion gap, "reset the counter at session start" for a missing-decrement path), or (b) **root-cause-fix** — the change corrects the state transition / lifecycle / invariant that produces the symptom (add the missing save-on-completion event, add the missing decrement). When the plan is composed entirely of (a)-class changes, surface this explicitly in Decisions as a recorded judgment (Recommendation: "ship mitigation only" vs Alternative: "extend the plan to include a root-cause fix"), with a one-line rationale, and add the structural cause to Risks even when not fixed in this scope.
- **Existing-contract preservation alternative**: when the plan's default approach would change an established subagent / callee / API contract (return schema, dispatch shape, side-effect set, `allowed-tools` surface, sub-step boundaries — any interface multiple consumers already rely on), enumerate **contract preservation + outer-layer adaptation** as a parallel Alternative alongside the contract-change Recommendation. The Alternative names where the same target objective can be reached without touching the contract — main-thread synthesis from the callee's existing detection-only output, a caller-side mapper / translation layer, or a wrapper that adapts the new outcome into the existing contract shape. Compare on three axes: (i) sweep cost (how many reference sites must change under the contract change), (ii) contract preservation (downstream callers' invariants stay intact), (iii) blast radius (how many consumers are affected). Evaluate the contract-preserving option first. Surface the choice as a binary Decisions item; the Recommendation may be either side, but the Alternative MUST be the contract-preserving option when contract change is the proposed default.
- **Sibling-mechanism extension alternative enumeration**: when the plan adds a new feature to a target module that already exposes **N ≥ 2 sibling mechanisms** for adjacent purposes (existing `--<flag>` modes, plugin / strategy / variant classes, config-branch families, named sub-skills — any pre-existing closed set of N siblings sharing a common dispatch surface), the Decisions section MUST enumerate two sibling-extension Alternatives alongside the "independent new addition" Recommendation: (i) **extend the responsibility of the most-closely-aligned existing sibling** to cover the new behavior (single-sibling scope expansion), and (ii) **merge the new behavior into the existing sibling group's shared dispatch surface** as a new variant of the same shape (full sibling-pattern inheritance). Enumeration may be skipped only when N = 0 / 1, or when an upstream task / handoff document explicitly mandates separation; record the rationale in a one-line note when skipping. The Step 3 reviewer's Cross-component sibling coverage sub-check covers this verification.
- **Conditional-skip set external-config exclusion**: when the plan introduces a mechanism that conditionally skips or gates a set of steps (difficulty-tier skip matrix, feature-flag-gated bypass, or any equivalent condition), audit each step in the proposed skip set for **project-specific external configuration dependency** — steps whose behavior or output is determined by per-project user settings (hooks, project-local config files, custom integrations) rather than a fixed skill-internal default. Default: exclude config-dependent steps from the skip set and run them unconditionally; when exclusion is infeasible, add a Risks entry justifying inclusion and documenting the expected cross-project variance.
- **External/vendor modification vs. repo-internal lever**: when any plan element's default approach involves modifying a file **outside the current repository** — a dependency package's source, an SDK's configuration, a framework's shipped default, or any vendor-owned artifact not under direct project control — audit whether a **repo-internal lever** achieves the same outcome (an override file, a config key, an adapter layer, an in-repo patch mechanism, or any equivalent abstraction that keeps the modification inside the project boundary). Surface the choice as a binary Decisions item: Recommendation = repo-internal lever, Alternative = direct external modification (modify the vendor file and accept the ownership / upgrade-churn implications). Record the internal-lever path even when it is less direct or requires additional scaffolding. When no internal lever exists, record the absence explicitly in the Decisions rationale.
- **Structural-pattern class enumeration before scope finalization**: when the plan proposes a change to a **structural pattern** — a recurring shape appearing in multiple instances within the codebase (error-handling forms, dispatch call sites, validation boundaries, state-variable lifecycle declarations, return-contract schemas, closed form-sets, or any equivalent multi-instance pattern) — enumerate the full class of instances **before finalizing the plan scope**: list every code site that participates in the same pattern, classify each as in-scope (the plan updates it) or out-of-scope (deferred with an explicit reason), and record the closed list in Decisions. When the full class is large and exhaustive enumeration is impractical within this plan's scope, enumerate the immediate siblings (same file / same dispatch group) and record "full class: deferred" as an explicit Risks entry rather than leaving the remainder implicit.
