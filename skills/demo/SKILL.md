# demo

```text
/demo [--plan <path>] [--base <ref>] [--lang ja|en] [--model <id>]
/demo --init
```

`--init` runs Setup mode only: it proposes and writes the settings, then stops with the return contract (`status: "ok"`, no capture). When a settings file already exists it stops with `status: "skipped"`, `reason: "settings exist"` and never overwrites. Without `--init`, a run that finds no settings file enters Setup mode by itself and continues into the demo.

Invocation contract, as fields in the invocation text (a field counts as provided when its value is non-empty): `Plan:` (the plan document the feature was built from; optional), `Base ref:` (git ref the diff is taken against; default `HEAD`), `Language:` (optional, see § Language), `Model:` (optional, see § Model). The command-line flags map onto the same fields.

Everything the run produces goes under `.demo/<slug>/` at the repository root: the screenshots, the recording, `steps.json`, `server.log` and `index.html`. The directory is meant to be gitignored and is never committed by this skill.

## No-Stall Principle

The only paths that do not reach § Return contract with `status: "ok"`, each ending with the contract's JSON block: `playwright-cli --help video-chapter` exiting non-zero (`playwright-cli not installed`); a settings file that exists but cannot be read (`settings unreadable`); no `start_command` after the merge (`start_command unset`); `cancel` at the Setup gate (`setup declined`); `--init` with a settings file present (`settings exist`); `.claude/demo.md` appearing between the Setup gate and its write (`setup conflict`); neither a readable plan nor a diff (`nothing to demo`); `skip` at the start-failure gate (`dev server not ready`); `skip` at the step-table gate (`declined at step table`); the capture agent's second unparseable reply (`no parseable capture result`); a capture result that fails the schema check (`capture schema violation`); the renderer rejecting `steps.json` (`page rejected`). Once the app has been started, every one of these runs § Procedure step 7 (Stop the app) before emitting the block.

The capture agent's reply is a return value: judge it and issue the next tool call at once. A re-capture is one more pass through § Procedure step 6, bounded by `<capture round>`, and its result is judged like the first; a first round with `failed` steps is not a stopping point. The data check's browser is closed before the step-table gate on every path. Non-fatal outcomes are recorded and the run continues: a step marked `failed`, a missing recording, a missing or failing `Artifact` tool, `.demo/` or `.playwright-cli/` not gitignored, a process still listening after the stop.

## Settings

Two files, YAML frontmatter only: `.claude/demo.md` (shared by the team, committed) and `.claude/demo.local.md` (personal, gitignored). The local file overrides the shared one key by key; a `null` or empty value in the local file clears the key.

| Key | Default | Meaning |
|---|---|---|
| `start_command` | required | Starts the app. Runs as `DEMO_PORT=<port> <start_command>` in the background; the app is expected to listen on `DEMO_PORT` |
| `reset_command` | none | Runs once, in the foreground, before `start_command`, as `DEMO_PORT=<port> <reset_command>`. Resets a throwaway environment |
| `url` | none | Starting with `http://` or `https://`: the URL itself, with `${VAR}` expanded from the environment plus `DEMO_PORT`. Otherwise a command run after the start as `DEMO_PORT=<port> <url>`; the first line of its stdout is the URL |
| `ready_timeout` | `120` | Seconds to wait for the URL to answer, at most 590 |
| `port` | none | When set, used as `DEMO_PORT` instead of a free port found at run time. Digits, or `${VAR}` expanding to digits: the port itself. Otherwise a command run before the start as `DEMO_PORT=0 <port>`; the first line of its stdout is the port |
| `auth_state` | none | Storage state file passed to `playwright-cli state-load` after the browser opens |
| `error_cases` | `true` | `false`: derive no error-case steps. Any other value is `true` |
| `video` | `full` | `normal`: the recording stops after the normal-case steps; the error cases are still captured but are not in the recording. Any other value is `full` |

When neither file exists, or `--init` was given, read `references/setup-mode.md` and follow it. When a file exists but `Read` fails for any other reason, or when it cannot be told whether the file is missing or unreadable, stop with `status: "error"`, `reason: "settings unreadable: <path>"` rather than entering Setup mode. When the merge leaves no `start_command`, stop with `status: "error"`, `reason: "start_command unset"`.

## Language

`Language:` or `--lang`, when given, is the language and nothing is read. Otherwise resolve it by reading only the `language` key from the YAML frontmatter of `~/.claude/dev-workflow.local.md`, `.claude/dev-workflow.md` and `.claude/dev-workflow.local.md`, in that order, later files overriding earlier ones; a `null` or empty value clears it, and a missing file, or one without frontmatter, contributes nothing. If none sets it, take `language` from `~/.claude/settings.json`; otherwise use `ja`. The page's fixed labels, the step table and every line written for the user follow the resolved language.

## Model

`Model:` or `--model` is applied as the `model` parameter of the capture `Agent` dispatch. It is valid only if it is one of the ids the current `Agent` tool's `model` parameter accepts; check the tool's live schema in this session. A full `claude-*` id is not among its aliases and is invalid. An absent or invalid value is treated as `sonnet`.

## Dispatch authorization

This skill's procedure dispatches subagents, so invoking the skill **is** the request to use that mechanism: an ambient instruction allowing subagent dispatch only when the user asked for it — a **permission-shaped restriction** — is already satisfied by this invocation. Do not ask the user to re-confirm the dispatch, and do not silently substitute inline execution for a dispatch this procedure specifies. Only two things justify that substitution: **technical availability** (the dispatch tool is not present and callable on the current tool surface), and an **explicit contract term from the caller** bounding this skill to its own thread. A permission-shaped restriction is neither.

## Procedure

`<base dir>` is this skill's directory as the harness reported it when the skill loaded.

1. **Preconditions.** Run `playwright-cli --help video-chapter`. A non-zero exit stops with `status: "error"`, `reason: "playwright-cli not installed"`. When its output starts with `playwright-cli video-chapter`, `<chapters>` = `true`; otherwise `<chapters>` = `false` and say in one line that this version records without chapters, cursor or action callouts. Then resolve the settings per § Settings (Setup mode when neither file exists), the language per § Language and the model per § Model.

2. **Inputs.** With `Plan:`, `<slug>` is the file name without `.md`; `Read` the plan. When that `Read` fails, use the plan text when it is already in this conversation; otherwise say in one line that the steps come from the diff alone and continue. Without `Plan:`, `<slug>` is `<YYYYMMDD-HHMMSS>` of now. Read the change set against `Base ref` (default `HEAD`): `git diff <base>` and the content of files `git ls-files --others --exclude-standard` lists. No readable plan and an empty change set → `status: "error"`, `reason: "nothing to demo"`. Run `mkdir -p .demo/<slug>`.

3. **Derive the steps.** From the plan's After, Scope and Test plan and from the diff:

   - **Features.** List the behaviors a person would check on screen, then group them into features. A feature is the set of actions a checker performs in a row for one purpose; it does not follow the count of tasks or commits. Group when the actions handle the same data for the same purpose, or when one action uses what an earlier one created or changed. Split when the purpose differs, when a part can be checked on its own, or when a different role performs it. When unsure, group. A single feature takes the same shape. Each feature gets a letter (`A` for the first, `B` for the second, and so on), a name stating what the user can do and a one- or two-sentence description.
   - **Normal cases.** Per feature, the flow that works. 3–10 steps across all features.
   - **Error cases**, when `error_cases` is `true`. One step per branch the diff implements (input validation, permissions, behavior that depends on state), each branch once. Errors the diff does not implement (raised by the framework or by shared code) are not walked. There is no cap; when the error steps exceed 10, the gate shows their count and a time estimate (10–20 seconds per step) in one line. The expected result is the error text itself. An error step uses records that later normal steps do not change; when they would, its data names a record of its own. An error step that needs a different session (signed out, another role) starts its action with that change (sign out, sign in as `<account>`) and names the account, taken from the fixtures or seed, in its data; it still counts as one step.
   - **Order and numbers.** Every normal step, feature by feature, then every error step, feature by feature. Numbers run through both.
   - **Sign-in.** Only when the diff changes sign-in (the code that creates or checks a session, the authentication settings, the account fields used to sign in, the sign-in page), sign-in becomes steps at the start of the first feature's normal cases. Otherwise it is not a step. When the pages need a signed-in user and `auth_state` is unset, write `<signin>`: the sign-in page's path, the account from the fixtures or seed, and the inputs and clicks; the data check performs it. `<signin>` appears in the step table and the data check only, never in `steps.json` or the page.
   - **Each step** holds `n`, `feature` (the 1-based position of its feature), `kind` (`normal` or `error`), the page path, the action (one imperative sentence), the expected result (one sentence), and the data it needs — covered by the project's fixtures or seed, created on screen by an earlier step, or inserted by a script written here, in that order of preference. A script's full text goes into the step table so the gate shows it. A step that creates a record on screen (a sign-up, a new item) fills its unique fields with values carrying `<YYYYMMDD-HHMMSS>` of now (for example an email address), so a second capture does not collide with the first. Nothing is cleaned up afterwards.

4. **Start the app.** `<port>` is the `port` key resolved as § Settings says (a command's first stdout line must be an integer from 1 to 65535; a non-zero exit or any other line goes to the start-failure gate below, which then shows the command's output) or, when unset, the output of
   `node -e 'const s=require("net").createServer();s.listen(0,()=>{console.log(s.address().port);s.close()})'`.
   Say in one line which `reset_command` and `start_command` are about to run. When `reset_command` is set, run `DEMO_PORT=<port> <reset_command>` in the foreground; a non-zero exit goes to the start-failure gate below, which then shows the reset output instead of `server.log`. Run `DEMO_PORT=<port> <start_command> > .demo/<slug>/server.log 2>&1` with `run_in_background: true`. Resolve `<url>`: the `url` key (as § Settings says), else the first `http://` or `https://` URL in `server.log`, else `http://localhost:<port>`. Wait for it with
   `node -e 'const u=process.argv[1],t=Date.now()+Number(process.argv[2])*1000;(async()=>{for(;;){try{await fetch(u);console.log("ready");process.exit(0)}catch{}if(Date.now()>t){console.log("timeout");process.exit(1)}await new Promise(r=>setTimeout(r,2000))}})()' "<url>" <ready_timeout>`
   passing `timeout: (ready_timeout + 10) * 1000` on that Bash call. Any HTTP response counts as ready. On `timeout`, the **start-failure gate** (USER GATE): show the last 20 lines of `server.log` and `<port>`, and ask `retry` / `skip`. `retry` runs step 7 (Stop the app), then this step again from `reset_command`; there is no retry limit. `skip` runs step 7 and stops with `status: "skipped"`, `reason: "dev server not ready"`.

   **Data check.** Once the URL answers, open each distinct step path once in a separate browser: `playwright-cli -s=demo-<slug>-check open`, `state-load <auth_state>` when set; when `<signin>` is set, sign in with `goto`, `snapshot`, `fill` and `click` as it says, then `state-save .demo/<slug>/auth.json` (a sign-in that fails is noted on every step for the gate); then per path `goto` and `snapshot` (read its output inline, or from the `.playwright-cli/` file it names), then `close`. A page that shows an error, a not-found, or an empty list where its step needs records is a data gap; so is a record the steps rely on that a persistent store the project itself keeps (seed data, an exported dataset) does not hold. For each gap, write an insertion script into the earliest step that needs the data, as in step 3. A page that fails for a reason data cannot explain is noted on its step for the gate.

5. **Step-table gate** (USER GATE). Show `<url>`, whether `reset_command` ran, the features (letter, name, description), the step table (number, feature, kind, path, action, expected result, data), `<signin>`, the error-step count line when there is one, the `video` value, every data script in full, and what the data check changed or noted, in the resolved language. Say in one sentence that `revise` can drop error steps and that `error_cases: false` leaves them out altogether. Ask `approve` / `revise` / `skip`, and in the same question set ask whether a step that fails for missing data may get an added insertion script and the whole flow be captured once more (`yes` / `no`); keep that answer as `<recapture>`. `revise` takes the user's corrections to the URL, the steps, the data or a script, applies them and shows the table again; when it changes `<signin>`, first open the data check's browser again, repeat its sign-in and `state-save`, and close it. `skip` runs step 7 and stops with `status: "skipped"`, `reason: "declined at step table"`. After `approve` nothing else asks the user a question.

6. **Capture.** `<session>` = `demo-<slug>`. Run `playwright-cli -s=<session> open`, then `playwright-cli -s=<session> state-load <file>` with `auth_state` when it is set, else `.demo/<slug>/auth.json` when it exists, then `playwright-cli -s=<session> goto <url>`. When `<chapters>` is `true`: `playwright-cli -s=<session> video-start .demo/<slug>/demo.webm --cursor`, then `playwright-cli -s=<session> video-show-actions`; otherwise only `playwright-cli -s=<session> video-start` (that version takes no path). Chain `&& playwright-cli -s=<session> eval "() => Date.now()"` onto the last of these recording commands and keep the number under that `eval`'s `### Result` line as `<t0>`. `<video stop>` is the stop command used below: `video-stop`, or `video-stop --filename .demo/<slug>/demo.webm` when `<chapters>` is `false`. Dispatch one `Agent` (`subagent_type: general-purpose`, `model` per § Model, `run_in_background: false`). The prompt is three fenced sections: `--- TASK ---` holds the text of `references/capture-prompt.md` § Capture prompt after its `---` rule, verbatim, with `{{session}}`, `{{out_dir}}` (`.demo/<slug>`), `{{url}}`, `{{chapters}}`, `{{t0}}`, `{{video}}`, `{{video_stop}}` (`<video stop>`) and `{{language}}` filled in; `--- STEPS ---` holds the approved table as one JSON object `{ "features": [ { "name", "description" } ], "steps": [ { "n", "feature", "kind", "path", "action", "expected", "data", "script" } ] }`; `--- RETURN ---` holds one sentence: the reply ends with a single fenced JSON block and nothing after it.

   **Pre-invocation reminder**: the agent's reply is a return value, not a turn boundary. The next tool call after it returns is `playwright-cli -s=<session> <video stop>`, issued by this same thread. See § No-Stall Principle.

   When the agent returns: run `playwright-cli -s=<session> <video stop>`, also when `video` is `normal` and the agent has already stopped it (that second stop's output is ignored), and `playwright-cli -s=<session> close`. Take the last fenced JSON block of the reply and parse it. No block, or a block that does not parse → run this step once more from `open`, on whatever state the first attempt left in the app, with the sentence `Your previous reply carried no parseable JSON block.` appended to `--- RETURN ---`; a second failure runs step 7 and stops with `status: "error"`, `reason: "no parseable capture result"`. Schema check, before anything is written: `steps` is an array whose `n` values are exactly those of the approved steps; each entry has a `status` of `ok` or `failed`, a non-empty string `screenshot` (a bare `step-NN.png` file name; a path is reduced to its base name), a non-empty string `result`, an optional string `note`, an optional `at` that is a non-negative integer or `null`, and, on a `failed` entry, an optional `cause` of `data` or `app`. `features`, when present, is an array whose entries hold `feature` (an integer from 1 to the feature count) and `at` / `error_at` (each a non-negative integer or `null`); a missing `features` or `at` is not a violation, it only leaves those chapter links out. A violation runs step 7 and stops with `status: "error"`, `reason: "capture schema violation"`.

   **Re-capture.** `<capture round>` is `1` on the first entry to this step. When `<recapture>` is `yes`, `<capture round>` is `1`, and at least one entry is `failed` with `cause: "data"`: read those steps' `note` and the last 40 lines of `server.log`, write an insertion script for each into its step's `script` (appended to any script it already has), set `<capture round>` to `2`, and run this step again from `open`, with the app still running and no `reset_command`. The second capture's result is final whatever it holds. Otherwise go on to step 7.

   **Return-point no-stall reminder**: regardless of outcome — every step `ok`, some `failed`, any non-error result — the next action, `playwright-cli -s=<session> <video stop>`, is issued in the next tool call; the re-capture decision comes after `close`. See § No-Stall Principle.

7. **Stop the app.** `<stop port>` is the port named in `<url>` when its host is `localhost`, `127.0.0.1` or `::1`, else `<port>`. Read the PIDs from `lsof -ti tcp:<stop port>`; when there are none, skip the kill. Otherwise run `kill <pids>`. Wait with `node -e "setTimeout(()=>{},2000)"`, read `lsof -ti tcp:<stop port>` again and `kill -9` what is left. If a PID still listens after that, keep one line for the report.

8. **Render and publish.** `Write` `.demo/<slug>/steps.json`: `title` (the change in two to four words), `dek` (the plan's After sentence, or one sentence from the diff), `url`, `features` (each approved feature's `name` and `description`, with the `at` and `error_at` of the agent's entry whose `feature` is its position), `steps` (each approved step with its `feature` and `kind`, merged with the agent's `status`, `result`, `note`, `at` and `screenshot`), and `video: "demo.webm"` when `.demo/<slug>/demo.webm` exists and is 15MB or smaller (checked, with its size, through `node -e` and `fs.statSync`). Run
   `node "<base dir>/scripts/render.mjs" --steps .demo/<slug>/steps.json --out .demo/<slug>/index.html --lang <language>`.
   A non-zero exit stops with `status: "error"`, `reason: "page rejected: <first stderr line>"` (the app is already stopped). Call `Artifact` with `file_path` `.demo/<slug>/index.html`, `files` mapping each `step-NN.png` to `.demo/<slug>/step-NN.png` and `demo.webm` to `.demo/<slug>/demo.webm` when `steps.json` has `video`, `icon` `camera`, and `description` one sentence naming the feature. Do not load the design skills: the page's layout and theming are fixed in the renderer. A missing or failing `Artifact` leaves `url` null; the page path still reports. Run `git check-ignore .demo .playwright-cli`; when its output lacks either path, keep one line for the report asking to add `.demo/` and `.playwright-cli/` to `.gitignore` (this skill does not edit it outside Setup mode).

9. **Report.** In the resolved language: the artifact URL (or the page path), the step count and the failed count, one line per feature with its normal and error step counts and its confirmed / not confirmed counts, whether the recording exists, a line saying the recording holds no error cases when `video` is `normal`, a line saying the recording is over 15MB and left off the page when it is, the stop result, and the gitignore line when there is one. When a re-capture ran, say so and show every script it added in full; list steps still `failed` with their `cause`. Then the return contract's JSON block.

## Return contract

Emit a single fenced JSON block at the end of the response, matching:

```json
{ "status": "ok" | "skipped" | "error", "reason": null | "<why>", "url": null | "<artifact url>", "page": null | "<path to index.html>", "video": null | "<path to demo.webm>", "steps": <n>, "failed": <n> }
```

`steps` and `failed` are `0` when the capture did not run. Only one fenced JSON block appears in the response.

## Sub-skill caller directive

When invoked as a sub-skill (i.e. via `Skill(demo)` from an orchestrator), the fenced JSON verdict block this skill emits is the **structured return value** of the skill's procedure — it is **not** a deliverable to the user, and emitting it does **not** terminate the orchestrator's turn. The same agent that ran this skill must immediately issue the next tool call dictated by the orchestrator's flow. Do not insert a prose summary, an acknowledgment, or a "shall I proceed?" sentence between the JSON verdict and the next tool call. Only one fenced JSON block — the verdict block — appears in the response, so callers can locate it unambiguously. The skill's own procedure is over; the orchestrator's procedure continues without pause.

## Fallback

When the `Agent` tool is not on the tool surface, this thread runs the flow of `references/capture-prompt.md` itself, between the same `video-start` and `video-stop` calls of step 6, builds the same `steps` and `features` arrays, and continues at the schema check.
