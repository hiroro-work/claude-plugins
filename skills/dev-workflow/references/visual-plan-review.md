# Visual Plan-Review Gate (Step 4)

Deep reference for Step 4's **visual gate**, the plan-approval surface. Read and follow this top to bottom once the caller's browser-reachability probe has cleared.

The run never enters Plan Mode, so this gate freely performs the non-read-only operations below (writing the served file, launching `serve.mjs`). The canonical plan document is `.claude/plans/<slug>.md`, written by Step 4 sub-step 2 before this procedure runs (step 3 below names the `<slug>` source).

The gate is a browser-based, structured plan review. It returns one of three outcomes to whoever entered it: **`approve`**, **`rewrite-approach`**, or **`fallback`** (defined in § Decision mapping and § Fallback contract below). What each outcome then leads to is the caller's own, and **no exit branches on which caller it was** — the verdict is the whole return. The *circumstance* of an entry is a different thing and is legitimately known here: step 3's compose and step 4's launch both read whether this entry follows edits made outside this gate, and whether a previous launch of this run has settled.

## serve.mjs contract

The viewer (`scripts/plan-review/serve.mjs`) ships with this skill; this gate only invokes it. Its contract:

- **Invocation**: `node <serve.mjs> --plan <path> [--prev <path>] --lang <resolved-language> [--timeout <seconds>] [--port <n>] [--no-open] --wait` — serves the Markdown plan at `<path>` on a random `127.0.0.1` port, opens the local default browser, and blocks until the user submits. `--lang` is the workflow's resolved `language` (`ja` / `en`); it controls **only** the language of browser-generated text — the "switch to alternative" comment body, the diff banner, the keyboard-shortcut hint, the note saying what requesting changes does, the conversation-thread labels, and the message shown while the page waits for the re-launch — and defaults to `en` when omitted. `--prev <path>` is the plan version the user reviewed on the previous launch (the `.plan-review.prev.md` snapshot — see § Prev snapshot); when supplied and readable, the browser highlights what changed since then. Omit it on the first launch; an unreadable `--prev` is non-fatal (the viewer renders without a diff). `--timeout <seconds>` caps the wait; omit it for serve.mjs's default (24h) and pass `--timeout 0` to disable the timer entirely (wait indefinitely). `--port <n>` asks for a specific port instead of a random one, and `--no-open` suppresses the browser launch — § Procedure step 4's launch sub-step pairs them on a re-launch so the tab already open reaches the new process. A busy `--port` is not a startup failure: serve.mjs retries it once after a second, then takes a random port and opens a browser regardless of `--no-open`, since the open tab points at the port it could not take.
- **`GET /api/plan`**: returns `{ "id": "<planId>", "markdown": "<raw plan markdown>", "lang": "<ja|en>", "prevMarkdown": "<raw markdown | null>", "thread": [ <round>, … ], "instance": "<per-process token>" }`. `thread` is the conversation thread's rounds (§ Conversation thread), and `instance` a token identifying this process, which the browser polls at `GET /api/instance` to notice a re-launch. The browser splits the markdown into sections, classifies them (Overview / Decisions / Build order / Test plan / Risks / …), and renders the review surface; the server does **not** segment the plan or enumerate block ids. `prevMarkdown` is the `--prev` file's content (or `null` when `--prev` is absent / unreadable).
- **stdout (in `--wait` mode)**: the **only** bytes written to stdout are the final submit JSON on one line — `JSON.parse`-able whole. All progress / errors go to stderr.
- **Submit JSON shape**: `{ "plan": "<planId>", "decision": "approve" | "revise", "submitted_at": "<iso8601>", "comments": [ { "block": "<id>", "section": "<section slug>", "excerpt": "<text>", "kind": "prose" | "figure", "body": "<comment>" } ] }`. `section` is the slug of the section the block sits in, which the conversation thread pairs with `excerpt` as the entry's anchor. `kind` names which source the commented block came from — `figure` only where the browser anchored the comment on a `<figure>`, `prose` everywhere else, decision cards included. `comments` may be empty (an `approve` with no comments). `block` is a **browser-assigned semantic id**: `decision-<n>` for the n-th Decision card, or `<section-slug>::<n>` for the n-th commentable block (paragraph / list item / code block / …) within a section. `excerpt` is a short prefix of the commented block's text, for disambiguation.
- **Comments file**: serve.mjs also writes the same JSON to `<planId>.comments.json` next to the plan file, where `planId` is the plan file's basename with the trailing `.md` removed.
- **Thread file**: on a `revise` submit carrying at least one comment, serve.mjs appends that round to `<planId>.thread.json` before printing the submit JSON (§ Conversation thread). An `approve`, and a `revise` with no comments, append nothing. A write failure there is non-fatal — the comments file already holds the round verbatim.
- **URL file**: at listen time, before the browser launch is attempted, serve.mjs writes the viewer URL as a single line to `<planId>.url` next to the plan file (same `planId` derivation as the comments file). A failure to write it is non-fatal and the server stays up.
- **Exit codes**: `0` submit, `124` timeout (fires after the `--timeout` cap — default 24h; `--timeout 0` disables the timer so it never fires), `130` SIGINT / SIGTERM, `1` startup error (e.g. unreadable plan). A busy `--port` is **not** among them — see the **Invocation** bullet's port-fallback sentence.

## Prev snapshot

To let the viewer show what changed across a revise round, the **previous** served-file content is preserved as `.claude/plans/<slug>.plan-review.prev.md` and passed to the next launch via `--prev`. Discipline: **whenever you are about to write the served file (`.plan-review.md`) and it already exists, first `cp` it to `.plan-review.prev.md`.** There is exactly **one** such site: the **Compose the served plan file** step, immediately before the `Write`, when the served file already exists — i.e. any non-first launch, whether reached by a localized `revise` re-launch, a `rewrite-approach` re-entry, or a caller re-entering after editing the canonical document itself.

On the **first** launch the served file does not yet exist, so no prev is created and the launch omits `--prev`. `.plan-review.prev.md` is a workflow artifact covered by `SKILL.md` § Workflow artifacts (cross-step fixed exclusion) and removed in [`finish-phase.md`](finish-phase.md) § Completion's cleanup.

## Conversation thread

The round-by-round record of what the user commented and what this gate replied, at `.claude/plans/<slug>.plan-review.thread.json`. The browser replays each entry under the block it was anchored on, and replays every entry again in a log panel at the end of the plan.

**Shape**: `{ "plan": "<planId>", "rounds": [ { "round": <int>, "submitted_at": "<iso8601>", "entries": [ … ] } ] }`. Each entry is `{ "id": "r<round>-c<n>", "block": "<id>", "anchor": { "section": "<slug>", "excerpt": "<text>" }, "kind": "prose" | "figure", "body": "<the user's comment>", "reply": <string | null>, "disposition": <"answered" | "revised" | "both" | null> }`.

**Who writes which field.** serve.mjs writes the round and every field but `reply` / `disposition`, which it leaves `null`. This gate fills those two, and maintains `anchor`, in § Procedure step 6's **Decision mapping**.

**`id` and `anchor` do different jobs.** `id` is immutable and is the entry's identity — what makes one round's entries distinguishable and lets a block's exchange be followed across rounds. `anchor` decides only where the entry is drawn, and is expected to change: the browser resolves it by text, so an edit to the anchored block invalidates it unless this gate updates it. `block` is kept as the id the browser originally assigned; the browser reads it only to recover the **section** when `anchor.section` is absent, never to find the block by its number — for the reason § Procedure step 6's **Block-id resolution** gives.

**Sweeping the anchors** is § Procedure step 6's **Decision mapping** duty on a revise round, and it is owed on one further occasion: a caller re-entering this procedure after applying edits to the canonical document outside this gate re-derives them before composing, for the same reason the figures re-check is owed there (§ Figures layer's **Who writes it, and when**). Without it, every earlier entry whose block those edits touched silently drops to the log panel.

**When the anchor does not resolve**, the entry is drawn in the log panel alone and marked there as not anchored.

`.plan-review.thread.json` is a workflow artifact covered by `SKILL.md` § Workflow artifacts (cross-step fixed exclusion) and removed in [`finish-phase.md`](finish-phase.md) § Completion's cleanup.

## Figures layer

Figures live outside the canonical plan document, in `.claude/plans/<slug>.figures.md`, so the plan's prose stays figure-free everywhere that document is read — Step 5's implementation walk, the Step 3 reviewer's payload, and the chat approval this gate degrades to. Only the served file carries them.

**File format.** A sequence of blocks. Each opens with a `## <section name>` heading naming the plan section it belongs to, spelled exactly as that section's heading in the canonical document, and holds that section's single figure with its caption. Which sections may be targeted is the calling skill's own closed list, in its plan-template file's § Figures. A heading naming a section the canonical document does not have is skipped with a one-line note. A repeated heading takes the same disposition — keep the first block, skip the rest, and say so in the same one-line note; never merge two blocks into one section.

**The one reserved heading — `## Hero`.** It names no plan section: it holds the whole-change picture the page opens on, above the plan. The viewer gives it a slot of its own across both columns, matched on that heading by name, and leaves the slot out of the layout entirely when the file carries no such block. It is therefore matched **before** the section-name rule above, so `Hero` is never taken for a missing section and skipped. Whether a plan is expected to carry one is the calling skill's own choice, stated in its plan-template file's § Figures alongside the section list. The hero is commentable like any other figure, so a revise comment can land on it. Its `block` id names the section **`_hero`** — a leading underscore no section slug can produce, so a plan section cannot collide with the slot — and **every** comment anchored there applies to the figures file's `## Hero` block, whatever its `kind`: the whole block lives in that file, so the canonical plan document holds none of the text a comment there could name. A second `## Hero` block takes the repeated-heading disposition above: the first is kept, the rest skipped.

**Insertion position**, one per section, keyed on what the section holds rather than on its name: a **field-bullet** section (the plan's overview) — directly after the bullets, before the next element; a **decision-item** section — after any leading prose, before the first `**Question**` line; the **Build order** — before the numbered list; any other **prose** section — after its last sentence, before the next heading. The `## Hero` block goes **at the top of the plan body, before the plan's first section heading** — the region the viewer reads as the preamble, which is where it finds the figure to lift into the slot. It goes **below** any YAML frontmatter the plan document carries, never above it: the renderer's strip is anchored to the start of the file, so a hero block pushed in front of the frontmatter would leave it to render as the page's opening paragraph. When the canonical document opens with a YAML frontmatter block ([`plan-format.md`](plan-format.md) § Step 4 presentation order's plan-document bullet), that block stays the first thing in the served file and the hero goes directly beneath it: the viewer only drops frontmatter that begins the file, so a hero above it would render the bookkeeping as page text.

**Who writes it, and when.** Whoever runs this gate writes it, immediately before the first compose — never at Step 2 (Create Plan), since a plan that never reaches a browser never needs figures. Later launches reuse the file as it stands, with three triggers that override that: a revise comment on a figure rewrites it (§ Procedure step 6's **Decision mapping**); a `rewrite-approach` re-entry — where the plan's approach has changed under it — re-authors or deletes it; and a re-entry that follows edits applied to the canonical document **outside** this gate re-checks it ([`plan-artifact.md`](plan-artifact.md) § Team-review gate step 3). The same re-check is owed whenever a prose comment changed a label or a count a figure carries: the headings keep matching either way, so a stale figure ships silently unless the trigger fires. The authoring conventions — which notation, how many figures, the caption contract, the colour tokens, the SVG skeletons — are in [`plan-figures.md`](plan-figures.md); `Read` it at that point and not before.

`.figures.md` is a workflow artifact covered by `SKILL.md` § Workflow artifacts (cross-step fixed exclusion) and removed in [`finish-phase.md`](finish-phase.md) § Completion's cleanup.

## Procedure

1. **Resolve the serve.mjs path.** It lives at `<skill base directory>/scripts/plan-review/serve.mjs`, where `<skill base directory>` is the directory the harness reports as "Base directory for this skill" at this skill's invocation. **Do not hardcode an absolute path.**

2. **Re-confirm reachability.** Run `printenv CLAUDE_CODE_REMOTE`; `true` means the served page never reaches the user — return **`fallback`** to the caller without launching. Any other value — including unset or empty — means local execution; continue.

3. **Compose the served plan file.**

   **On the first compose of the run only** — the served file does not yet exist — write `.claude/plans/<slug>.figures.md`, one figure per targetable section. `Read` [`plan-figures.md`](plan-figures.md) at this point (§ Figures layer's **Who writes it, and when**) and follow it: it holds that default, the carve-outs that drop a section from it, and what each figure claims. A plan every one of whose sections falls to a carve-out writes no file.

   **On every later launch**, reuse the figures file as it stands — **except** where one of § Figures layer's **Who writes it, and when** triggers fires. Check those triggers here rather than assuming reuse. A later launch that follows edits made outside this gate also re-derives the conversation thread's anchors before composing (§ Conversation thread's **Sweeping the anchors** paragraph), for the same reason. Two absences read differently: a file absent because every section fell to a carve-out is the intended state and stays absent, while one absent unexpectedly — a served copy survives but the figures file is gone — is re-authored as a first compose would.

   Then compose the file itself. If `.claude/plans/<slug>.plan-review.md` **already exists** (any non-first launch), first `cp` it to `.claude/plans/<slug>.plan-review.prev.md` before overwriting (§ Prev snapshot). Then compose the served file from two inputs and `Write` it to `.claude/plans/<slug>.plan-review.md`, where `<slug>` is the slug Step 4 sub-step 2 established: the **canonical plan document** `.claude/plans/<slug>.md`, carried **verbatim** — no block markers are inserted — and the **figures file** `.claude/plans/<slug>.figures.md`, each of its blocks inserted at the position § Figures layer gives the section its heading names. When the figures file does not exist — every section having fallen to a carve-out — the served file is the canonical document verbatim and this step is a plain copy.

   This **served file** is the gate's derived copy, and the canonical `.claude/plans/<slug>.md` is **never written from it**. Prose a revise round changes is applied to the canonical document itself (§ Procedure step 6's **Decision mapping**), so that document is current at every moment of the loop.

4. **Launch the gate (background Bash).** **On a re-launch this run itself performed, read the previous port before deleting anything**: `Read` `.claude/plans/<slug>.plan-review.url` and take the port out of the URL it holds. The order matters — the deletion below is what removes the only record of it. **A `.url` left behind by an earlier, interrupted run is not a re-launch**: the tab it names is gone, so treat a run that has not launched the gate before as a first launch and ignore the file, whatever it holds. **Neither is an entry that follows a settled submit** — a caller re-entering this procedure after the previous launch returned a verdict ([`plan-artifact.md`](plan-artifact.md) § Team-review gate step 3 is the one such caller): that process exited on its submit, the tab has been sitting on a finished page since, and the wait in between is exactly as long as the team took. Treat it as a first launch too — **for the port and `--no-open` decision alone**; the `--prev` clause below keys on the snapshot file's own existence and still applies, so this entry does show the diff, which is the round where the user most needs it. Reusing a dead tab's port with `--no-open` shows the user nothing at all, and the gate then blocks on a submit that can never arrive. Then clear the stale URL file — `rm -f .claude/plans/<slug>.plan-review.url`, as its own foreground call so it stays inside the `Bash(rm -f .claude/plans/*)` grant. Then run `node "<skill base directory>/scripts/plan-review/serve.mjs" --plan ".claude/plans/<slug>.plan-review.md" --lang <resolved-language> --wait` as a **background Bash** command (`run_in_background: true`), substituting the workflow's resolved `language` for `<resolved-language>`, and emit a Progress Visibility status line in the same turn (e.g. "Launching the visual plan-review gate in your browser…"). **When a previous port was read**, append `--port <n> --no-open` so the tab the user still has open reaches this process and reloads itself rather than a second tab opening beside it. Omit both on the first launch, and omit both when the URL file could not be read. **When `.claude/plans/<slug>.plan-review.prev.md` exists** (a re-launch where a prev snapshot was taken — § Prev snapshot), append `--prev ".claude/plans/<slug>.plan-review.prev.md"` so the viewer shows the diff; omit it on the first launch. Do **not** pass `--timeout`: the gate uses serve.mjs's 24h default. Pass `--timeout 0` only if truly no timeout (wait indefinitely) is wanted. Notes:
   - This is background **Bash**, **not** the `Agent` tool.
   - Background dispatch is **required** here — a foreground Bash call (~10-min limit) could not survive the wait. The harness re-invokes the agent when the background process exits. Waiting for that exit is a **harness-tracked boundary**, not a "type continue" pause (see `SKILL.md` § No-Stall Principle) — proceed on the exit notification.

   **Surface the gate URL in chat** on the **first launch of the run, on any launch treated as a first launch by the rule above, and on any later launch whose port differs from the one passed as `--port`** (the busy-port fallback, or a launch that had no previous port to reuse) — a re-launch that kept its port is reaching a tab that is already open on that URL, and re-emitting it every round is noise. When it applies, do so in the turn right after the launch call returns: `Read` `.claude/plans/<slug>.plan-review.url` (§ serve.mjs contract's **URL file** bullet) and emit its single line in chat as a one-line message, so the user can open the gate by hand when the browser did not open on its own. The URL is copied verbatim; the surrounding sentence is written in the resolved `language`. Paired bilingual samples (runtime rendering demonstration) — `language: ja`: `ブラウザが開かない場合はこちらを開いてください: http://127.0.0.1:52341/`; `language: en`: `If your browser did not open, visit http://127.0.0.1:52341/`. If the `Read` fails, re-read up to **twice more** and then give up silently — a missing URL file is non-fatal. The extra attempts are for the busy-port path, whose one-second retry delays the write by exactly as long as the case that most needs the URL. Do not delay the read with a `sleep`. This read-and-emit is the required tool-carrying turn after the background dispatch, not the content-free waiting turn `SKILL.md` § No-Stall Principle forbids. A re-launch loops back to this step and reuses the port, so the read still happens — to compare against `--port` — and only a differing port is emitted.

5. **Read the decision.** When the background process exits, read its captured stdout. In `--wait` mode the only stdout content is the submit JSON (one line) — parse it. **When the JSON is there, decide on it.** When it is absent, re-read the capture until the host's termination marker appears (Claude Code appends `[exited with code N]` as the capture's last line), for up to 5 further reads. Each read is a fresh tool call and that round-trip is the only spacing — do not insert a `sleep`, which this skill does not grant. **Both a marker with no parseable JSON and 5 reads without a marker are step 6's "no parseable result obtained" row.** `Keep in sync with crit-commit-review.md § Procedure step 4's background-capture re-read guard.` The decision comes from this stdout; the on-disk comments file (`.claude/plans/<slug>.plan-review.comments.json`, per § serve.mjs contract's derivation) is a durable side record that is **not** read here. The served file, the comments file, the URL file (`.plan-review.url`), the conversation thread (`.plan-review.thread.json`), and the prev snapshot (`.plan-review.prev.md`) are workflow artifacts covered by `SKILL.md` § Workflow artifacts (cross-step fixed exclusion) — excluded from Step 10 commits automatically (no `.gitignore` entry needed).

6. **Decision mapping.** Evaluate the parsed result in order (first match wins):
   - **Non-zero exit** (`124` timeout — fires only after the cap elapses (default 24h), never with `--timeout 0`; `130` SIGINT / SIGTERM; `1` startup error) — or no parseable result obtained — → return **`fallback`** to the caller.
   - **`decision: "approve"`** → the plan is approved. Any accompanying `comments` are **advisory only** — record them but do not block on them (the user chose approve). Write no reply and nothing to the conversation thread for them (§ serve.mjs contract's **Thread file** bullet). Return **`approve`** to whoever entered this procedure, with no write of any kind — the canonical `.claude/plans/<slug>.md` is already the approved plan — the browser submit being itself the final confirmation. Where the verdict then goes is the caller's alone; this procedure carries no record of who launched it and must not branch on one.
   - **`decision: "revise"`** → apply the block comments **to the source the commented block came from**, never to the served file (which the next launch's compose rebuilds): a comment on plan prose lands in the canonical plan document `.claude/plans/<slug>.md` — keeping any YAML frontmatter that document carries ([`plan-format.md`](plan-format.md) § Step 4 presentation order's plan-document bullet) — and a comment on a figure lands in the figures file `.claude/plans/<slug>.figures.md`. Route each comment by its `kind` field (§ serve.mjs contract's **Submit JSON shape**): `figure` to the figures file, `prose` to the canonical document. **One override, ahead of `kind`**: a comment whose `block` names the section `_hero` goes to the figures file's `## Hero` block whatever its `kind` — that block lives in the figures file in its entirety, so the canonical document holds none of the text such a comment could name (§ Figures layer's **The one reserved heading — `## Hero`** paragraph). Never infer the side from the excerpt text — a caption that quotes prose would route wrong. A `figure` comment whose body also asks for a prose change is applied to both, in that order.

     **Triage each comment before applying anything.** Take the comments one at a time and decide, per comment, whether it is a **question** or a **change request**. The test is whether **what to change, and to what, is determined by the comment's own wording**. When it is, apply the change. When it is not — the comment asks what something means, what a choice costs, or why an approach was taken — answer it and leave the plan alone. A comment that does both gets both. When the reading is genuinely open, do not guess at an edit: answer, and say in the same reply what you would change if that is what was wanted. The reply is written in the resolved `language`.

     For each comment that is a change request, map its `block` id to the corresponding part of the plan and apply the requested change autonomously (same discipline as Step 3 finding application — the user's block comments are the review):
     - **Block-id resolution**: `decision-<n>` → the n-th Decision item; `<section-slug>::<n>` → the n-th commentable block within that section. **Resolve by the `excerpt` first**: it is a whitespace-normalized, ≤40-char prefix of the commented block's text, so locate the block whose leading text matches it after the same normalization (collapse runs of whitespace, then compare the prefix) rather than requiring an exact substring match. Treat the numeric index (`<n>`) as a secondary, advisory hint only — never rely on the index alone. Block ids are assigned on the served file and resolved against the canonical document, so in any section carrying a figure every index after the insertion point is off by one — systematically, not incidentally, which is why the excerpt leads. A `kind: "figure"` comment is the exception: resolve it by the section its `block` id names, since a section holds one figure and a figure's `excerpt` is unusable either way — an inline SVG's is its label text run together, a mermaid figure's is mermaid's own injected CSS.
     - **"Switch to alternative" comments**: a Decision card's toggle emits a comment on `decision-<n>` whose `body` is the fixed switch instruction (`この Decision を Alternative に切り替える` for `lang: ja` / `Switch this decision to its Alternative` for `lang: en`, optionally followed by free-text). Treat it as a **bounded Recommendation/Alternative swap** on that Decision: swap the item's Recommendation and Alternative in the canonical plan document and propagate the dependent updates (Approach / Risks / Scope / Test-plan sweep) exactly as the text-path swap-decisions bucket does (see `SKILL.md` Step 4's swap-decisions handling). When the `body` carries free-text beyond the fixed switch sentence (the portion after that sentence), apply **both legs**: perform the swap first, then apply that trailing portion as an ordinary revise instruction on the same Decision — the swap is not a license to drop the rest of the comment. Omit the text-path read-back sub-step here.

     **Then record the round, for every comment — answered, revised, or both.**
     - **Write back to the conversation thread** (§ Conversation thread), once per comment, in a **single** update of that entry: set `reply` to the answer, `disposition` to `answered` / `revised` / `both` for what the triage above actually did, and — when this round edited the anchored block — `anchor.excerpt` to the block's new leading text **in the form serve.mjs writes**: whitespace collapsed to single spaces, truncated to 40 characters. Writing the block whole instead leaves trailing markup the browser's normalization does not strip, and the entry stops matching. Leave `id` and `block` alone.
     - **Sweep the anchors once, immediately before the next compose**: walk every entry in the log, current rounds and earlier ones alike, and re-derive `anchor.excerpt` for any whose text no longer appears in the canonical document **and whose block this round can still identify**. Leave the rest — an entry whose block is gone belongs in the log panel, which is where an unresolved anchor already sends it.

     This comment-application happens for **every** `revise` submit, before and regardless of the branch below. Then branch on the nature of the (already-applied) changes:
     - **Zero applied changes**: either the `comments` array was empty, or the triage answered every comment and edited nothing. **Re-launch the gate** (loop back to step 3, **Compose the served plan file**, so the next launch serves the current canonical document); its compose takes the prev snapshot on the way (§ Prev snapshot), so the re-launch still passes `--prev`. An answered-only round re-launches for the replies themselves — the page is where they are read.
     - **Approach-level material change** (a new overall approach, a scope change — same vocabulary as Step 4's `rewrite-approach` bucket: "Approach / Build order / Scope-level material change"): do **not** loop the gate. Return **`rewrite-approach`** to the caller, whose own `rewrite-approach` handling takes it from there — the canonical plan document already carries the applied comments, so whatever re-review that handling runs sees the current plan. (On a re-entry the reachability probe re-runs; if the browser is still reachable, the gate re-runs on the revised plan.)
     - **Localized edits** (wording, a single Decision tweak, a bounded Recommendation/Alternative swap, a bounded section edit): **re-launch the gate** (loop back to step 3, **Compose the served plan file**) — the edits already landed in the canonical document, and the compose rebuilds the served file from it. Step 3 (Plan Review) is not re-run for localized revise. The loop is human-paced — each iteration blocks on a fresh browser submit, so no machine iteration cap applies. A closed browser does **not** by itself end the gate (the server keeps waiting); the gate exits via `fallback` only on the timeout cap (default 24h, never with `--timeout 0`), a SIGINT / SIGTERM, or a startup error (the non-zero-exit row above).

7. **Fallback contract.** Return **`fallback`** to the caller on any of: local browser unreachable (`CLAUDE_CODE_REMOTE="true"`, step 2), non-zero serve.mjs exit, a startup / launch failure, or the launch Bash call being blocked / yielding no result. What the caller does with it is the caller's own — do not run its recovery from inside this procedure.

   **The served copy's disposition belongs here, not to the caller**, because only this procedure knows whether its compose ran. Step 2's probe returns before step 3, so the served file still holds whatever the previous entry left — on that exit, and only that one, delete `.claude/plans/<slug>.plan-review.md` (`rm -f`, its own foreground call). Every later exit is past the compose, so the served file was just rebuilt from the current canonical document and the figures layer: leave it, and the next publish carries the figures. A caller must not delete it on its own — it cannot tell the two exits apart.
