**Plan-body prose polish** (`Keep in sync with dev-workflow references/step4-finalize-plan.md's Plan-body prose polish paragraph.`). When `polish_prose` is `true`, call `Skill(prose-polish)` in file mode before the approval surface below: `Files:` = `.claude/plans/<slug>.md` (written at M3 sub-step 3's plan authoring), plus `state_file_path` on the run whose M2 (Kickoff) wrote it — including the `../dev-workflow/references/task-decomposition-resume.md` § A step 3a recovery, which starts from `--resume` but continues in Normal sub-mode and re-binds the path once a decomposition is accepted — it stays `null` otherwise, and `Files:` then carries the plan document alone; `Language:` = the resolved language; no `Model:`. Run it **before** sub-step 1 enters the visual gate, which copies its served file from the plan document; polishing after that copy leaves the junior reading the un-polished text. The state file joins the plan document because its subtask prose is written for the junior to read as well and no other step polishes it. Restricting it to the creating run leaves two things un-polished — a subtask M13's deferral/exclusion gate promotes afterwards, and any later edit to the file.

An `error` verdict means prose-polish ran — note it in one line, present the un-polished plan, and append nothing. A `Skill()` call failure is the distinct availability signal: retry once, then skip and append `prose-polish unavailable (plan-body polish)` to `bundle_skills_unavailable`. Both targets are § Workflow artifacts, which M7's changed-file scope excludes, so the two call sites never overlap.

3. Classify the outcome into three buckets: **accept** (→ implementation) / **adjust** (revise the plan → re-open M4 → re-review → re-enter M5) / **withdraw** (end the workflow). These buckets are the source of truth for [`learning-gates.md`](learning-gates.md) § E's **change** bucket, which is **adjust** one phase earlier — sweep it whenever they change. **Disabled-plan-phase exception on the adjust bucket**: when the plan phase is configured off, skip the re-open-M4 and re-review legs entirely — run sub-step 4's read-back where that path calls for it, apply the revision, and re-enter M5 directly. The user turned the phase off, so an adjust must not re-enable it; re-opening the `M4` row here would also strand it, since M4's entry condition skips the step (this mirrors `dev-workflow` Step 4's own rewrite-approach exception, which the same setting drives). A browser gate's return maps directly — `approve` → **accept**, `rewrite-approach` → **adjust** (the gate has already written its revisions to `.claude/plans/<slug>.md`, so resume adjust at the re-open-M4 leg rather than revising the plan again — or, when the disabled-plan-phase exception above applies, at re-entering M5, since that leg is skipped); `fallback` is a route rather than an outcome (continue with sub-step 1's **chat** bullet). On the chat path classify the reply semantically; interrogative / non-committal replies re-classify via a confirming question.
