# Project Rules - Local (Conversation-Extracted)

このファイルは `--from-conversation` で抽出された project-specific patterns を保持する `.local.md` です。`project.rules.md` の Principles と分離して、organizational rule sharing 時に portable な Principles のみを promote できるよう運用しています。

各項目には規範・発動条件・判断軸だけを置き、実例は書かない。

## Project-specific patterns

- **`jq` の `null` 文字列フォールバック**: `jq` は entry / key 不在時に literal `null\n` を **zero exit** で出すため `|| echo unknown` は発火しない。filter 内 `// "unknown"` + post-pipeline `[ -z "$value" ] && value="unknown"` の 2 段構えにする。producer / consumer の両側に適用する
- **SKILL.md の手続きが起動するコマンドはパイプの各バイナリまで `allowed-tools` に載せる。載せたくないならパイプ自体を落とす**: `git ... | grep` / `| wc -l` / `| awk` のように出力を外部バイナリへ流すと、そのバイナリが grant されていない環境で permission dialog に当たって停止する。canonical fix は **grant を広げるのでなく依存自体を除去**する — 行数カウントや pattern 抽出はコマンド出力をそのまま読んで agent 側で判定し、pipe を落とす。判断軸は「この集計・走査は外部バイナリ無しで agent 内でできるか」。ガードが呼ぶ git サブコマンド自体（`git switch` / `git remote show` / `git symbolic-ref` / `git merge-base` 等）は除去できないので `allowed-tools` に宣言する
- **detached HEAD ガード**: branch 操作を伴う routine では Pre-flight に `git symbolic-ref -q HEAD >/dev/null` の non-zero exit で detached HEAD を検出し early abort。`git rev-parse --abbrev-ref HEAD` は detached HEAD で literal `HEAD` を返すため単独では使えない
- **disposition enum 拡張ではなく既存 enum の厳格化**: 新 case 追加時は新 disposition value を発明せず、**既存 criteria の厳格化**（複数条件の AND test への具体化等）を優先する。enum 増加は downstream parser / mapping table の全 update と後方互換性の崩壊を招く
- **Branch behavior は completion で specify する（negation 禁止）**: 「branch A と同じだが X を除く」型の negation は hidden gap を作る。canonical 2 階層: (i) **Full <set-name> (applies to both <A> and <B>)** の shared block、(ii) branch-specific actions で差分のみ。error class の shared updates も by-completion の explicit list。1 箇所で negation を見つけたら同 SKILL.md 内の全分岐を sweep する
- **Pre-implementation smoke test (Step 0) for undocumented platform capabilities**: 前例のない platform capability（`Skill()` を subagent から呼び出す / `subagent_type` の tool set / allowed-tools 継承等）に依存する architectural rewrite は、Step 5 前に Step 0 smoke test phase を Test plan に組み込む。必須項目: (i) feasibility PASS/FAIL、(ii) tool inheritance、(iii) state-management simulation、(iv) audit-trail (READY/NEEDS-FALLBACK/BLOCKED)。wording は「必須 (Step 0 item #N)」で統一する（「推奨」表記は不可）
- **Dispatch-layer health と callee-layer health の counter 分離**: subagent dispatch 経由で callee skills を呼ぶ設計では (i) dispatch-layer error（dispatch 失敗 / verdict parse / schema violation / tool error）と (ii) callee-layer error（callee error verdict / max-iter）で counter を分ける。dispatch-layer error path は per-callee disable counter を increment も reset もしない（callee は走っていない）。aggregate は 2 layer を別行で render し observability axis の直交を保つ
- **Sequential N-callee orchestration を 1 Agent dispatch に集約する architectural pattern**: N 個の sequential `Skill()` で N 個の stall surface が積む場合、1 `Agent` dispatch に集約して aggregate JSON を返す。必須: (i) aggregate JSON schema が per-callee field を nest、(ii) dispatch-layer error class を callee-layer から分離、(iii) `subagent_type` を Step 0 smoke test で確認、(iv) subagent prompt に「Do not run further `Skill()` dispatches beyond what is enumerated」を入れて内部の stall surface も bound する
- **Routing-field entry shape validation extension** (class-level extension of `Edit` old_string validation rule): entry shape validation は `Edit` の `old_string` だけでなく **downstream tool call が dereference する全フィールド**に拡張する。parse 段階の schema-violation check で全 routing field を non-empty string 検査する
- **Bold-prose label cross-reference style** (specialization of stable heading reference rule): 参照先が `### Heading` でなく bold-prose label の場合、`§ <Heading>'s "<bold-prose label>" paragraph` 形式で bold 内文言を verbatim のまま引用符で囲む。bold label を書き換えるときは参照側も同期する
- **Coordinated multi-site sweep on extension/addition**: 新しい値・member・gate・rename token の追加は、coordinated site 全てを closed list で enumerate し 1 commit 内で sweep する。canonical 形は (i) trigger 明示、(ii) 同期 site 列挙（設定表や節見出しを写している自スキルの README も含める）、(iii) 1 commit atomicity、(iv) Edit 直後の同期 audit（pre-existing instance も sweep）、(v) reference 側に `Source of truth: ...; keep in sync` directive — 権威方向とメンバーシップ基準の両方を書き、基準は carve-out まで含める
- **bundle plugin に新メンバーを足す場合の closed list は 4 + 1 leg**: marketplace.json の 4 edit（新 skill plugin entry の append / bundle `skills` array への append / bundle `description` 追記 / bundle `version` の paired bump）に加え、新メンバー `SKILL.md` への横断ディレクティブ `## Dispatch authorization` 同梱。`Source of truth`: 4 edit は本項目、+1 leg は `project.rules.md` § プラグイン構造 の「**bundle 全メンバーに複製する横断ディレクティブは byte-identical を保ち、メンバー追加時に必ず同梱する**」bullet。両者を keep in sync
- **lexical grep で拾えない参照も sweep target に入れる**: rename では旧概念の同義語・派生形・隣接表現を grep で炙り出して Test plan の sweep target に明記する。挙動変更・削除の diff では類推参照（「〜と同じ挙動で動く」）を意味で sweep する — token が不変なので lexical grep は 0 hit になる
- **Plan rewrite triggered by user material change at Step 4 gate (+ swap / insertion specializations)**: Step 4 で user が Alternative 選択等を要求したら、Step 3 の再 review を経て、今回の実行が到達した承認面（visual ゲート、縮退していればチャット）へ再提示する。書き換えは 1 pass で行い、user 既選択を Decisions に記録し、依存する Approach / Scope / Risks / Test plan / CHANGELOG note を同じ pass で sweep する。**Swap-direction**（Decisions に既にある choice の Alternative 選択）は R / A を position swap して新 R に「user 既選択」annotation を付ける。**Insertion-direction**（Decisions に無い choice — 典型は default value）は swap でなく **新 Decision § (N+1) を insert** し、見出しに `**user 既選択: <value> — Step 4 gate にて**` annotation を付け、R = user 選択 / A = 元の暗黙 default とする。swap と insertion を混同すると元の structure が壊れる。partial rewrite は plan 肥大化と buried decisions を招く
- **Routine-side action ownership over environment-finalization delegation**: 非対話 routine が外部副作用（`git push` 等）を伴う場合、「session finalization に委譲」と宣言しない。canonical: routine 自身が once per run で実行し（単一箇所、cleanup 判定後 / summary 直前）、`allowed-tools` に glob を追加し、session-level rule との conflict 文脈と禁止条項を明記する
- **External-command failure: retry once + stderr-derived `<reason>` + no auto-recovery**: 外部 CLI（`git push` / `gh api` / `curl`）失敗の canonical pattern 3 点: (i) **retry 1 回のみ + 1–2 sec sleep**（指数バックオフは over-spec、deterministic failure は retry で改善しない）、(ii) **`<reason>` は stderr 最終 non-empty 行を ≤ 80 文字で truncate**、empty なら `(no stderr)`、(iii) **auto-recovery 明示禁止**（`Do not auto-recover (no force push, no rebase, no branch rename)` — 禁止文言なしだと LLM が rebase を hallucinate する）。retry の rationale 段落は Simplify で削除されるため prose に残さない
- **Agent definition (`.claude/agents/<name>.md`) の frontmatter `allowed-tools` 宣言**: 宣言なしだと nested dispatch (`Skill()` / `Agent` / `Bash(...)`) が silent fail する。canonical: callee `Skill(<name>)` を明示、callee の `allowed-tools` を union で列挙、`Bash(*)` は避ける
- **Agent 定義に `Skill(<callee>)` を許す場合は inline 再実行を禁止する節を置く**: agent の `allowed-tools` に `Skill(<callee>)` を含めると callee SKILL.md が subagent context に injected され、subagent が dispatch せず inline 再実行する。canonical mitigation: agent 定義に `## Dispatch discipline` 節を新設し 3 段落の reinforcement-by-repetition を置く — (i) MUST 宣言「Each callee MUST be invoked via `Skill(<name>)`. Do not read, interpret, or replicate any callee's SKILL.md logic inline」、(ii) concrete restatement、(iii) closed-list bound。callee 内部スキーマの field 名を agent prose に書かない
- **Routing-identifier permissive / content strict layering**: routing identifier fields（title format / regex）と judgment 用 content fields（enum / required fields）が併存する場合、**identifier permissive / content strict** に分離する。両 layer を strict にすると grammar 揺れ（`1 finding` vs `N findings`、trailer の有無）で silent skip の regression が出る。判断軸: 事前フィルタ済みなら format check は不要、保持するなら permissive form（`\d+ finding(s)?`）にし content strict は維持する
- **Vacuous-truth gap in per-element ALL-quantifier close predicates**: per-element の ALL-quantifier（`every Finding is OK to close`）は zero records で vacuously true になり、parse-error / dispatch-aborted の whole-state を silently 同じ分岐として扱ってしまう。canonical は 2-leg AND predicate: (i) whole-state gate（not parse-error, not aborted）AND (ii) per-element check
- **Step renumbering propagation in SKILL.md (mechanical sweep + individual overrides + 2-stage grep audit)**: 2 階層で設計する — (i) **Generic rule** で単純置換群を列挙、(ii) **Individual overrides** で、機械置換すると意味が誤りになる箇所（旧番号を前提にした相対表現、番号だけでは指示対象が曖昧になる参照）を line 別に列挙して個別の置換後文言を決める。line 番号は pre-edit の reference に留め、最終確認は phrase / heading anchor で行う。`references/*.md` への波及は line-by-line checklist にする。**最終 audit は 2 段階 grep**: (1) phrase-pair-only grep（旧 heading 句の OR）で 0 hit、(2) 変更した番号への word-boundary grep で残り hit を目視
- **TodoWrite single-row for unknown sub-iteration count at registration time**: sub-iteration の数が user-approval 依存で登録時点に確定しない Step は、per-iteration row に展開せず single row で登録する（未確定の M と mid-flight 書き換えは stall surface を増やす）。登録箇所に `(single row — per-X iteration is handled inline within Step N because the X count is not known until <ref>)` と annotation する。登録時点で確定している Step は per-iter 展開してよい — 両 pattern を混同しない
- **変更集合の収集は filename-robust な形で once 実行する**: canonical form は `git status --porcelain=v1 --untracked-files=all -z`（`=v1` で format pin、`-z` で NUL 区切りにして C-quoting を抑制）。procedure 冒頭で once 実行して in-memory で reuse する。`git diff <base>` は untracked を含まないため、tracked は `git diff`、untracked は `Read` で new-file hunk を作り、`??` prefix を discriminator にする
- **commit は pathspec で scope する**: staging は `git add -- "<f1>" "<f2>" ...` の multi-pathspec single call とし、`-A` / `git add .` は禁止（unrelated drift を staging する）。環境によっては Stop hook が untracked を auto-stage するため、commit も `git commit -m <msg> -- <path-1> ...` の形で scope する（`-m` は `--` より前）。staging 文書の除外は `.gitignore` でなく commit pathspec で行う（gitignore は team-shared plan を消す）
- **bookkeeping / release commit は closed set に厳密 scope する**: version bump + CHANGELOG の bookkeeping コミットの pathspec は `.claude-plugin/marketplace.json` と `CHANGELOG.md` のみに限定する。collect が拾う working tree には無関係な user 編集や workflow artifact が混在しうるので、collect 段で識別して全コミットから除外し、commit-plan に「除外: …」と明示する。混入時は `git commit --amend -- <正しい closed set のみ>` で直す
- **Counter lifecycle: zero-exit-only increment + amend exclusion**: counter は loop 開始で 0 init、zero exit 時のみ +1、retry / abort / failed path では increment しない、`--amend` / re-commit で再 increment しない。SKILL.md に「On zero exit, increment by 1」「The amend ... is NOT re-incremented」を symmetric に明示する
- **Downstream routing は config-flag でなく counter で行う**: `<counter> > 0` で routing する（config-flag intent だと `enabled: true` × skip 条件で 0 件になる case を取り違える）。`<counter> == 0` 側は「flag が false だった」「Step が skip された」の 2 cause の OR union として書く。boolean flag + counter の合成は、counter 単独で同等の semantics を表現できないか精査する
- **Token defined-once + cross-reference (re-render 禁止)**: 複数箇所から参照される token（localized / status / enum mapping）は 1 箇所で定義し、他箇所は cross-reference にする（re-render すると canonical 更新時に drift する。i18n token は wording 更新の頻度が高い）。cross-ref 構文は `Bold-prose label cross-reference style` の `§ <Heading>'s "<bold label>" paragraph` 形式。re-render の finding が出たら 1 source-of-truth に統合する
- **Temporary-workaround skill integration: single hook point over state-machine weave**: 暫定対処の project-local skill を既存 routine skill に組み込むときは、(i) outer state machine / record schema / counter / TodoWrite rows / No-Stall reminder enumeration に触れない、(ii) 既存 sub-step 境界に 1 段落だけ挿入する、(iii) deletion 手順を SKILL.md に明記する。Step 1 で「暫定 = 削除予定」と判明した時点で deep integration を early reject し、単一 hook point を Recommendation に立てる
- **Edit-induced false-positive: widen edit scope, not add detect-only check**: verification skill が持続的に fail するとき、root cause の多くは **upstream edit operation の scope incomplete**。fix 方向は (i) ❌ verification 側を fail-open にする、(ii) ❌ detect-only を足して conflict を cascade させる、(iii) ✅ **edit 側の scope を広げる**（canonical edit の直後に同期 phase を足し、phase 1 sync → phase 2 verify の 2 段構成にする）。auto-apply で fail-open 側へ寄せると structural な漏れを隠蔽する
- **Setup-mode の `Write` 直前に pre-existence を再確認する**: config 不在を検出したあと Setup-mode template の `Write` 直前に、再度 `Read` で不在を再確認する（race で既存 file を clobber するのを防ぐ）。canonical: 「Before writing: re-confirm `.claude/<config>.local.md` does not exist ... If it now exists, abort Setup mode and report the conflict — never overwrite」
- **`Read` error semantics は stop-with-error を既定にする**: error が missing か permission / encoding かを reliably distinguish できない場合、Setup-mode 分岐は判別可能なときだけ取り、判別不能なら stop-with-error にする。誤分岐は既存 config を clobber する経路になる
- **Pre-existing layout flag vs new-change regression discrimination**: TEST_FAILED のときは (a) change が導入した regression か (b) base-commit の pre-existing state かを必ず discriminate する。check: (i) `git stash` か base clone で同じ test を再実行、(ii) 同じ failures なら pre-existing、(iii) test agent が flag した plugin / skill 名と change set の path を grep で交差確認、(iv) Step 8 では「pre-existing failures (out of scope of this PR)」と明記する。pre-existing の修正は scope creep
- **Callee-side schema-verb wording for fenced JSON return contracts**: terminal-action 動詞（`End every invocation` / `Terminate` / `Do not produce any additional turn`）は orchestrator に「turn を閉じろ」と受け取られて stall する。canonical: (i) schema-verb form「`Emit a single fenced JSON block at the end of the response, matching the schema ...:`」（terminal-action は禁止）、(ii) 独立した `## Sub-skill caller directive` 節に 3 段落 —「fenced JSON は **return value** であって turn 境界ではない」「次の tool call を同じ agent が immediately issue する」「JSON と次の tool call の間に prose / 確認 /「shall I proceed?」を挿入しない」、(iii) uniqueness clause「Only one fenced JSON block」。複数 callee に置くときは byte-identical にし、新規作成・編集時は terminal-action verb を grep する。orchestrator 側 reminder と必ずペアで入れる — callee 側 wording が無いと reminder は callee の prompt-injection に相殺される
- **Orchestrator-side entry + return-point reminder**: return-point だけでは「決定の瞬間」を救えないので、entry-side の `Pre-invocation reminder` を dispatch 直前に挿入して return-point と直交させる。構造: (i) 次の tool call の named specification、(ii) JSON verdict as return value の framing、(iii) `See § No-Stall Principle.`。この duplication は意図的な reinforcement-by-repetition であり、Simplify で削ってはならない。callee 側の schema-verb wording とペアで入れる（片方だけでは stall が残る）
- **Routine-skill anxiety-abort prohibition + canonical scale-management gate enumeration**: routine skill で mid-flow abort の誘惑を観測したら、`§ No-Stall Principle` 末尾に (i) workload-anxiety abort の禁止と (ii) scale-management gate の明示を置く。(a) 禁止 wording「Aborting the routine mid-flow because cumulative `Skill()` loads "feel expensive", ... is a No-Stall Principle violation」、(b) scale gate の列挙（件数 cap / `*_disabled` flag / max-iter cap 等）、(c) self-recognition prompt「If you find yourself reasoning "X Findings × Y callees would consume too much context — let me stop here", that is precisely the anti-pattern this clause forbids」。「禁止」「forbidden」で表記を統一する。gate enumeration は closed list にして「append here on future addition」を添える
- **Per-invocation input binding for multi-callee orchestration with structured per-element args**: per-element loop で element-specific な args を複数 callee に渡す設計で、per-dispatch の「verbatim from source」再計算だけに頼ると (i) cross-element contamination（Critical bug）と (ii) paraphrase drift が出る。canonical: **per-element loop entry の earliest sub-step で immutable な record fields に binding** し、callee dispatch は record 経由で args を読む。必須: (i) record schema に args field を置き `Bound at (a) entry to verbatim text of <source field>` と明記、(ii) 上記の Critical 警告を binding step に埋め込む。args を必要としない callee は binding を skip する旨を明記する。execution log の render rules で binding field は **出力しない**
- **Commit accept gate は body を verbatim render する**: commit body は必ず fenced code block で独立に render する（prose の宣言だけでは不十分）。提示要素は closed list 4 要素 = Subject fenced / Body fenced（empty は `(no body)`）/ files list / per-file diff
- **UI 成果物は accept gate で実描画も見せる**: user-observable な描画出力を持つ UI は、diff / body の提示に加えて gate を保留したまま実 run-mode で実描画を起動し、目視確認して片付けてから gate に復帰する（synthetic preview は不可）
- **on-disk diff が Step 5 の適用内容と乖離していたら user-gate にかける**: 無言で commit せず provenance を調査し（review 系フックの予期せぬ Edit 適用を疑う）、内容を評価して keep / revert を user に判断させる。keep する場合は独立に再検証してから再提示する
- **Threshold magic numbers anchored on observable platform signals + buffer ratio (not arbitrary)**: (i) signal を実機で empirically 観測する、(ii) 80% buffer で trigger threshold を算出する、(iii) Configuration description に anchor + rationale + version-sensitivity を明記する。trigger は新しい定数の導入であり、既存の既定値を設定可能から内部定数へ落とす変更は trigger しない — 据え置いた既存値に後付けの anchor を要求するのは reject してよい
- **文書サイズは char（`wc -m`）で測り byte（`wc -c`）で測らない**: 日本語を含むファイルは両者が大幅に乖離する。prose に「chars」と単位を明示し、variable にも `*_chars` suffix を付ける
- **Subagent dispatch prompt body lives in `references/<mode>-prompt.md`, not inline in SKILL.md**: 目安 50+ 行で切り出す。canonical: (i) schema（return JSON）は SKILL.md に source-of-truth として残す、(ii) prompt body は references file に verbatim で置く、(iii) SKILL.md の dispatch payload に「`--- LABEL ---` fence に references § <Section> を injected verbatim」と明記する。references file の内容を SKILL.md に重複させない
- **Step 1.5 (or pre-implementation) check: user-specified step number / location reference may be stale**: user が指定した step number は user の頭にある version のもので、現行 SKILL.md と乖離しうる。確認手順: (i) 指定 step の heading を Read、(ii) heading title と user 意図を semantic match、(iii) mismatch なら正しい step を plan に明記、(iv) 訂正を user に明示報告する。silent に解釈すると wrong step を変更して user が混乱する。decomposition / plan creation の earliest step で実施する
- **Experimental feature → opt-in default `false` heuristic (overrides sibling-config consistency)**: 新しい config flag が **直近リリースの experimental** なら、sibling-config の default が `true` でも default を `false`（opt-in）にする。判断軸: (i) 直近の minor / patch で導入、(ii) 実証実験の段階、(iii) unconditional に走らせると想定外の副作用リスク — いずれか該当なら experimental 安全側を優先する。Plan の初期に Decisions § N として「default value」を独立の question に立て、R = opt-in / A = sibling-consistency とする。CHANGELOG の first line は `**Default: disabled** — set \`<flag>: true\` in \`<config-path>\` to opt in per project`。prior version で unconditional だった場合は末尾に「**Behavior change from v<prior>**: ...must explicitly set \`<flag>: true\`」を添える
- **Live validation via current workflow run's own subsequent steps**: 新しい default が今回の実行の後続 step で natural に exercise される変更では、Test plan の検証を manual でなく「今回の実行で natural exercise (live validation)」にするのが canonical。(i) Test plan に「`<config-file>` に新 flag 未指定 → 新デフォルト → 今回の実行の Step N が skip-path を通る」と 1 行、(ii) Out-of-scope reject「`.claude/<config-file>.md` への明示追加は別タスク（live validation を保護するため scope 外）」、(iii) 本 repo で実利用される skill にのみ適用できる（dogfooding できないなら従来どおり manual verification）
- **Risks vs Context placement for natural consequences of a deliberate design choice**: Decisions で意図的に受容した状態は **Risks ではなく Context** に置く。Risks は「想定外で対処が必要な不確実性」、Context は「設計判断の自然帰結」。混同すると (i) Risks が肥大化して真の不確実性が埋もれ、(ii) 次の review iter で「risk なのか accepted state なのか曖昧」と再指摘される。判断軸: 当該事項を「次回 review iter でも `risk` と書き続けるか？」— 書かないなら Context へ移す。canonical 表現は「**<状態名>**: <Decision N> の自然帰結。<解消手段 or 受容理由>」
- **Tool-boundary clarification: `extract-rules` absorbs new patterns, not stale-token renames**: `extract-rules` の責務は **新規 patterns の抽出 / 統廃合** であり、既存ルール内の token rename の自動追従ではない。rules-review が `.claude/rules/` 内の stale token を borderline-flag した場合、Out-of-scope reject の Recommendation は「別 PR / 後続 subtask に手動 rewrite で委譲」。理由付きの reject を明文化して同じ finding の再提起を抑える。stale token の rewrite は per-rule-file の意図再構成を伴うため、auto-extraction より manual edit が canonical
- **Existing-rule literal-trigger exception via context-discrimination rationale**: 既存 project rule（version-skew guard / paired-bump 等）の literal trigger が、**rule 制定時の context** と異なる context で発火した場合、abort せず **3-point rationale** で例外扱いにして Risks に記録する: (i) rule の制定 context を明示、(ii) 現 PR の context が rule context とどう違うか、(iii) rule の目的が現 PR でも結果的に達成されること。3 点すべてを cite して初めて例外が正当化される（1〜2 点では reject）。rule の literal text 改定が必要なら別 PR の Out-of-scope 扱いにする
- **Existing-convention alignment as primary fix direction for natural-language phrasing in skill prose**: skill SKILL.md / references 内の自然言語表現に違和感がある場合、**同一 file / sibling skill 内の既存 convention を探して align** するのを第一候補にする。新しい phrasing の発明は (i) sibling との不整合、(ii) downstream caller の semantic check 行の拡張、(iii) reviewer の再 flag を招く。phrasing-awkward の finding が来たら、まず同 file 内を grep して類似 phrasing を確認し既存 form に揃える
- **Boot-time platform-loader behavior: observational verification + pre-push session-restart validation**: `.claude/rules/**` の再帰 auto-load scope のように **session-boot 時に loader が決定する platform 挙動** に依存する変更は、(i) primary source が未公開なら observational assumption として明示扱いにする、(ii) in-run の live validation はできない（loader は session boot で走る）、(iii) Test plan に「commit 完了後・push 前に手元で Claude Code を再起動して観測検証」を 1 行足す、(iv) Risks に「loader spec は observational」「primary source 未確認」を明記し follow-up monitoring の道を残す。「Live validation via current workflow run's own subsequent steps」rule は適用外。`.claude/rules/**` の placement、`paths:` frontmatter、output 振り分け先の auto-load 判定はこの class に該当する
- **0 件マッチしうる glob は必ずクォートする（この repo の shell snippet は zsh（macOS default）で実行される）**: zsh の `nomatch` はマッチ無しでコマンド自体を非実行のまま abort させ、routine がそこで silent halt する。対象は refspec に限らず glob を含む全引数。bash でも quote 推奨
- **複数行の command-substitution 結果は `while IFS= read -r` で回す（`for x in $var` は不可）**: zsh は unquoted 変数を語分割しない仕様のため、`for x in $var` は変数全体が 1 要素になり 1 回しか回らない（bash は IFS で語分割するので複数回回る）。canonical は `printf '%s\n' "$var" | while IFS= read -r x; do ...; done` または `while IFS= read -r x; do ...; done <<< "$var"`。`setopt shwordsplit` 依存は portability を下げるため採らない
- **Retain the original section label + keep runtime-referenced definitions inline when extracting a heavyweight block out of SKILL.md into a `references/*.md`** (specialization of the stable-phrase-anchor cross-reference rule): 切り出し先には本文を逐語コピーし、本体は元の節ラベル + 委譲ポインタの 1 行に圧縮する（ラベルごと消すと repo-wide でリンクが切れる）。runtime-referenced 定義 — cross-step state-variable の初期化、closed list、entry / skip 条件、USER GATE 宣言 — は本体に inline 残置する。判断軸は「skip-condition 経路でも値が well-defined である必要があるか」「他 Step がその定義を直接読むか」で、Yes なら inline を維持する。**例外 — 工程入口の 1 点で無条件に読み込まれる phase file への節単位の全文移設**: 連続する複数の節をまとめて 1 つの `references/*.md` へ移し、その読込を手前の工程境界に置いた無条件の `Read` 1 箇所に集約する場合、移した定義は inline 相当として扱い、列挙された 4 カテゴリを含めて移してよい。成立条件は 4 つある。(i) 読込が条件分岐の手前に置かれ、かつ**読込地点の節自身が無条件に入場されること** — 節の登録や到達が設定に依存するなら、読込は必ず入場される地点まで前倒しする。(ii) 移した定義を**参照するものと更新するものの両方**が、その境界より後にしか動かないこと — 読み手だけを見ると、前段が追記する変数の初期化を移してしまい、追記が宛先を失う。(iii) 本体に元の節ラベルと委譲ポインタが残ること。(iv) context 圧縮後の再読経路を用意すること — inline と 1 度読みが等価なのは圧縮が起きない前提の下だけで、移す対象に USER GATE 宣言や判定用の網羅列挙が含まれるほどこの差は効く。閉じた列挙を分割する場合は、本体側に「残りは <file> § <節> にある」と述べる集約項目を 1 つ置き、両者の合計が閉じた列挙であることを明示する。あわせて**新しい項目がどちらの半分に属するかを決める基準**を集約項目に書く — 分割の仕組みだけを決めて振り分け基準を書かないと、次の編集者が両方に足すかどちらにも足さない。基準は節の列挙でなく分割の根拠そのもの（境界や条件）で述べる
- **config flag は 4 段階の lifecycle で扱い、期間 anchor は calendar-time にする**: stage 1 — experimental / opt-in（判断基準と CHANGELOG 文言は § "Experimental feature → opt-in default `false` heuristic (overrides sibling-config consistency)" paragraph が定義箇所）→ stage 2 — graduate / default flip（flip の判断は Step 4 の Decisions rationale に組み込む）→ stage 2.5 — deprecation notice（flip 後の安定を確認したら CHANGELOG + README に「vX で削除予定。opt-out 依存があれば issue を」と告知）→ stage 3 — 削除（「flip から ≥4 週間 かつ deprecation notice から ≥2 週間、opt-out signal ゼロ」が条件）。期間の anchor は release 数でなく calendar-time にする
- **default flip の CHANGELOG entry には 2 要素を書く**: (i) opt-out 手順を first sentence に置く（`**Default: enabled** — set \`<flag>: <old-default>\` in \`<config-path>\` to opt out`）、(ii) downstream automation note（自動 update CI は CHANGELOG を読まない）
- **config flag の opt-out signal は closed list の観測チャネルで見る**: (a) 本 repo の dogfooding config、(b) self-retrospective 経由の実行時 signal、(c) 本 marketplace repo の GitHub issues、(d) 既知利用プロジェクトの config 確認
- **config flag 削除の正当化根拠は機能的冗長性のみ**: 「本 repo で未使用」は根拠にならない（配布先 config は観測不能）。documented 需要の一次情報は削除拒否の根拠に使える。user が計画開始前に明示決定した場合のみ stage 2.5 と待機期間を経ず即時削除でき、その際は CHANGELOG に標準 lifecycle からの意図的逸脱である旨と理由を明記する
- **進捗カタログの派生数値ベースラインは一次情報源から再計測する**: 進捗管理用カタログ文書を編集する diff の中で、既に確定済みとして引用されている数値ベースラインを見つけた場合、カタログの記載値（二次情報源）を転記せず対象ファイル自体（一次情報源）から再計測する。同じ分解タスクの兄弟 subtask が既にその値の元になったファイルを変更してコミット済みの場合、キャッシュされた数値は陳腐化している可能性が高い
- **「別の場所に記録済み」を削除の根拠にする前に、その場所が git 追跡下か確認する**: 内容を削除する・重複させない判断を「同じ内容が別の場所に既にある」で正当化する場合、その場所が git 追跡下にあることを先に確認する。`.claude/plans/` はディレクトリごと gitignore 対象なので、そこに設計根拠があることは削除の根拠にならない（fresh clone では解決しない）
- **コミット対象文書から gitignore 対象パスを名指ししない**: コミットされる成果物（`CHANGELOG.md`、配布される `SKILL.md` / `references/*.md`）から gitignore 対象パスを名指ししない — 参照が解決しないうえ、ローカル限定の構成を不必要に露出させる
- **CHANGELOG エントリの粒度**: 「何が変わったか」と「受け手が判断に使う理由」までを簡潔に書き、そこに至る検討経緯・不採用案との対比・内部的な導出過程は書かない。詳細な背景は計画文書や PR 本文に残す
- **共有 reference への切り出しは、全 caller を委譲ポインタまで畳んでから実行あたりの純読込量を再計測する**: 複数 caller に重複した手続きを共有 reference へ切り出すとき、caller 側に手続きの再記述を残すと二重管理になって実際に乖離する。また切り出しただけでは新ファイルの読込が全 caller に加算されるので、実行あたりの純読込量は増える方向に動く — 畳み込み後に `wc -m` で再計測し、増分が残るならそれを受容する判断として記録する
- **実行時に参照されない散文をスキルに書かない**: 対象は **SKILL.md 本体と `references/*.md` の両方**（どちらも起動ごとに読まれる hot path）。置かない内容は、変更の根拠・不採用案・設計判断の経緯・規約が割れている事実・兄弟ファイルが何を書いているか — いずれも agent の動作を変えない。記録先は commit message か PR 本文、または追跡下の `README.md`。根拠専用の新しい reference は作らない（新設すると同期対象が 1 箇所増え、bundle メンバーでは canonical と bundle copy の両方に増える）。**別の規則が「記録を残せ」と求めていても、それは記録がどこかに存在することの要求であってスキル本文に置くことの要求ではない**
