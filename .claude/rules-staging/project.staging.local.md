# Project Rules - Staging

1 回観測のみの候補ルール。次回 incremental 抽出走行（incremental extraction run — `--from-conversation` / `--from-pr` / `--update`）で再観測されたら canonical へ promote されます。手動で `.local.md` へ移動することも可能（promote 待たずに採用する場合）。

## Project-specific patterns

- 検知プローブの網羅性を配布物の散文で断定せず、そのプローブが実際に検査するものだけを述べる。`git rev-parse --git-path hooks/pre-commit` + `test -f` は `core.hooksPath` を解決するが、git config のイベント登録だけで発火する設定駆動の hook ランナーは取りこぼす
- 文書を項目へ分割するパーサが認める形は、実際に踏んだ形だけに限る（`ITEM_HEAD_RE` の類）。分割の判定は内容の行き先を決めるので、誤検知は前の項目の本文を切り落として末尾を次の項目へ運ぶ。`識別用の照合は緩く、内容の検査は厳しくする` が言う「照合は緩める側へ寄せる」は、取りこぼしても対象から漏れるだけで済む絞り込み用の照合を対象にしたものであり、分割の判定には及ばない
- 出力がパーサで分割されるテンプレートには、項目ごとの書式の列挙に加えて、何が項目を分けるかを明記する（`**Question**` 行が Decisions 項目の境界、の類）。境界を書かないと、項目の間に見出しや導入段落を挟んだ書き方が誤りとして扱われず、前の項目の末尾フィールドへ黙って吸い込まれる
- **外部コマンドの出力で分岐する条件は、出力の全パターンを洗ってから書く**: 手元で 1 回動かして観測した文言だけを条件にしない。同じ事象に別の語で始まる行を出す経路があると、条件は取りこぼしても失敗が表に出ず、直したはずの不具合が静かに戻る。ヘルプとバイナリが持つ書式文字列まで当たり、その事象で出うる文言を列挙する
- **出力を読ませる指示には読む先を書く**: エージェントに「コマンドの出力に X が出ていたら」と判断させる指示では、標準出力と標準エラーのどちらを読むかまで書く。書かないと片方だけを読む解釈が成り立ち、その行が反対側に出ていれば条件は一度も成立しない。どちらへ出るかは実測で確かめる
- **範囲外を戻す安全装置は、その呼び出しの中で生まれた変更にだけ効かせる**: レビュー用スキルが範囲外のファイルを `git checkout` で戻す装置を持つ場合、対象はその呼び出しの中でレビュー担当が書いたファイルに限る。呼び出し時点で既に作業ツリーにあった変更は戻さない。1 つの変更に配布用コピー・バージョン・変更履歴が付いて回るこの repo では、範囲外という理由だけで戻すと同じ作業で意図して入れた成果を消す
- **作り手に自分の産物を判定させない**: 受け入れ基準に「何が産んだか一切覚えていない状態で読む」類の条件を持つ産出スキルでは、その判定を産んだディスパッチの中では実行できない。基準の文言を厳しくしても直らないので、書き終えたあとに、その実行の入力（会話ログ・PR コメント・走査結果）を読めない別のサブエージェントへ判定だけを投げる。作る最中の判断は載せる方向へ傾き、あとから問われると同じ基準でも答えが変わる
- **逐語注入される節は注入地点で自己完結させる**: サブエージェントへのプロンプトを節の閉じた列挙から組み立てる場合、節が列挙に載っていれば制約は呼び出し先へ運ばれたように見えるが、本文が他ファイルへのポインタ止まりなら、そこが引く規約はサブエージェントに届かない。届かない規約は `old_string` の衝突や文字の正規化として黙って失敗する。再掲で解かず、fence の項目側に引いている規約を名指しして運ぶ
- **後段の対象集合は書き込み工程の記録から受け取る**: 直前の工程が何を書いたかを、レンダリング済みのレポート文面を読み直して復元しない。レポートはモードごとに形が違い、件数の表しか出さない経路や、見出しのパスと実際の書き込み先が食い違う経路があり、対象集合が静かに空になる。書き込み工程に「どのファイルへどの項目を書いたか」の記録を残させ、それを唯一の対象集合にする
- **1 単位 1 ディスパッチを多単位へ広げるときは、境界が担っていた不変条件を書き直す**: ファイル単位のディスパッチを複数ファイルへまとめると、ファイル内でしか一意でない識別子は `(ファイル, 識別子)` の組で突き合わせ直す必要があり、ファイル単位で足りていた適用ガードは項目単位まで狭め直す必要がある。どちらを落としても、対象ファイル内にある対象外の項目への書き換えが、検証も適用ガードも素通りして通る
- **手順の実体が参照ファイルにあるモードへ工程を足すときは、参照ファイルの番号付き手順に足す**: SKILL.md 側のモード要約への 1 行追加は呼び出しの実装ではない。SKILL.md が全手順は参照ファイルを読めと指示している以上、その手順どおり実行するエージェントには新しい工程が一度も現れず、そのモードだけ書き込み経路が素通りする。要約と参照ファイルの手順を同じ変更で両方更新する
