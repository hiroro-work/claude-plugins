   **Plan-body prose polish (runs when `polish_prose` is `true` and `run_mode` is not `fast`, after the plan document is written and before it is presented).** **Skip when `polish_prose` is not `true`, or when `run_mode == "fast"`** (the `polish_prose` case fires only when explicitly set to `false`; the default `true` and a non-boolean fall-back-to-`true` both run — see § Configuration's `polish_prose` bullet; the run-mode case follows the same silent-skip discipline as Step 6.5's fast-mode skip): skip this `prose-polish` call **silently** and present the un-polished plan — emit no note. When both conditions allow it, once the full plan body has been written to `.claude/plans/<slug>.md` (established below) and after sub-step 1.5's **Prose-language self-audit** has brought the explanation prose into the resolved `language`, and **before** presenting it — before delegating to the visual gate, which copies its served file from `.claude/plans/<slug>.md`, or before the chat presentation when the probe skips the gate — invoke `Skill(prose-polish)` in **file mode**: `Files:` = the plan document path, **plus the decomposition state file's canonical path on the run that created it** ([`task-decomposition.md`](task-decomposition.md) § Canonical state-file path); `Language:` = the resolved `language`; and **no `Model:`** (see § Configuration's `subagent_model` bullet). A plain `--resume` run did not write it, so it stays out — with one exception: the planning-draft recovery ([`task-decomposition-resume.md`](task-decomposition-resume.md) § A step 3a) starts from `--resume` but continues in Normal sub-mode, so a state file written after it belongs to this run. On an undecomposed run `Files:` carries the plan document alone. **Anti-skip guard**: do not skip this dispatch when `polish_prose` is `true` merely because sub-step 1.5's **Prose-language self-audit** returned clean or because the prose appears concise; the self-audit corrects language-level translation errors, while prose-polish refines naturalness and fluency and may still improve prose the self-audit passed. It runs on every difficulty tier. Judge the verdict semantically and proceed per § No-Stall Principle: on a `done` / `no-change` verdict present the (possibly-polished) plan; on `error` emit a one-line note and present the un-polished plan rather than blocking — nothing is appended to `bundle_skills_unavailable`. A `Skill()` call failure after one retry is the distinct availability signal — the skill itself is unreachable — and additionally appends `prose-polish unavailable (plan-body polish)` to `bundle_skills_unavailable` (§ Step 1 sub-step 3's "Initialize the bundle-unavailability ledger here" bullet). The verdict is a return-point covered by § No-Stall Principle — do not pause after it.

   **Establish the plan document.** Resolve `<slug>` **once per run, then reuse it verbatim on any Step 4 re-entry** (a `rewrite-approach` re-entry must not re-resolve it). Reuse the active decomposition state file's `slug` when a state file is in play, otherwise derive a kebab-case slug from the effective task (transliterate non-ASCII where reasonable, strip punctuation, lowercase; on collision with an existing `.claude/plans/<slug>.md` **from a prior run**, suffix `-2`, `-3`, … — this collision check applies only to first resolution, never on re-entry against this run's own `<slug>.md`), mirroring `references/task-decomposition-normal.md` § B. The plan was internally reviewed in Step 3 when `plan_review_enabled`; when it is `false` (`SKILL.md` Step 3's Disabled-phase exception) Step 3 was skipped, so this user-approval gate is the sole review — carry any unresolved Step 3 points into the presentation either way.

      - **Trivial-tier route.** When the assessed tier is **Trivial** ([`tier-assessment.md`](tier-assessment.md) § Lanes), go straight to the **chat approval** below **without reading** `references/visual-plan-review.md`, and skip the probe. This is keyed on the **assessed tier**, never on `plan_review_enabled` being `false`: a `fast` run produces that without the tier being Trivial.       - **Browser-reachability probe** (skipped on the Trivial route above)**.** Run `printenv CLAUDE_CODE_REMOTE`. A value of `true` (the cloud-execution marker Claude Code on the Web sets) means the local browser is unreachable and the gate can never display: go straight to the **chat approval** below **without reading** `references/visual-plan-review.md`. Any other value — including unset or empty — means local execution; continue with the visual gate. **Anti-skip guard**: this probe's `true` result is the *only* thing that licenses skipping the gate reference. Skipping it on a guess — including rationalizing under § No-Stall Principle that chat is faster — silently disables the gate and remains a defect.
      - **Visual gate**: read [`references/visual-plan-review.md`](visual-plan-review.md) and follow it top to bottom. The visual path does **not** emit the chat condensed view / preamble / guidance line.
      - **Chat approval** (entered on the Trivial route, when the probe returned `true`, or when the visual gate returned `fallback`): render it per [`references/plan-format.md`](plan-format.md) § Step 4 presentation order's chat output sequence, which ends on a pointer to the plan document written above and a wait for the user's chat reply. ## Sub-step 1 — Step 3-completion verification

1. Before presenting, verify via `TaskList` that `Step 3: Plan Review` is `completed`. If the row is not `completed`, emit a one-line inline note to the user naming it (e.g., `Plan review found incomplete (Step 3: Plan Review still pending) — running the review pass before presenting the plan.`) then return to Step 3 to process it (do not flip the row to `completed` without doing the review work). **Exception**: when `plan_review_enabled` is `false` (`SKILL.md` Step 3's Disabled-phase exception) — so the row is already `completed` — that completed state is the intended skip, so proceed to the approval presentation normally.

## Sub-step 1.5 — Prose-language self-audit

1.5. **Prose-language self-audit**: Before presenting the plan for approval, verify that explanation prose in the plan body (Overview narrative, Decisions rationale, Build order descriptions, Test plan steps, Risks/Unknowns paragraphs) is written in the resolved `language`. Schema tokens (`Overview` / `Decisions` / `Build order` / `Test plan` / `Risks` / `Unknowns`), step labels, enum values, identifiers, and quoted code strings stay in their original form regardless of `language`. Audit both directions: (a) if any explanation sentences are in a different language than the resolved `language`, and (b) if concept words outside the verbatim-preserve scope — ordinary nouns, adjectives, conjunctions, verb phrases — are over-preserved in the source language rather than rendered in the resolved `language` (per [`references/localization.md`](localization.md) § Localization granularity's Negative-direction rule). Revise any failures now per [`references/localization.md`](localization.md) § Localization granularity before proceeding to sub-step 2. **Re-entry coverage**: this audit must re-run on every entry into Step 4 — both the initial entry and any re-entry triggered by sub-step 1's "return to Step 3" path or sub-step 3's material-change path.

## Sub-step 3 — rewrite-approach bucket runtime

- **Base behavior**: mark the `Step 3: Plan Review` row `pending` again, run the read-back sub-step, return to Step 3 to re-review the modified plan (one further single pass), then re-enter Step 4 from sub-step 1 (so sub-step 1's completion check on the re-opened row and sub-step 1.5's prose-language re-entry-coverage audit both run before re-presenting at sub-step 2).
- **Exception — the plan phase held off by the run mode** (applies on a **full-lane** tier only; on an express-lane tier the reactivation below takes precedence): **`run_mode == "fast"`**, which left `plan_review_enabled = false` at Step 1 sub-step 4 (§ Configuration's **Run mode** bullet). Skip the re-open and return-to-Step-3 legs entirely — apply the revision to the plan document, run the read-back sub-step to confirm it, then re-enter Step 4 directly from sub-step 1, since `plan_review_enabled` stays `false` through the rewrite. The `fast` run mode's Step 6.5-only skip is re-evaluated only when [`tier-assessment.md`](tier-assessment.md) § Resolution procedure actually re-runs (the express-lane reactivation below), not when this exception fires.
- **Express-lane re-activation**: if the assessed tier put the run on the **express** lane ([`tier-assessment.md`](tier-assessment.md) § Lanes — Trivial or Simple), an Approach-level material change means the task is no longer self-evident at that tier. **Key this on the assessed tier, not on `plan_review_enabled` / `code_review_enabled` being `false`** — a `fast` run or a configured `code_review: false` produces that without the tier being express, so inferring the tier from a flag would fire this reactivation on a run that merely held a review phase off. **Re-derive the tier against the rewritten plan**: reset `difficulty_skipped_steps = []` and `fast_mode_skipped_steps = []`, then re-run [`tier-assessment.md`](tier-assessment.md) § Resolution procedure in full against the rewritten plan. **Clamp the re-assessment upward**: take `max(pre-rewrite tier, new assessment)`, so a rewrite that scopes the task *down* cannot lower the tier and re-disable a review phase mid-run. It re-initializes `plan_review_enabled` / `code_review_enabled` from the run mode, config, and the newly assessed tier — one of the two exceptions to their monotonic-lowering invariant (`references/step1-load-settings.md` § Sub-step 4 — review-phase resolution) — re-resolves `subagent_model`, rebuilds both ledgers from scratch, and re-marks the rows the new tier skips. Then **clear back to `pending`** every row the pre-rewrite assessment had marked `completed` that the clamped tier no longer skips: the top-level `Step 8: Code Review` row and its `Step 8-1` row **when the re-derived `code_review_enabled` is `true`** — it always is on a clamped tier above Trivial *unless* the project configured `code_review: false`, in which case leave their `completed` state in place; the top-level `Step 3: Plan Review` row **unless** the re-derived `plan_review_enabled` is still `false`, which happens on one guard — `run_mode == "fast"`, whose Step 1 sub-step 4 derivation holds the phase off at every tier (the re-run re-appends its `fast_mode_skipped_steps` entry for a clamped tier above Trivial, and the row stays `completed` from its Step 1 registration); and any of `Step 6: Tidy` / `Step 6.5: Polish Prose` / `Step 7.5: Rules Compliance Review` / `Step 11: Update Rules`. Finally, **when the clamped tier leaves the express lane**, apply [`tier-escalation.md`](tier-escalation.md) § What an escalation does' **Read what the express lane deferred** step — the plan was authored on that lane and now needs the full lane's shape. When the clamp lands the run back on the express lane, skip that step: the deferred references still do not apply.
