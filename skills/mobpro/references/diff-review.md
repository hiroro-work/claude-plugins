# mobpro M6 Diff Review

**Read this file once at M6 loop entry**: § Per-unit review range's numbered steps apply at each unit, and its **M6-exit unstage** paragraph applies once at M6 exit. Read `../dev-workflow/references/diff-presentation.md` at the same point. The `crit` surface's own procedure sits in [`crit-diff-review.md`](crit-diff-review.md) — read it once, and only after § crit path's probes clear.

## Display surface (`commit_review_gate`)

Branch on the resolved `commit_review_gate` ([`configuration.md`](configuration.md) § Fallback keys):

- **`diff`** (the default): render `git diff <m6_review_base>..<unit_obj>` in chat inside a fenced block, preceded by the line [`learning-gates.md`](learning-gates.md) § A (M6 diff review)'s "Opening the review" paragraph gives.

  **Rendering mode.** Pick the mode per `../dev-workflow/references/diff-presentation.md` § Rendering ladder. Capture the diff once — the same output the render consumes — and use that capture as the measurement input, slicing it on `diff --git a/<path> b/<path>` boundaries wherever the chosen mode truncates per file. The full-diff command the skeleton trailer names is `git diff <m6_review_base>..<unit_obj> -- "<path>"`.

- **`crit`**: launch crit on the same range (§ crit path), emitting the line [`learning-gates.md`](learning-gates.md) § A's "Opening the review" paragraph gives **in the same turn as the launch, before the junior opens the browser**.

## Per-unit review range

Each unit's review names a *range* built without moving a ref — the technique `../dev-workflow/references/diff-presentation.md` § Detached review object owns, with `<base>` = `m6_review_base` and `<head>` = `<unit_obj>` per that file's § Caller endpoints.

`m6_review_base` is M6-loop-local state, initialized to `base_commit` at M6 loop entry. Per unit:

1. **Build `<unit_obj>`** per `../dev-workflow/references/diff-presentation.md` § Detached review object steps 1–3, with `<base>` = `m6_review_base`, the paths in scope being **this unit's edited paths**, and a one-line message naming the unit. Four M6 obligations ride on its step 1. **With this unit's paths staged, run `boundary_check_commands`** ([`configuration.md`](configuration.md) § Fallback keys — skipped entirely when the key resolves to none, which is its default): execute each entry in order, then re-run the same `git add` over that same path set, so what a command rewrites is carried into this unit's tree and the junior reviews the content as it will be committed rather than as it was typed. Without the re-add, `write-tree` snapshots the pre-run content and the key changes nothing. Unlike `dev-workflow`, no `interactive_commits` condition applies — M6 builds a unit object on every run. On a non-zero exit, record a one-line note naming the unit and the command, with `<reason>` = the last non-empty line of stderr truncated to ≤ 80 characters, or `(no stderr)` when stderr is empty or whitespace-only; then fix what the command reported and re-run that one command **once**, and on a second non-zero exit keep the note as the record and build the object from whatever the working tree now holds — M8's `check_commands` is still the gate that stops the run, and the chain-abandon fallback below covers the git calls alone. The staged set excludes the `SKILL.md` § Workflow artifacts set — never stage the plan document or the decomposition state file, which a run edits as it goes. **Immediately before `write-tree`, unstage any § Workflow artifacts entries the index carries** (`git reset -- "<artifact-path-1>" ...`, skipped entirely when none are staged): `write-tree` snapshots the whole index, not the paths staged above, so an artifact something *else* staged mid-loop — an environment hook that bulk-stages untracked files, or the user's own `git add` — rides into this and every later unit's tree, and M11 lands those trees as commits. Do **not** reset the index between units: it must accrue every earlier unit's content for the range below to carry only this unit's delta. And append every path staged here to `m6_staged_paths` — M6-loop-local like `m6_review_base`, initialized to `[]` at M6 loop entry — rather than reading the set off the index at M6 exit, since the index there also holds whatever the user had staged before the run, which M6 deliberately leaves alone.
2. **Present** `<m6_review_base>..<unit_obj>` on the resolved surface (§ Display surface).
3. **Advance and record** once the review resolves: `m6_review_base = <unit_obj>`, and — unless the fallback below has already abandoned the chain for this run, in which case advance only and record nothing — append `{heading, <unit_obj>}` to `implementation_boundaries` (`SKILL.md` § Cross-step state variables) — the **accepted** object, so a unit rebuilt mid-review records only its final form. `heading` is this unit's name as narrated in its preview (`SKILL.md` M6 sub-step 2 (a)), which is what M11 labels the unit's commit with. That list is M6's half of the **Build-order boundary chain**. A mid-review code change does not resolve it — per [`learning-gates.md`](learning-gates.md) § A's "Change requests raised during the review" paragraph, re-run step 1 against the unchanged `m6_review_base` to rebuild `<unit_obj>` from the now-edited files, then present again.

If step 1's git calls fail, this unit's review falls back to a chat rendering that needs no new object: tracked paths via `git diff <m6_review_base> -- "<path>" ...`, and untracked ones (`??` in `git status --porcelain=v1 --untracked-files=all -z` is the discriminator — `-z` keeps paths verbatim instead of C-quoting them) via `Read`, presented as a new-file hunk. § Display surface's "Rendering mode" paragraph governs this rendering too, measured across the tracked slices plus the untracked contents, with each path standing as its own slice in place of the `diff --git` boundaries. Its skeleton trailer takes a per-kind form here, since the failed step left no `<unit_obj>` to range against: on a tracked slice it names `git diff <m6_review_base> -- "<path>"`, and on an untracked slice it names opening `<path>` itself. `m6_review_base` stays put, so the next unit's range covers both units. **Also set `implementation_boundaries = []` and record no boundary for any later unit**: because the index accrues, a chain missing this unit would fold its content silently into the next unit's object, and M11 would label it as that unit's commit.

`git write-tree` snapshots the whole index, so anything already staged when M6 began rides along in unit 1's tree and appears inside `base_commit..<unit_obj>`. Point it out if the junior asks about a file no unit touched.

**M6-exit unstage** — once at M6 exit, after the last unit's review (`SKILL.md` M6 sub-step 4 anchors this in the M6 step sequence), run `../dev-workflow/references/diff-presentation.md` § Detached review object step 5's unstage over `m6_staged_paths`, so M11 still sees new files as untracked (`??`) rather than staged. Two notes. A path the user had already staged before the run loses that staging if a unit review touched it — its content is untouched in the working tree. And a failure follows that section's "On failure" paragraph.

## crit path

**Probe before reading** (`Keep in sync with ../dev-workflow/references/interactive-commits.md's Diff-review mode branch probe paragraph, which names the owning sections.`)**.** The first time the M6 loop reaches this path, run both probes — `crit --version` (non-zero exit / command-not-found → unavailable; never substitute `command -v crit`, which sits outside the `Bash(crit *)` grant) and `printenv CLAUDE_CODE_REMOTE` (value `true` → no local browser) — unconditionally, and cache the pair as `m6_crit_available` — M6-loop-local like `m6_review_base`. The distinct name matters: M11 runs the same pair at its own gate and writes upstream's `crit_commit_review_available`, so a shared name would have one gate overwrite the other's answer. **When either fails**, skip the delegated read below — and with it `crit-commit-review.md` — entirely: render this unit and every one after it on the chat surface (§ Display surface's `diff` bullet) — the failing probe does not skip the unit that triggered it — and make no further attempt for the rest of the loop. Emit **one** informational note for the whole M6 loop, not per unit, in the resolved `language`: `crit --version` failed → name the install URL (<https://github.com/tomasz-tomczyk/crit>); only the reachability probe failed → name that no local browser is reachable; both failed → name the unavailability. That is the whole of the note.

**When both clear**, read [`crit-diff-review.md`](crit-diff-review.md) and follow it — it holds the `../dev-workflow/references/crit-commit-review.md` parts M6 reuses and the decision mapping M6 substitutes for that file's own.
