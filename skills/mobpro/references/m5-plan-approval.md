# mobpro M5 Plan Approval

The procedure `SKILL.md` **M5 — Plan approval (USER GATE)** delegates here. **Read this file once**, at M5. Unqualified `§ <Heading>` references resolve to `SKILL.md`, and a bare `sub-step N` is this step's own.

**Plan-body prose polish** (`Keep in sync with dev-workflow references/step4-finalize-plan.md's Plan-body prose polish paragraph.`). When `polish_prose` is `true` **and `fast_mode_active` is not** (`SKILL.md` § Fast mode), call `Skill(prose-polish)` in file mode before the approval surface below: `Files:` = `.claude/plans/<slug>.md` (written at M3 sub-step 3's plan authoring), plus `state_file_path` on the run whose M2 (Kickoff) wrote it — including the `../dev-workflow/references/task-decomposition-resume.md` § A step 3a recovery, which starts from `--resume` but continues in Normal sub-mode and re-binds the path once a decomposition is accepted — it stays `null` otherwise, and `Files:` then carries the plan document alone; `Language:` = the resolved language; no `Model:`. When either condition fails — `polish_prose` not `true`, or `fast_mode_active` — skip silently and append nothing to `fast_mode_skipped_steps`.

Run it **before** sub-step 1 enters the visual gate, which copies its served file from the plan document.

An `error` verdict means prose-polish ran — note it in one line, present the un-polished plan, and append nothing. A `Skill()` call failure is the distinct availability signal: retry once, then skip and append `prose-polish unavailable (plan-body polish)` to `bundle_skills_unavailable`.

1. **Approval surface** — the visual gate, degrading to chat. **On the browser path, before entering the reference at all**, do both of these in the turn that issues the launch: emit sub-step 2's plan narration, and fold any open points M4 carried forward into the plan document's `Watch-outs` so the browser renders them. Once the reference is entered it blocks on the browser submit and renders nothing in chat, so a later turn is too late.
   - **Browser-reachability probe** (`Keep in sync with dev-workflow references/step4-finalize-plan.md's Browser-reachability probe bullet.`): run `printenv CLAUDE_CODE_REMOTE`. A value of `true` means the local browser is unreachable — go straight to the **chat** bullet **without reading** `../dev-workflow/references/visual-plan-review.md`. Any other value — including unset or empty — continues with the gate below. This probe's `true` result is the only thing that licenses skipping the reference; skipping it on a guess — including on the grounds that chat is faster — silently disables the gate, and § Learning-Stop Principle is not a licence for it.
   - **Visual gate**: read `../dev-workflow/references/visual-plan-review.md` and follow it top to bottom. It returns `approve` / `rewrite-approach` / `fallback`; its `fallback` continues with the **chat** bullet below (that file's § Fallback contract still owns the launch-time failures the probe cannot foresee). Resolve `serve.mjs` under the sibling `dev-workflow` directory (`../dev-workflow/scripts/plan-review/serve.mjs`) rather than by that reference's step 1 base-directory rule, which here resolves under `mobpro` — per § Runtime reads' "Script carve-out" paragraph. Issue that reference's prev-snapshot `cp` with **unquoted** paths — M3 sub-step 3 keeps `<slug>` kebab-case ASCII, and the `allowed-tools` grant is path-scoped.
   - **chat** (the destination of the probe's `true` result and of the gate's `fallback`): present the full plan in chat.

   The browser gate launches its process via **background Bash**, not the `Agent` tool (§ Direct Agent dispatch sites). The browser path renders nothing in chat.
2. **Plan narration**: explain in 2–3 lines what it builds and in what order — narration, not a comprehension question. On the browser path sub-step 1 has already placed it in the launch turn; on the chat path it follows the plan body and is closed by the approval question — the only thing this gate asks the junior. **When `plan_review_enabled` is `false`**, say within those same 2–3 lines that the reviewer pass did not run, so this approval is the only review the plan gets. Name the cause the entry condition at `SKILL.md` § M4 — Plan review (quality gate) gives: a configured `plan_review: false` reads as turned off for this project, and `--fast` as turned off for this run. **When both hold, name the configured one**. Emit the narration **once per M5 entry**: when the gate returns `fallback`, it already went out with the launch turn, so present the plan body and go straight to the approval question rather than repeating it. That question asks whether to go ahead with the plan and invites anything that looks off to be raised first. It is **chat-path only**: do not also ask it in chat.
3. Classify the outcome into three buckets: **accept** (→ implementation) / **adjust** (revise the plan → re-open M4 → re-review → re-enter M5) / **withdraw** (end the workflow). **Disabled-plan-phase exception on the adjust bucket**: when the plan phase is off — on either cause the entry condition at `SKILL.md` § M4 — Plan review (quality gate) closes its list at — skip the re-open-M4 and re-review legs entirely: run sub-step 4's read-back where that path calls for it, apply the revision, and re-enter M5 directly. A browser gate's return maps directly — `approve` → **accept**, `rewrite-approach` → **adjust** (the gate has already written its revisions to `.claude/plans/<slug>.md`, so resume adjust at the re-open-M4 leg rather than revising the plan again — or, when the disabled-plan-phase exception above applies, at re-entering M5, since that leg is skipped); `fallback` is a route rather than an outcome (continue with sub-step 1's **chat** bullet). On the chat path classify the reply semantically; interrogative / non-committal replies re-classify via a confirming question.
4. **Chat path**: run a one-line read-back before applying any revise instruction. **Browser path**: no read-back — the gate applies its own submitted comments autonomously inside its loop, its "switch to alternative" toggle's Recommendation/Alternative swap included. The gate's procedure sends the swap's dependent updates through "the text-path swap-decisions bucket" in dev-workflow's `SKILL.md`, which `mobpro` neither reads nor has: treat the swap as a localized in-gate edit and sweep its dependents across `mobpro`'s own sections — `What we're building` / `Build order` / `How we'll check it works` / `Watch-outs`, per [`plan-shape.md`](plan-shape.md) § Review lens' mapping rule, whose first two absorb dev-workflow's `Approach` / `Scope` sweep vocabulary.
