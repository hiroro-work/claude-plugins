# Visual Plan-Review Gate (Step 4)

Deep reference for Step 4's **visual gate**, the plan-approval surface. Read and follow this top to bottom once the caller's browser-reachability probe has cleared.

The run never enters Plan Mode, so this gate freely performs the non-read-only operations below (writing the served file, launching `serve.mjs`). The canonical plan document is `.claude/plans/<slug>.md`, written by Step 4 sub-step 2 before this procedure runs (step 3 below names the `<slug>` source).

The gate is a browser-based, structured plan review. It returns one of three outcomes to Step 4: **`approve`**, **`rewrite-approach`**, or **`fallback`** (defined in § Decision mapping and § Fallback contract below).

## serve.mjs contract

The viewer (`scripts/plan-review/serve.mjs`) ships with this skill; this gate only invokes it. Its contract:

- **Invocation**: `node <serve.mjs> --plan <path> [--prev <path>] --lang <resolved-language> [--timeout <seconds>] --wait` — serves the Markdown plan at `<path>` on a random `127.0.0.1` port, opens the local default browser, and blocks until the user submits. `--lang` is the workflow's resolved `language` (`ja` / `en`); it controls **only** the language of browser-generated text — the "switch to alternative" comment body and the diff banner — and defaults to `en` when omitted. `--prev <path>` is the plan version the user reviewed on the previous launch (the `.plan-review.prev.md` snapshot — see § Prev snapshot); when supplied and readable, the browser highlights what changed since then. Omit it on the first launch; an unreadable `--prev` is non-fatal (the viewer renders without a diff). `--timeout <seconds>` caps the wait; omit it for serve.mjs's default (24h) and pass `--timeout 0` to disable the timer entirely (wait indefinitely).
- **`GET /api/plan`**: returns `{ "id": "<planId>", "markdown": "<raw plan markdown>", "lang": "<ja|en>", "prevMarkdown": "<raw markdown | null>" }`. The browser splits the markdown into sections, classifies them (Overview / Decisions / Build order / Test plan / Risks / …), and renders the review surface; the server does **not** segment the plan or enumerate block ids. `prevMarkdown` is the `--prev` file's content (or `null` when `--prev` is absent / unreadable).
- **stdout (in `--wait` mode)**: the **only** bytes written to stdout are the final submit JSON on one line — `JSON.parse`-able whole. All progress / errors go to stderr.
- **Submit JSON shape**: `{ "plan": "<planId>", "decision": "approve" | "revise", "submitted_at": "<iso8601>", "comments": [ { "block": "<id>", "excerpt": "<text>", "body": "<comment>" } ] }`. `comments` may be empty (an `approve` with no comments). `block` is a **browser-assigned semantic id**: `decision-<n>` for the n-th Decision card, or `<section-slug>::<n>` for the n-th commentable block (paragraph / list item / code block / …) within a section. `excerpt` is a short prefix of the commented block's text, for disambiguation.
- **Comments file**: serve.mjs also writes the same JSON to `<planId>.comments.json` next to the plan file, where `planId` is the plan file's basename with the trailing `.md` removed.
- **URL file**: at listen time, before the browser launch is attempted, serve.mjs writes the viewer URL as a single line to `<planId>.url` next to the plan file (same `planId` derivation as the comments file). A failure to write it is non-fatal and the server stays up.
- **Exit codes**: `0` submit, `124` timeout (fires after the `--timeout` cap — default 24h; `--timeout 0` disables the timer so it never fires), `130` SIGINT / SIGTERM, `1` startup error (e.g. unreadable plan).

## Prev snapshot

To let the viewer show what changed across a revise round, the **previous** served-file content is preserved as `.claude/plans/<slug>.plan-review.prev.md` and passed to the next launch via `--prev`. Discipline: **whenever you are about to write the served file (`.plan-review.md`) and it already exists, first `cp` it to `.plan-review.prev.md`.** There is exactly **one** such site: the **Compose the served plan file** step, immediately before the `Write`, when the served file already exists — i.e. any non-first launch, whether reached by a localized `revise` re-launch or a `rewrite-approach` re-entry. A revise round needs no site of its own: its comments land in the canonical plan document and the figures file, and the next launch's compose is what rebuilds the served file from them.

On the **first** launch the served file does not yet exist, so no prev is created and the launch omits `--prev`. `.plan-review.prev.md` is a workflow artifact covered by `SKILL.md` § Workflow artifacts (cross-step fixed exclusion) and removed in [`finish-phase.md`](finish-phase.md) § Completion's cleanup.

## Figures layer

Figures live outside the canonical plan document, in `.claude/plans/<slug>.figures.md`, so the plan's prose stays figure-free everywhere that document is read — Step 5's implementation walk, the Step 3 reviewer's payload, and the chat approval this gate degrades to. Only the served file carries them.

**File format.** A sequence of blocks. Each opens with a `## <section name>` heading naming the plan section it belongs to — `Overview` / `Decisions` / `Build order`, the closed list of sections a figure may target — and holds that section's single figure with its caption. A heading naming a section the canonical document does not have is skipped with a one-line note; a repeated heading is a violation the compose step reports rather than merging.

**Insertion position**, one per section: `Overview` — directly after the field bullets, before the next element; `Decisions` — after any leading prose, before the first `**Question**` line; `Build order` — before the numbered list.

**Who writes it, and when.** Whoever runs this gate writes it, immediately before the first compose — never at Step 2, since a plan that never reaches a browser never needs figures. Later launches reuse the file as it stands; only a revise comment on a figure rewrites it (§ Procedure step 6). The authoring conventions — which notation, how many figures, the caption contract, the colour tokens, the SVG skeletons — are in [`plan-figures.md`](plan-figures.md); `Read` it at that point and not before.

`.figures.md` is a workflow artifact covered by `SKILL.md` § Workflow artifacts (cross-step fixed exclusion) and removed in [`finish-phase.md`](finish-phase.md) § Completion's cleanup.

## Procedure

1. **Resolve the serve.mjs path.** It lives at `<skill base directory>/scripts/plan-review/serve.mjs`, where `<skill base directory>` is the directory the harness reports as "Base directory for this skill" at this skill's invocation. **Do not hardcode an absolute path.**

2. **Re-confirm reachability.** Run `printenv CLAUDE_CODE_REMOTE`; `true` means the served page never reaches the user — return **`fallback`** to Step 4 without launching. Any other value — including unset or empty — means local execution; continue.

3. **Compose the served plan file.** If `.claude/plans/<slug>.plan-review.md` **already exists** (any non-first launch), first `cp` it to `.claude/plans/<slug>.plan-review.prev.md` before overwriting (§ Prev snapshot). Then compose the served file from two inputs and `Write` it to `.claude/plans/<slug>.plan-review.md`, where `<slug>` is the slug Step 4 sub-step 2 established: the **canonical plan document** `.claude/plans/<slug>.md`, carried **verbatim** — no block markers are inserted — and the **figures file** `.claude/plans/<slug>.figures.md`, each of its blocks inserted at the position § Figures layer gives the section its heading names. When the figures file does not exist — the ordinary case for a plan with no figures — the served file is the canonical document verbatim and this step is a plain copy.

   This **served file** is the gate's derived copy, and the canonical `.claude/plans/<slug>.md` is **never written from it**. Prose a revise round changes is applied to the canonical document itself (step 6), so that document is current at every moment of the loop, and each launch rebuilds the served file from it.

4. **Launch the gate (background Bash).** First clear any stale URL file from a previous launch — `rm -f .claude/plans/<slug>.plan-review.url`, as its own foreground call so it stays inside the `Bash(rm -f .claude/plans/*)` grant. Then run `node "<skill base directory>/scripts/plan-review/serve.mjs" --plan ".claude/plans/<slug>.plan-review.md" --lang <resolved-language> --wait` as a **background Bash** command (`run_in_background: true`), substituting the workflow's resolved `language` for `<resolved-language>`, and emit a Progress Visibility status line in the same turn (e.g. "Launching the visual plan-review gate in your browser…"). **When `.claude/plans/<slug>.plan-review.prev.md` exists** (a re-launch where a prev snapshot was taken — § Prev snapshot), append `--prev ".claude/plans/<slug>.plan-review.prev.md"` so the viewer shows the diff; omit it on the first launch. Do **not** pass `--timeout`: the gate uses serve.mjs's 24h default. Pass `--timeout 0` only if truly no timeout (wait indefinitely) is wanted. Notes:
   - This is background **Bash**, **not** the `Agent` tool.
   - Background dispatch is **required** here — a foreground Bash call (~10-min limit) could not survive the wait. The harness re-invokes the agent when the background process exits. Waiting for that exit is a **harness-tracked boundary**, not a "type continue" pause (see `SKILL.md` § No-Stall Principle) — proceed on the exit notification.

   **Surface the gate URL in chat**, in the turn right after the launch call returns: `Read` `.claude/plans/<slug>.plan-review.url` (§ serve.mjs contract's **URL file** bullet) and emit its single line in chat as a one-line message, so the user can open the gate by hand when the browser did not open on its own. The URL is copied verbatim; the surrounding sentence is written in the resolved `language`. Paired bilingual samples (runtime rendering demonstration) — `language: ja`: `ブラウザが開かない場合はこちらを開いてください: http://127.0.0.1:52341/`; `language: en`: `If your browser did not open, visit http://127.0.0.1:52341/`. If the `Read` fails, re-read **once** and then give up silently — a missing URL file is non-fatal. Do not delay the read with a `sleep`. This read-and-emit is the required tool-carrying turn after the background dispatch, not the content-free waiting turn `SKILL.md` § No-Stall Principle forbids. Every re-launch loops back to this step on a fresh port, so the URL is re-emitted per launch.

5. **Read the decision.** When the background process exits, read its captured stdout. In `--wait` mode the only stdout content is the submit JSON (one line) — parse it. **When the JSON is there, decide on it.** When it is absent, re-read the capture until the host's termination marker appears (Claude Code appends `[exited with code N]` as the capture's last line), for up to 5 further reads. Each read is a fresh tool call and that round-trip is the only spacing — do not insert a `sleep`, which this skill does not grant. **Both a marker with no parseable JSON and 5 reads without a marker are step 6's "no parseable result obtained" row.** `Keep in sync with crit-commit-review.md § Procedure step 4's background-capture re-read guard.` The decision comes from this stdout; the on-disk comments file (`.claude/plans/<slug>.plan-review.comments.json`, per § serve.mjs contract's derivation) is a durable side record that is **not** read here. The served file, the comments file, the URL file (`.plan-review.url`), and the prev snapshot (`.plan-review.prev.md`) are workflow artifacts covered by `SKILL.md` § Workflow artifacts (cross-step fixed exclusion) — excluded from Step 10 commits automatically (no `.gitignore` entry needed).

6. **Decision mapping.** Evaluate the parsed result in order (first match wins):
   - **Non-zero exit** (`124` timeout — fires only after the cap elapses (default 24h), never with `--timeout 0`; `130` SIGINT / SIGTERM; `1` startup error) — or no parseable result obtained — → return **`fallback`** to Step 4.
   - **`decision: "approve"`** → maps to Step 4's `accept`. Any accompanying `comments` are **advisory only** — record them but do not block on them (the user chose approve). Return **`approve`** to Step 4 with no write of any kind — the canonical `.claude/plans/<slug>.md` is already the approved plan — the browser submit is itself the final confirmation, so Step 4 proceeds directly to implementation.
   - **`decision: "revise"`** → apply the block comments **to the source the commented block came from**, never to the served file (which the next launch's compose rebuilds): a comment on plan prose lands in the canonical plan document `.claude/plans/<slug>.md`, and a comment on a figure lands in the figures file `.claude/plans/<slug>.figures.md`. Route each comment by which side its `excerpt` matches — a figure's `excerpt` is its caption or its rendered label text, so a match there sends the comment to the figures file; anything else is prose. A comment whose body asks for both — a figure change and the prose it sits beside — is applied to both. For each comment, map its `block` id to the corresponding part of the plan and apply the requested change autonomously (same discipline as Step 3 finding application — the user's block comments are the review):
     - **Block-id resolution**: `decision-<n>` → the n-th Decision item; `<section-slug>::<n>` → the n-th commentable block within that section. **Resolve by the `excerpt` first**: it is a whitespace-normalized, ≤40-char prefix of the commented block's text, so locate the block whose leading text matches it after the same normalization (collapse runs of whitespace, then compare the prefix) rather than requiring an exact substring match. Treat the numeric index (`<n>`) as a secondary, advisory hint only — never rely on the index alone.
     - **"Switch to alternative" comments**: a Decision card's toggle emits a comment on `decision-<n>` whose `body` is the fixed switch instruction (`この Decision を Alternative に切り替える` for `lang: ja` / `Switch this decision to its Alternative` for `lang: en`, optionally followed by free-text). Treat it as a **bounded Recommendation/Alternative swap** on that Decision: swap the item's Recommendation and Alternative in the canonical plan document and propagate the dependent updates (Approach / Risks / Scope / Test-plan sweep) exactly as the text-path swap-decisions bucket does (see `SKILL.md` Step 4's swap-decisions handling). When the `body` carries free-text beyond the fixed switch sentence (the portion after that sentence), apply **both legs**: perform the swap first, then apply that trailing portion as an ordinary revise instruction on the same Decision — the swap is not a license to drop the rest of the comment. Omit the text-path read-back sub-step here.
     This comment-application happens for **every** `revise` submit, before and regardless of the branch below. Then branch on the nature of the (already-applied) changes:
     - **Zero applied changes (revise with no comments)**: the `comments` array was empty — nothing was applied to either source. **Re-launch the gate** (loop back to step 4); its compose takes the prev snapshot on the way (§ Prev snapshot), so the re-launch still passes `--prev`.
     - **Approach-level material change** (a new overall approach, a scope change — same vocabulary as Step 4's `rewrite-approach` bucket: "Approach / Build order / Scope-level material change"): do **not** loop the gate. Return **`rewrite-approach`** to Step 4 — the canonical plan document already carries the applied comments, so the re-review sees the current plan with no write-back needed, which re-opens Step 3, re-reviews the plan, and re-enters Step 4 from sub-step 1 (Step 4's rewrite-approach handling names an exception when the plan phase is held off by the run mode — `run_mode == "fast"` — see its "Exception — the plan phase held off by the run mode" clause). (On re-entry the reachability probe re-runs; if the browser is still reachable, the gate re-runs on the re-reviewed plan.)
     - **Localized edits** (wording, a single Decision tweak, a bounded Recommendation/Alternative swap, a bounded section edit): **re-launch the gate** (loop back to step 4) — the edits already landed in the canonical document, and the compose rebuilds the served file from it. Step 3 is not re-run for localized revise. The loop is human-paced — each iteration blocks on a fresh browser submit, so no machine iteration cap applies. A closed browser does **not** by itself end the gate (the server keeps waiting); the gate exits via `fallback` only on the timeout cap (default 24h, never with `--timeout 0`), a SIGINT / SIGTERM, or a startup error (the non-zero-exit row above).

7. **Fallback contract.** Return **`fallback`** to Step 4 on any of: local browser unreachable (`CLAUDE_CODE_REMOTE="true"`, step 2), non-zero serve.mjs exit, a startup / launch failure, or the launch Bash call being blocked / yielding no result. Step 4 then continues with its **chat approval** (sub-step 2's "Chat approval" bullet): the chat-rendered condensed plan → preamble → guidance line → a pointer to `.claude/plans/<slug>.md` → wait for the user's chat reply.
