# Crit gate

Read from `commits.md` § Procedure at Interactive Commits, and from `mob-mode.md` § Per-unit review at Implement. The probe, the launch, and the `approved:` reading below apply to both. So does the split between a `scope: "line"` comment, applied as an edit, and a `scope: "review"` body, answered as a reply. The candidate derivation, the story, the landing, and the routing of a reply through `commits.md` § Approval tokens are for the commit gate only: a unit review's range is `<prev>..<snapshot>`, it attaches no story, and `mob-mode.md` § Per-unit review governs what its verdict means.

crit (https://github.com/tomasz-tomczyk/crit) is a locally installed browser diff reviewer. Probe once per run: `crit --version` and `printenv CLAUDE_CODE_REMOTE`. If crit is missing or the session is remote, the whole run uses the chat presentation with one note (the install URL, or "no local browser").

Per commit: on the chain path the candidate is the chain commit itself and `<parent>` = `<commit>^` (not HEAD, whose re-created commits are not the chain's ancestors), or `<S_k>` when mob mode presents the post-review delta. On the cohesion path `<parent>` = `git rev-parse HEAD`; build the candidate without landing: `git write-tree` on the staged group, then `git commit-tree <tree> -p <parent>` with the subject and body on stdin. Then attach the **story**, which carries the body the browser never shows:

1. `crit story --range <parent>..<candidate> --prep /dev/stdout` lists the hunks; each `--- (<file_path>, <old_start>) [<status>]` line is one hunk id (`old_start` is `0` for a new file).
2. `crit story --range <parent>..<candidate> --story-file - --refresh --no-open <<'STORY' … STORY` ingests crit's JSON. Take every field's shape from `crit story --guide`, which prints the schema this build accepts, rather than from memory — a guessed shape is rejected on ingest. What goes where: `prologue` from the subject and the body, `chapters` grouping hunks by theme (one or two per commit), `support` for mechanical hunks (lockfiles, generated output, version bumps) with a `reason`. Every hunk goes in a chapter or in `support`; prose follows the resolved language. Reuse the first round's wording on later rounds while the subject and body are unchanged; re-derive only the hunk references.

A story failure is non-fatal. On a non-zero exit whose report names hunks by id, correct those hunks' placement across the story's chapters and `support`, and retry once; nothing else is retried. `"auto_repaired": true` is not a failure. On failure say so in one line with the last stderr line (≤ 80 chars) and launch without the story.

Run `crit --range <parent>..<candidate>` in background Bash with a status line. When either attempt of the story ingest printed `Started` or `Restarted crit daemon at <url>` on stdout or stderr, add `--no-open` to the `crit --range` command and put that URL in the status line. Read stdout and stderr for the literal line `approved: true` or `approved: false` (both exit 0). The review is over only when one of those lines has appeared or the process exited non-zero; output without either line means the review is still open, even after a completion notice — re-read up to 5 times before treating it as broken, and never stop the daemon during the run. `true` → land per `commits.md` § Procedure's accept. `false` with no comments → same candidate, new round. `false` with comments → apply the `scope: "line"` comments as edits (or refuse the ones that would change a landed commit), run `check_commands` once if anything changed, then treat each `scope: "review"` body as a typed reply through `commits.md` § Approval tokens (cancel wins over adjust over accept); the commit stays pending and is rebuilt and re-reviewed. No parseable line or a non-zero exit → chat presentation for this commit only; crit stays enabled for the next.
