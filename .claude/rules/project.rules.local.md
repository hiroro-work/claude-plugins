# Project Rules - Local (Conversation-Extracted)

会話から抽出した、このリポジトリ固有の規範。他のプロジェクトへ持ち出せる原則は `project.rules.md` に置く。各項目には規範・発動する場面・見分け方だけを書き、実例は `../rules-extras/project.rules.examples.md` に置く。

## Project-specific patterns

- **`jq` の `null` 文字列フォールバック**: `jq` はキーやエントリが無いと文字列 `null` を出して正常終了するので、`|| echo unknown` は効かない。filter 内の `// "unknown"` と、パイプラインの後の `[ -z "$value" ] && value="unknown"` を両方置く。値を書く側と読む側の両方に適用する
- **パイプの先のコマンドも `allowed-tools` に載せる。載せたくないならパイプを外す**: SKILL.md の手順が `git ... | grep` や `| wc -l` のように出力を別のコマンドへ流すと、そのコマンドが許可されていない環境では確認ダイアログで止まる。許可を広げるより依存を外す。行数や一致の判定は、コマンドの出力を直接読んでエージェント側で行う。ガードが呼ぶ git のサブコマンド（`git switch` / `git remote show` / `git symbolic-ref` / `git merge-base` など）は外せないので `allowed-tools` に書く
- **detached HEAD を事前に検出する**: ブランチを操作するルーチンでは、事前チェックで `git symbolic-ref -q HEAD >/dev/null` が 0 以外で終わったら detached HEAD として早めに中止する。`git rev-parse --abbrev-ref HEAD` は detached HEAD で文字列 `HEAD` を返すので、単独では使えない
- **0 件になりうる glob は必ずクォートする**: この repo の shell スニペットは zsh（macOS の既定）で動く。zsh の `nomatch` は一致が無いとコマンドを実行せずに中断し、ルーチンがそこで無言で止まる。refspec に限らず、glob を含む引数は全てクォートする。bash でもクォートを勧める
- **複数行の結果は `while IFS= read -r` で回す**: zsh はクォートしない変数を語分割しないので、`for x in $var` は全体を 1 要素として 1 回しか回らない（bash は分割するので複数回回る）。`printf '%s\n' "$var" | while IFS= read -r x; do ...; done` か `while IFS= read -r x; do ...; done <<< "$var"` を使う。`setopt shwordsplit` には頼らない
- **変更の集合は一度だけ、特殊なファイル名でも崩れない形で集める**: `git status --porcelain=v1 --untracked-files=all -z` を手順の冒頭で 1 回実行し、結果を使い回す（`=v1` で書式を固定し、`-z` で NUL 区切りにして引用符付けを抑える）。`git diff <base>` は未追跡のファイルを含まないので、追跡済みは `git diff`、未追跡は `Read` で新規ファイルの差分を作り、`??` で見分ける
- **コミットは pathspec で範囲を絞る**: ステージは `git add -- "<f1>" "<f2>" ...` を 1 回で行い、`-A` や `git add .` は使わない（無関係な変更が入る）。Stop hook が未追跡のファイルを自動でステージする環境もあるので、コミットも `git commit -m <msg> -- <path-1> ...` の形で絞る（`-m` は `--` の前）。作業用の文書の除外は `.gitignore` でなく pathspec で行う。gitignore にするとチームで共有するプランが消える
- **記録用コミットは決まったファイルだけに絞る**: バージョンと CHANGELOG の記録用コミットの pathspec は `.claude-plugin/marketplace.json` と `CHANGELOG.md` だけにする。作業ツリーには無関係なユーザーの編集や作業の成果物が混じりうるので、集める段階で見分けて全コミットから外し、コミット計画に「除外: …」と書く。混入したら `git commit --amend -- <その 2 ファイル>` で直す
- **外部コマンドの失敗は 1 回だけ再試行し、自動で復旧しない**: `git push` / `gh api` / `curl` などが失敗したら、1〜2 秒待って 1 回だけ再試行する（決まって失敗するものは再試行では直らない）。`<reason>` には stderr の最後の空でない行を 80 字以内に切って入れ、空なら `(no stderr)` にする。`Do not auto-recover (no force push, no rebase, no branch rename)` と禁止を明記する。書かないと LLM が rebase をでっち上げる
- **外部への副作用はルーチン自身が実行する**: 非対話のルーチンが `git push` などの外部への副作用を伴うなら、「セッションの終了処理に任せる」と書かない。ルーチン自身が 1 回の実行につき 1 か所（後片付けの判定の後、要約の直前）で実行し、`allowed-tools` に追加し、セッション単位の規則と衝突する事情と禁止事項を明記する
- **既存の列挙値を増やさず、基準を厳しくする**: 新しい場合を扱うとき、新しい判定値を作らず、既存の基準を厳しくする（複数条件の AND に具体化するなど）。値を増やすと下流のパーサや対応表を全て直すことになり、後方互換も崩れる
- **分岐の振る舞いは否定でなく全列挙で書く**: 「A と同じだが X を除く」の形は見えない穴を作る。両方に共通する動作を「Full <set-name> (applies to both <A> and <B>)」として上に置き、分岐ごとの差分だけを下に列挙する。エラーの種類ごとの共通の更新も全て列挙する。1 か所で否定形を見つけたら、同じ SKILL.md の全分岐を見直す
- **前例の無い機能に頼る書き直しは実装前に試験する**: 前例の無いプラットフォーム機能（サブエージェントから `Skill()` を呼ぶ、`subagent_type` のツール構成、`allowed-tools` の継承など）に頼る大きな書き直しでは、Phase 6 (Implement) の前に行う Step 0 の試験を Test plan に入れる。必須の項目は 4 つ。実現できるか（PASS / FAIL）、ツールを継承するか、状態管理を模擬できるか、監査記録としての総合判定（READY / NEEDS-FALLBACK / BLOCKED）。表記は「必須 (Step 0 item #N)」に揃え、「推奨」とは書かない
- **呼び出し層と呼び出し先の失敗を別のカウンタで数える**: サブエージェント経由で呼び出し先スキルを動かす設計では、呼び出し層の失敗（呼び出しの失敗・判定の解釈失敗・スキーマ違反・ツールエラー）と、呼び出し先の失敗（呼び出し先の error 判定・反復の上限）を分けて数える。呼び出し層の失敗では、呼び出し先ごとの無効化カウンタを増やしも戻しもしない（呼び出し先は動いていない）。集計でも別の行に出す
- **順に呼ぶ複数の `Skill()` は 1 回の `Agent` にまとめる**: N 個の `Skill()` を順に呼ぶと停止しうる地点が N 個積み重なるなら、1 回の `Agent` にまとめ、集約した JSON を返させる。必須なのは、呼び出し先ごとのフィールドを入れ子にしたスキーマ、呼び出し層と呼び出し先の失敗の区別、Step 0 の試験での `subagent_type` の確認、サブエージェントのプロンプトに入れる「Do not run further `Skill()` dispatches beyond what is enumerated」の 4 つ
- **太字ラベルは `§ <Heading>'s "<label>" paragraph` の形で参照する**: 参照先が `### 見出し` でなく太字のラベルなら、`§ <Heading>'s "<bold-prose label>" paragraph` の形で、ラベルの文言をそのまま引用符で囲む。ラベルを書き換えるときは参照側も直す
- **値や手順を足すときは同期先を全て挙げて 1 コミットで直す**: 新しい値・メンバー・ゲートの追加や名前の変更では、一緒に直す箇所を全て列挙して 1 コミットで直す。書くのは、何が起点か、同期先の一覧（設定表や見出しを写している自スキルの README も含む）、`Edit` の直後の同期の確認（既存の箇所も含む）、参照側に置く `Source of truth: ...; keep in sync` の一文。一文には、どちらが正本かと、何が列挙に入るかの基準を例外まで含めて書く
- **grep で拾えない参照も洗い出す**: 名前を変えるときは、旧い概念の同義語・派生形・近い表現を grep で洗い出し、Test plan の直す対象に書く。振る舞いの変更や削除では、「〜と同じ挙動で動く」のような類推による参照を意味で探す。語は変わらないので grep では 0 件になる
- **承認の段階で大きな変更を求められたら、プランを 1 回で書き直す**: Phase 5 (Plan Approval) でユーザーが代替案の選択などを求めたら、Phase 4 (Plan Review) を通し直し、今回の実行が使った承認の場（ブラウザのゲート。それが使えなかった実行ではチャット）へ出し直す。書き直しは 1 回で行い、ユーザーの選択を Decisions に記録し、それに依存する Approach / Scope / Risks / Test plan / CHANGELOG の記述も同じ回で直す。部分的に直すとプランが膨らみ、決定が埋もれる
- **既存の選択肢を選び直すなら入れ替え、無かった選択なら新しい決定を足す**: Decisions に既にある選択の代替案をユーザーが選んだら、推奨と代替を入れ替え、新しい推奨に「user 既選択」と注記する。Decisions に無かった選択（典型は既定値）を求められたら、入れ替えずに Decision § (N+1) を足し、見出しに `**user 既選択: <value> — Phase 5 gate にて**` と書き、推奨をユーザーの選択、代替を元の暗黙の既定値にする。取り違えると元の構造が壊れる
- **Agent 定義の frontmatter に `allowed-tools` を書く**: `.claude/agents/<name>.md` に宣言が無いと、中で呼ぶ `Skill()` / `Agent` / `Bash(...)` が黙って失敗する。呼び出す `Skill(<name>)` を明記し、呼び出し先の `allowed-tools` を合わせて列挙し、`Bash(*)` は避ける
- **Agent 定義で `Skill(<callee>)` を許すなら、中身を直接実行しないよう書く**: `allowed-tools` に `Skill(<callee>)` を含めると、呼び出し先の SKILL.md がサブエージェントの文脈に入り、呼ばずに中身を直接実行してしまう。Agent 定義に `## Dispatch discipline` 節を設け、3 段落で繰り返す。「Each callee MUST be invoked via `Skill(<name>)`. Do not read, interpret, or replicate any callee's SKILL.md logic inline」、同じことの具体的な言い換え、呼び出し先の全件列挙による上限。呼び出し先の内部スキーマのフィールド名は書かない
- **識別用の照合は緩く、内容の検査は厳しくする**: 振り分けに使う識別フィールド（タイトルの書式や正規表現）と、判定に使う内容フィールド（列挙値や必須フィールド）が並ぶなら、前者を緩く後者を厳しくする。両方を厳しくすると、`1 finding` と `N findings` の違いや、末尾の定型行の有無のような揺れで黙って飛ばされる。事前に絞り込み済みなら書式の検査は要らず、残すなら `\d+ finding(s)?` のように緩めた形にする
- **全件条件の判定には全体の状態の条件も足す**: 「全ての Finding が閉じてよい」のような要素ごとの全称条件は、0 件で真になり、解釈失敗や中止の状態を同じ分岐に流してしまう。全体の状態の条件（解釈失敗でない、中止していない）と要素ごとの条件の AND にする
- **Step の番号を振り直すときは、機械置換と個別の上書きを分け、2 段階の grep で確かめる**: まず単純に置換できる参照を一般規則として挙げる。機械的に置換すると意味を誤る箇所（旧い番号を前提にした相対表現、番号だけでは指す先が曖昧な参照）は行ごとに挙げて、置換後の文言を個別に決める。行番号は編集前の目安にとどめ、最後は見出しやフレーズで確かめる。`references/*.md` への波及は行ごとのチェックリストにする。最後の確認は、旧い見出しの語句の OR で grep して 0 件、変えた番号を単語境界で grep して残りを目で見る、の 2 段階
- **登録時に回数が決まらない反復は進捗管理ツールに 1 行で登録する**: 反復の回数がユーザーの承認しだいで登録時に決まらない Step は、反復ごとの行に展開せず 1 行で登録する。未確定の数と途中での書き換えは、停止しうる地点を増やす。登録箇所に `(single row — per-X iteration is handled inline within Step N because the X count is not known until <ref>)` と注記する。登録時に回数が決まっているなら反復ごとに展開してよい
- **カウンタは正常終了のときだけ増やす**: ループの開始で 0 にし、正常終了のときだけ 1 増やす。再試行・中止・失敗の経路では増やさず、`--amend` やコミットのやり直しでも増やさない。SKILL.md に「On zero exit, increment by 1」と「The amend ... is NOT re-incremented」を対にして書く
- **後段の振り分けは設定フラグでなくカウンタで決める**: `<counter> > 0` で振り分ける。設定フラグで振り分けると、`enabled: true` なのに飛ばされて 0 件になった場合を取り違える。`<counter> == 0` の側は「フラグが false」と「Step が飛ばされた」の 2 つの原因の和として書く。フラグとカウンタを組み合わせたくなったら、カウンタだけで表せないか先に考える
- **複数箇所から参照する語は 1 か所で定義する**: 言語別の文言・状態値・列挙の対応などは 1 か所で定義し、他は参照にする。描き直すと、正本を直したときにずれる（言語別の文言はとくに頻繁に変わる）。参照は「太字ラベルは `§ <Heading>'s "<label>" paragraph` の形で参照する」の書式に従う。描き直しの指摘を受けたら 1 か所へまとめる
- **暫定対処のスキルは既存ルーチンの 1 か所だけにつなぐ**: 暫定対処として作る開発用スキルを既存のルーチンに組み込むときは、外側の状態遷移・記録のスキーマ・カウンタ・進捗の行・停止防止の列挙には触れず、既存の小手順の境界に 1 段落だけ挿入し、削除の手順を SKILL.md に書く。分解の段階で「暫定 = 消す予定」とわかった時点で、深く組み込む案は退け、1 か所につなぐ案を推奨に立てる
- **検証が落ち続けるなら、検証でなく編集の範囲を広げる**: 検証スキルが落ち続ける原因の多くは、上流の編集が範囲を取りこぼしていること。検証を緩めたり、検出だけの確認を足したりせず、正本の編集の直後に同期の工程を足し、同期 → 検証の 2 段にする。自動適用で緩める側へ寄せると、構造的な漏れが隠れる
- **Setup モードでは `Write` の直前に不在を確かめ直す**: 設定ファイルが無いと判断した後も、テンプレートを `Write` する直前にもう一度 `Read` して不在を確かめる。間に別の処理が作ったファイルを上書きしないため。例: 「Before writing: re-confirm `.claude/<config>.local.md` does not exist ... If it now exists, abort Setup mode and report the conflict — never overwrite」
- **`Read` のエラーは既定で止める**: エラーが「存在しない」のか、権限や文字コードの問題なのかを確実に見分けられないなら、Setup モードへは見分けられたときだけ進み、見分けられなければエラーで止める。誤って分岐すると既存の設定を上書きする
- **テストが落ちたら、今回の変更のせいか元からかを見分ける**: TEST_FAILED になったら、今回の変更が入れた退行か、基準コミットの時点からあるものかを見分ける。`git stash` か基準の clone で同じテストを回し、同じ失敗なら元からある。テストが挙げたプラグインやスキルの名前と、変更したパスも突き合わせる。Phase 11 (Code Review) では「pre-existing failures (out of scope of this PR)」と書き、元からある失敗は直さない
- **戻り値の JSON を指示する文で終わりを命じない**: 呼び出し先では `End every invocation` / `Terminate` / `Do not produce any additional turn` のような終わりを命じる動詞を使わない。呼び出し元に「ターンを閉じろ」と読まれて止まる。`Emit a single fenced JSON block at the end of the response, matching the schema ...:` の形にし、独立した `## Sub-skill caller directive` 節に 3 点を書く。JSON は戻り値でありターンの区切りではないこと、同じエージェントがすぐ次のツール呼び出しを出すこと、JSON と次の呼び出しの間に散文や「shall I proceed?」を挟まないこと。JSON ブロックが 1 つだけであることも「Only one fenced JSON block」と書く。複数の呼び出し先に置くなら、スキル名を除いて文面を揃え、新規作成や編集のたびに終わりを命じる動詞を grep する。呼び出し元の注意書き（`project.rules.md` の「サブスキルの呼び出し直前と戻り点に注意書きを置く」）と必ず組にする
- **要素ごとの引数はループの入口で記録に固定する**: 要素ごとのループで要素固有の引数を複数の呼び出し先へ渡すとき、呼び出しのたびに元から逐語で計算し直すと、他の要素の値が混ざる重大な不具合や、言い換えによるずれが起きる。ループの入口の最初の小手順で、変更しない記録のフィールドに固定し、呼び出し先はその記録から読む。記録のスキーマに `Bound at (a) entry to verbatim text of <source field>` と書き、固定する手順に混入の警告を書く。引数の要らない呼び出し先は固定を飛ばすと明記し、実行ログにこのフィールドは出さない
- **コミットの承認ゲートでは本文をそのまま見せる**: コミットの本文は独立したコードブロックで表示する。「本文を含む」と散文で言うだけでは足りない。見せるのは、件名のブロック、本文のブロック（空なら `(no body)`）、ファイルの一覧、ファイルごとの差分の 4 つ
- **画面を持つ成果物は承認ゲートで実際の描画も見せる**: 利用者が目で見る出力を持つ UI は、差分や本文に加えて、ゲートを保留したまま実際の実行モードで描画を起動し、目で確かめて片付けてからゲートに戻る。作り物のプレビューでは代えない
- **ディスク上の差分が実装した内容とずれていたら、ユーザーに判断を仰ぐ**: Phase 6 (Implement) で適用した内容とディスク上の差分が違ったら、黙ってコミットせずに出どころを調べる（レビュー系フックが予期せず `Edit` を適用した可能性を疑う）。内容を評価し、残すか戻すかをユーザーに決めてもらう。残すなら独立に検証し直してから出し直す
- **しきい値の数値はプラットフォームの観測値に余裕の比率をかけて決める**: 実機で目に見える合図を観測し、その 80% を発火のしきい値にし、設定の説明に根拠・比率・バージョン依存を書く。新しい定数を入れるときに適用し、既存の既定値を設定から内部定数に移すだけの変更には適用しない。据え置いた既存の値に後から根拠を求める指摘は退けてよい
- **しきい値の無効化はフラグでなく大きな番兵値で表す**: 数値のしきい値に「無効にする」手段を用意するときは、無効化の真偽値フラグを足さず、`99999999` のような大きな値を設定すれば実質無効になる形にし、設定の説明にその方法を 1 行書く。フラグを足すと `enabled=false` と `threshold=N` の組み合わせの意味が曖昧になり、下流に真偽値の判定も増える
- **文書の大きさは文字数（`wc -m`）で測る**: バイト数（`wc -c`）では測らない。日本語を含むと大きくずれる。散文には単位「chars」を書き、変数名には `*_chars` を付ける
- **サブエージェントへの長いプロンプトは `references/<mode>-prompt.md` に置く**: 目安は 50 行以上。戻り値の JSON スキーマは SKILL.md に正本として残し、プロンプト本文を references にそのまま置き、SKILL.md の呼び出しの記述に「`--- LABEL ---` の区切りに references § <Section> をそのまま入れる」と書く。references の内容を SKILL.md に重複させない
- **直近に入れた試験的な機能のフラグは既定で無効にする**: 新しい設定フラグが直近のリリースの試験的な機能なら、兄弟の設定の既定が `true` でも既定を `false`（明示的に有効化）にする。当てはまるのは、直近の minor / patch で入った、実証実験の段階にある、無条件に動かすと想定外の副作用がありうる、のいずれか。プランでは早い段階で既定値を独立した Decision に立て、推奨を明示的な有効化、代替を兄弟との一貫性にする。CHANGELOG の 1 行目は `**Default: disabled** — set \`<flag>: true\` in \`<config-path>\` to opt in per project` にし、前の版で無条件に動いていたなら末尾に「**Behavior change from v<prior>**: ...must explicitly set \`<flag>: true\`」を添える
- **今回の実行の後続の工程で試せる変更は、その場で検証する**: 新しい既定値が今回の実行の後続の Step で自然に使われる変更では、Test plan の検証を手作業でなく「今回の実行で自然に試す」にする。Test plan に「`<config-file>` に新しいフラグを書かない → 新しい既定値 → 今回の Step N が飛ばす経路を通る」と 1 行書き、`.claude/<config-file>.md` への明示的な追加は別の作業として範囲外に置く（書くと検証の機会が消える）。このリポジトリで実際に使うスキルにだけ使える。使えないなら従来どおり手作業で確かめる
- **意図して受け入れた状態は Risks でなく Context に書く**: Decisions で意図的に受け入れた状態は Context に書く。Risks は想定外で手当てが要る不確実性、Context は設計判断の自然な帰結。混ぜると本当の不確実性が埋もれ、次のレビューで「リスクなのか受け入れ済みなのか」と再び指摘される。見分け方は「次のレビューでもリスクと書き続けるか」。書き方は「**<状態名>**: <Decision N> の自然帰結。<解消の手段か受け入れる理由>」
- **不自然な言い回しは、まず既存の言い回しに揃える**: SKILL.md や references の言い回しに違和感があるときは、同じファイルや兄弟スキルの既存の表現を探して揃えるのを第一候補にする。新しい表現を作ると、兄弟との不整合、呼び出し元の意味検査の拡張、レビューでの再指摘を招く。指摘を受けたら、まず同じファイルを grep する
- **起動時に決まる読み込みの挙動は、再起動して確かめる**: `.claude/rules/**` の再帰的な自動読み込みの範囲のように、セッション起動時にローダーが決める挙動に頼る変更では、一次情報が無ければ観測に基づく仮定として扱う。実行中には確かめられないので、Test plan に「コミットの後・push の前に手元で Claude Code を再起動して確かめる」と 1 行足し、Risks に「ローダーの仕様は観測に基づく」「一次情報は未確認」と書いて、後で経過を追えるようにする。「今回の実行の後続の工程で試せる変更は、その場で検証する」は当てはまらない。`.claude/rules/**` への配置、`paths:` frontmatter、出力先が自動読み込みの対象かの判断がこれにあたる
- **SKILL.md の節を references へ移すときは、節ラベルと実行時に参照される定義を残す**: 移す先には本文を逐語でコピーし、SKILL.md には元の節ラベルと委譲先を指す 1 行を残す（ラベルごと消すとリポジトリ中の参照が切れる）。実行時に参照される定義（Step をまたぐ状態変数の初期化、全件の列挙、入る条件と飛ばす条件、USER GATE の宣言）は SKILL.md に残す。見分け方は「飛ばす経路でも値が定まっている必要があるか」「他の Step がその定義を直接読むか」で、どちらかが Yes なら残す
- **工程の入口で必ず読む phase ファイルへは、定義ごと移してよい**: 連続する複数の節をまとめて 1 つの `references/*.md` へ移し、読み込みを手前の工程境界にある無条件の `Read` 1 か所に集めるなら、移した定義はその場にあるものとして扱える。条件は 4 つ。読み込みが条件分岐の手前にあり、読み込む節自身にも無条件に入ること（節の登録や到達が設定しだいなら、必ず入る地点まで読み込みを前へ出す）。移した定義を参照するものと更新するものの両方が境界より後でしか動かないこと（読む側だけを見ると、前の工程が書き足す変数の初期化まで移してしまう）。元の節ラベルと委譲先を残すこと。文脈の圧縮後に読み直す経路を用意すること（移すものに USER GATE の宣言や判定用の全件列挙が多いほど効く）
- **全件の列挙を分けるときは、どちらに足すかの基準も書く**: 節を references へ移すのに伴って全件の列挙を 2 つのファイルに分けるなら、本体側に「残りは <file> § <節> にある」と述べる項目を 1 つ置き、両方を合わせて全件であると示す。その項目には、新しい項目をどちらに足すかの基準を、節の列挙でなく分けた根拠（境界や条件）で書く。基準が無いと、次に編集する人が両方に足すか、どちらにも足さない
- **SKILL.md の節を references へ移すときは、修飾の無い `§` 参照の解決先を冒頭で宣言する**: 移した本文は元のファイルの視点で書かれているので、`§ <見出し>` や `sub-step N` が移した先と元のどちらを指すか決まらない。冒頭の段落で既定の解決先を書くか、外を指す参照だけを列挙する。元のファイルの視点の参照を持たない共有定義のファイルには要らない
- **「別の場所に記録済み」を理由に消す前に、その場所が追跡されているか確かめる**: 同じ内容が別の場所にあることを削除や重複回避の根拠にするなら、先にその場所が git で追跡されているか確かめる。`.claude/plans/` はディレクトリごと gitignore されているので、そこに設計の根拠があっても削除の理由にならない（新しく clone すると存在しない）
- **コミットする文書から gitignore 対象のパスを名指ししない**: `CHANGELOG.md` や配布される `SKILL.md` / `references/*.md` から、gitignore 対象のパスを名指ししない。参照が解決しないうえ、手元だけの構成を不必要に見せる
- **CHANGELOG には何が変わったかと判断に使う理由までを書く**: 検討の経緯、採らなかった案との比較、内部の導出の過程は書かない。詳しい背景はプラン文書や PR 本文に残す
- **共有の reference へ切り出したら、全ての呼び出し元を委譲先の 1 行まで畳み、読み込み量を測り直す**: 呼び出し元に手続きの書き直しを残すと二重管理になり、実際にずれる。切り出すだけでは新しいファイルの読み込みが全ての呼び出し元に加わるので、実行あたりの読み込み量は増える方向に動く。畳んだ後に `wc -m` で測り直し、増えた分が残るなら受け入れる判断として記録する
- **実行時に参照されない散文をスキルに書かない**: SKILL.md 本体と `references/*.md` の両方が対象で、どちらも起動ごとに読まれる。変更の根拠、採らなかった案、設計の経緯、規約が割れている事実、兄弟ファイルに何が書いてあるか、はどれもエージェントの動作を変えないので書かない。記録するならコミットメッセージか PR 本文、または追跡されている `README.md` に書く。根拠のためだけの reference は作らない（同期先が増え、bundle メンバーでは正本とコピーの両方に増える）。別の規則が「記録を残せ」と求めていても、それはどこかに記録があることの要求で、スキル本文に置くことの要求ではない
