# Project Rules - Local (Conversation-Extracted)

このファイルは `--from-conversation` で抽出された project-specific patterns を保持する `.local.md` です。`project.rules.md` の Principles と分離して、organizational rule sharing 時に portable な Principles のみを promote できるよう運用しています。

各項目には規範・発動条件・判断軸だけを置き、実例は書かない。

## Project-specific patterns

- **`jq` の `null` 文字列フォールバック**: `jq` は entry / key 不在時に literal `null\n` を **zero exit** で出すため `|| echo unknown` は発火しない。filter 内 `// "unknown"` + post-pipeline `[ -z "$value" ] && value="unknown"` の 2 段構えにする。producer / consumer の両側に適用する
- **SKILL.md の手続きが起動するコマンドはパイプの各バイナリまで `allowed-tools` に載せる。載せたくないならパイプ自体を落とす**: `git ... | grep` / `| wc -l` / `| awk` のように出力を外部バイナリへ流すと、そのバイナリが grant されていない環境で permission dialog に当たって停止する。canonical fix は **grant を広げるのでなく依存自体を除去**する — 行数カウントや pattern 抽出はコマンド出力をそのまま読んで agent 側で判定し、pipe を落とす。判断軸は「この集計・走査は外部バイナリ無しで agent 内でできるか」。ガードが呼ぶ git サブコマンド自体（`git switch` / `git remote show` / `git symbolic-ref` / `git merge-base` 等）は除去できないので `allowed-tools` に宣言する
- **detached HEAD ガード**: branch 操作を伴う routine では Pre-flight に `git symbolic-ref -q HEAD >/dev/null` の non-zero exit で detached HEAD を検出し early abort。`git rev-parse --abbrev-ref HEAD` は detached HEAD で literal `HEAD` を返すため単独では使えない
- **Run-level invariant の Pre-flight への hoist**: per-Finding / per-iteration loop 内で同一値を毎回 resolve している場合は Step 1 Pre-flight に hoist してキャッシュする。producer / consumer の両側を hoist する
- **disposition enum 拡張ではなく既存 enum の厳格化**: 新 case 追加時は新 disposition value を発明せず、**既存 criteria の厳格化**（複数条件の AND test への具体化等）を優先する。enum 増加は downstream parser / mapping table の全 update と後方互換性の崩壊を招く
- **Run-level 失敗系は per-Finding edge-case 表に混ぜない**: pre-flight 失敗（loop 外）と per-Finding edge-case（loop 内）は semantics scope が違うため節を分ける。前者は SKILL.md Pre-flight で手続き的に記述し、reference 側 edge-case 表には載せない
- **Step 6 Simplify の rationale 段落は配布スキルでも brevity を保つ**: subtle behavior の rationale は技術的に正確でも段落が膨らみやすい（100 words 級になりがち）。Simplify-revival check と同時に rationale の分量も見る
- **Branch behavior は completion で specify する（negation 禁止）**: 「branch A と同じだが X を除く」型の negation は hidden gap を作る。canonical 2 階層: (i) **Full <set-name> (applies to both <A> and <B>)** の shared block、(ii) branch-specific actions で差分のみ。error class の shared updates も by-completion の explicit list。1 箇所で negation を見つけたら同 SKILL.md 内の全分岐を sweep する
- **Pre-implementation smoke test (Step 0) for undocumented platform capabilities**: 前例のない platform capability（`Skill()` を subagent から呼び出す / `subagent_type` の tool set / allowed-tools 継承等）に依存する architectural rewrite は、Step 5 前に Step 0 smoke test phase を Test plan に組み込む。必須項目: (i) feasibility PASS/FAIL、(ii) tool inheritance、(iii) state-management simulation、(iv) audit-trail (READY/NEEDS-FALLBACK/BLOCKED)。wording は「必須 (Step 0 item #N)」で統一する（「推奨」表記は不可）
- **Dispatch-layer health と callee-layer health の counter 分離**: subagent dispatch 経由で callee skills を呼ぶ設計では (i) dispatch-layer error（dispatch 失敗 / verdict parse / schema violation / tool error）と (ii) callee-layer error（callee error verdict / max-iter）で counter を分ける。dispatch-layer error path は per-callee disable counter を increment も reset もしない（callee は走っていない）。aggregate は 2 layer を別行で render し observability axis の直交を保つ
- **Sequential N-callee orchestration を 1 Agent dispatch に集約する architectural pattern**: N 個の sequential `Skill()` で N 個の stall surface が積む場合、1 `Agent` dispatch に集約して aggregate JSON を返す。必須: (i) aggregate JSON schema が per-callee field を nest、(ii) dispatch-layer error class を callee-layer から分離、(iii) `subagent_type` を Step 0 smoke test で確認、(iv) subagent prompt に「Do not run further `Skill()` dispatches beyond what is enumerated」を入れて内部の stall surface も bound する
- **Routing-field entry shape validation extension** (class-level extension of `Edit` old_string validation rule): entry shape validation は `Edit` の `old_string` だけでなく **downstream tool call が dereference する全フィールド**に拡張する。parse 段階の schema-violation check で全 routing field を non-empty string 検査する
- **Bold-prose label cross-reference style** (specialization of stable heading reference rule): 参照先が `### Heading` でなく bold-prose label の場合、`§ <Heading>'s "<bold-prose label>" paragraph` 形式で bold 内文言を verbatim に囲み込む。bold label を書き換えるときは参照側も同期する
- **Coordinated multi-site sweep on extension/addition**: 新しい値・member・gate・rename token の追加は、coordinated site 全てを closed list で enumerate し 1 commit 内で sweep する。
  **canonical 形**: (i) trigger 明示、(ii) 同期 site 列挙、(iii) 1 commit atomicity、(iv) Edit 直後の同期 audit（pre-existing instance も sweep）、(v) reference 側に `Source of truth: ...; keep in sync` directive — **権威方向とメンバーシップ基準の両方を書く**（基準は carve-out まで含める）。
  **同期先の列挙には自スキルの README も含める**（設定表や節見出しを README が写している場合、列挙漏れがそのまま取り残しになる）。
  **bundle plugin に新メンバーを足す場合の closed list は 4 + 1 leg**: marketplace.json の 4 edit（新 skill plugin entry の append / bundle `skills` array への append / bundle `description` 追記 / bundle `version` の paired bump）に加え、新メンバー `SKILL.md` への横断ディレクティブ `## Dispatch authorization` 同梱。`Source of truth`: 4 edit は本項目、+1 leg は `project.rules.md` § プラグイン構造 の「**bundle 全メンバーに複製する横断ディレクティブは byte-identical を保ち、メンバー追加時に必ず同梱する**」bullet。両者を keep in sync。
  **新しい user-gate を足す場合の同期先**: SKILL.md `§ No-Stall Principle` の gate 列挙、`references/plan-format.md` § User-gate summary preamble の **Applies to:** と **Content slots**、および Test plan の sweep target。
  **rename では旧概念の同義語・派生形・隣接表現も grep で炙り出して Test plan の sweep target に明記する**。
  **挙動変更・削除の diff では、類推参照（「〜と同じ挙動で動く」）を意味で sweep する** — token が不変なので lexical grep は 0 hit になる
- **Plan rewrite triggered by user material change at Step 4 gate (+ swap / insertion specializations)**: Step 4 で user が Alternative 選択等を要求したら、Step 3 の再 review を経て、今回の実行が到達した承認面（visual ゲート、縮退していればチャット）へ再提示する。手順 1 pass: Title から旧 approach 語句を削除、Context / Goal / Approach 置換、Risks 完全置換、Decisions § N に user 既選択を記録。**Swap-direction**（Alternative 選択）: R / A の position swap + 新 R に「user 既選択」annotation + Risks / CHANGELOG note / Approach / Scope / Test plan を sweep。**Insertion-direction**（Decisions に無い choice — 典型は default value）: swap でなく **新 Decision § (N+1) を insert**、見出しに `**user 既選択: <value> — Step 4 gate にて**` annotation、R = user 選択 / A = 元の暗黙 default、Approach / Scope / Test plan / Risks / CHANGELOG を新 default の文脈で sweep する。swap と insertion を混同すると元の structure が壊れる。partial rewrite は plan 肥大化と buried decisions を招く
- **Routine-side action ownership over environment-finalization delegation**: 非対話 routine が外部副作用（`git push` 等）を伴う場合、「session finalization に委譲」と宣言しない。canonical: routine 自身が once per run で実行し（単一箇所、cleanup 判定後 / summary 直前）、`allowed-tools` に glob を追加し、session-level rule との conflict 文脈と禁止条項を明記する
- **Closed form-set invariant for multi-form summary tokens**: SKILL.md summary line の render form 数は closed list として bounded に保つ（3 以下程度）。partial-failure / cleanup 中断は新 form でなく別 warning line に分離する。SKILL.md prose に「form set stays closed at <N>」と明示し、class-level extension audit の対象を明確にする
- **External-command failure: retry once + stderr-derived `<reason>` + no auto-recovery**: 外部 CLI（`git push` / `gh api` / `curl`）失敗の canonical pattern 3 点: (i) **retry 1 回のみ + 1–2 sec sleep**（指数バックオフは over-spec、deterministic failure は retry で改善しない）、(ii) **`<reason>` は stderr 最終 non-empty 行を ≤ 80 文字で truncate**、empty なら `(no stderr)`、(iii) **auto-recovery 明示禁止**（`Do not auto-recover (no force push, no rebase, no branch rename)` — 禁止文言なしだと LLM が rebase を hallucinate する）。retry の rationale 段落は Simplify で削除されるため prose に残さない
- **Mis-justification audit when citing infrastructure mechanisms**: 設計制約を別 mechanism の挙動で justify する場合、引用先の実挙動を一次情報で確認し、誤りなら design intent ベースに書き換える
- **Cross-section rendering-authority pointer (computed-here / rendered-there)**: 「section A で compute、section B で render」の設計では、両 section に明示的な相互参照ポインタを置き、実行順と rendering 担当範囲が両側から読めるようにする
- **Agent definition (`.claude/agents/<name>.md`) discipline (2-clause)**: (i) **Frontmatter `allowed-tools` requirement** — 宣言なしだと nested dispatch (`Skill()` / `Agent` / `Bash(...)`) が silent fail する。canonical: callee `Skill(<name>)` を明示、callee の `allowed-tools` を union で列挙、`Bash(*)` は避ける。(ii) **Subagent inline-execution prohibition** — agent の `allowed-tools` に `Skill(<callee>)` を含めると callee SKILL.md が subagent context に injected され、subagent が dispatch せず inline 再実行する failure mode がある。canonical mitigation: agent 定義に `## Dispatch discipline` 節を新設し 3 段落の reinforcement-by-repetition を置く — (i) MUST 宣言「Each callee MUST be invoked via `Skill(<name>)`. Do not read, interpret, or replicate any callee's SKILL.md logic inline」、(ii) concrete restatement、(iii) closed-list bound。anti-pattern: callee 内部スキーマの field 名を agent prose に書くこと
- **Routing-identifier permissive / content strict layering**: routing identifier fields（title format / regex）と judgment 用 content fields（enum / required fields）が併存する場合、**identifier permissive / content strict** に分離する。両 layer を strict にすると grammar 揺れ（`1 finding` vs `N findings`、trailer の有無）で silent skip の regression が出る。判断軸: 事前フィルタ済みなら format check は不要、保持するなら permissive form（`\d+ finding(s)?`）にし content strict は維持する
- **Vacuous-truth gap in per-element ALL-quantifier close predicates**: per-element の ALL-quantifier（`every Finding is OK to close`）は zero records で vacuously true になり、parse-error / dispatch-aborted の whole-state を silently 同じ分岐として扱ってしまう。canonical は 2-leg AND predicate: (i) whole-state gate（not parse-error, not aborted）AND (ii) per-element check
- **Step renumbering propagation in SKILL.md (mechanical sweep + individual overrides + 2-stage grep audit)**: 2 階層で設計する — (i) **Generic rule** で単純置換群を列挙、(ii) **Individual overrides** で意味的に誤りになる箇所を line 別に列挙（`Runs after Step N` が新番号で hook 自体が Step N になるケースは `Runs as Step N (immediately after Step N-1)` に、`Step 9 transition` は `Step 9 (Completion Hooks) transition` で disambiguate）。line 番号は pre-edit の reference に留め、最終確認は phrase / heading anchor で行う。`references/*.md` への波及は line-by-line checklist にする。**最終 audit は 2 段階 grep**: (1) phrase-pair-only grep（旧 heading 句の OR）で 0 hit、(2) bare number への word-boundary grep（`\b(Step 9|Step 9\.5|Step 10)\b`）で残り hit を目視
- **TodoWrite single-row for unknown sub-iteration count at registration time**: sub-iteration の数が user-approval 依存で登録時点に確定しない Step は、per-iteration row に展開せず single row で登録する（未確定の M と mid-flight 書き換えは stall surface を増やす）。登録箇所に `(single row — per-X iteration is handled inline within Step N because the X count is not known until <ref>)` と annotation する。登録時点で確定している Step は per-iter 展開してよい — 両 pattern を混同しない
- **Multi-form gate vocabulary disambiguation in § No-Stall Principle enumeration**: 1 Step が taxonomy の異なる複数 user-gate を持つ場合、gate ごとに別 bullet で列挙する（merge 禁止）。各 bullet は canonical token classifier の定義段落を `§ Step <N>'s "<paragraph label>" paragraph` で参照する。conflate すると enum を取り違える
- **Filename-robust git collection + per-commit pathspec scoping for Step 10 / commit flows**: canonical form は `git status --porcelain=v1 --untracked-files=all -z`（`=v1` で format pin / user config override を防ぎ、`-z` で NUL 区切りにして C-quoting を抑制）。**Untracked Read fallback**: `git diff <base>` は untracked を含まないため、tracked は `git diff`、untracked は `Read` で new-file hunk を作り、`??` prefix を discriminator にする。Procedure 冒頭で once 実行して in-memory で reuse する。**Multi-pathspec single call**: `git add -- "<f1>" "<f2>" ...` で一括、`-A` / `git add .` は禁止（unrelated drift を staging する）。**Stop-hook auto-stages**: 環境によっては Stop hook が untracked を auto-stage するため、各 commit を `git commit -m <msg> -- <path-1> ...` で pathspec scope する（`-m` は `--` より前）。staging 文書は `.gitignore` でなく commit pathspec で scope-out する（gitignore は team-shared plan を消す）。**bookkeeping / release commit は closed set に厳密 scope**: version bump + CHANGELOG の bookkeeping コミットの pathspec は **`.claude-plugin/marketplace.json` と `CHANGELOG.md` のみ**に限定する。collect が拾う working tree には無関係な user 編集や workflow artifact が混在しうるので、collect 段で識別して全コミット（bookkeeping 含む）から除外し、commit-plan に「除外: …」と明示する。混入時は `git commit --amend -- <正しい closed set のみ>` で直す
- **Counter lifecycle + counter-based routing (zero-exit-only increment + amend exclusion + actuality routing)**: counter の lifecycle 4 点: loop 開始で 0 init、zero exit 時のみ +1、retry / abort / failed path では increment しない、`--amend` / re-commit で再 increment しない。SKILL.md に「On zero exit, increment by 1」「The amend ... is NOT re-incremented」を symmetric に明示する。**Downstream routing は config-flag でなく counter で行う**: `<counter> > 0` で routing する（config-flag intent だと `enabled: true` × skip 条件で 0 件になる case を取り違える）。`<counter> == 0` 側は「flag が false だった」「Step が skip された」の 2 cause の OR union として書く。**dead flag より単一 counter**: boolean flag + counter の合成は、counter 単独で同等の semantics を表現できないか精査する
- **Token defined-once + cross-reference (re-render 禁止)**: 複数箇所から参照される token（localized / status / enum mapping）は 1 箇所で定義し、他箇所は cross-reference にする（re-render すると canonical 更新時に drift する。i18n token は wording 更新の頻度が高い）。cross-ref 構文は `Bold-prose label cross-reference style` の `§ <Heading>'s "<bold label>" paragraph` 形式。re-render の finding が出たら 1 source-of-truth に統合する
- **Temporary-workaround skill integration: single hook point over state-machine weave**: 暫定対処の project-local skill を既存 routine skill に組み込むときは、(i) outer state machine / record schema / counter / TodoWrite rows / No-Stall reminder enumeration に触れない、(ii) 既存 sub-step 境界に 1 段落だけ挿入する、(iii) deletion 手順を SKILL.md に明記する。Step 1 で「暫定 = 削除予定」と判明した時点で deep integration を early reject し、単一 hook point を Recommendation に立てる
- **Edit-induced false-positive: widen edit scope, not add detect-only check**: verification skill が持続的に fail するとき、root cause の多くは **upstream edit operation の scope incomplete**。fix 方向は (i) ❌ verification 側を fail-open にする、(ii) ❌ detect-only を足して conflict を cascade させる、(iii) ✅ **edit 側の scope を広げる**（canonical edit の直後に同期 phase を足し、phase 1 sync → phase 2 verify の 2 段構成にする）。auto-apply で fail-open 側へ寄せると structural な漏れを隠蔽する
- **Project-local skill placement, layout, and self-description**: 配布 skill と project-local skill は、レイアウトでなく **配置場所 + 登録の有無** で区別する（両者ともフラット）。判定軸: 配布性が必要 → `skills/<name>/SKILL.md` 配下 + `marketplace.json` 登録 + CHANGELOG ペア bump、project-local → `.claude/skills/<name>/SKILL.md` 配下 + 未登録 + CHANGELOG 対象外。**Self-description canonical phrasing**: canonical form は ``**project-local** skill (lives under `.claude/skills/<name>/`, not registered in `.claude-plugin/marketplace.json`)``。既存 sibling を `grep` して punctuation / 語順まで mirror する（prefix prose は不要 — fragment 形）。**Step 4 で明示 Decision（project-local → public-skill model switch）**: 両モデルは blast radius が異なるので Step 4 で明示 Decision に立て、bundle 化の要求が来たら Plan rewrite (insertion-direction) で新 Decision § (N+1) を立てて Approach / Scope / Test plan / Risks を bundle 文脈で sweep する。**Subtask split（skill creation vs caller wiring）**: subtask 1 = skill 単体の作成 / publish、subtask 2 = caller wiring + version bump の 2 分割にする（判断軸: 各 subtask 単独で構造検証と live exercise 検証ができるか。1 PR に統合すると bisect が困難で review surface も肥大する）。間の dead-on-arrival 期間は設計判断の自然帰結なので Context に明記して subtask 2 で解消し、subtask 1 の Test plan には「subtask 2 territory 非侵入確認」を sweep target として組み込む。**Globally-exposed project-local skill**: repo 外からも呼び出したい場合は `~/.claude/skills/<name>` から repo 内 `.claude/skills/<name>/` へ symlink する。**absolute path 禁止 / relative path 必須**（repo の `mv` / rename で absolute は dangling になる）。既存 `~/.claude/skills/*` の convention に揃えて `../../<rest-of-path>` 形にし、追加時は `ls -la` で既存を確認する。SKILL.md 内で absolute path を例示しない
- **`Read` / `Write` / Setup-mode safety (3-clause)**: (i) **Drop `test -f` / `test -d` pre-checks (TOCTOU anti-pattern)** — `Read` 自体が missing-file error を明示するため pre-check は冗長かつ TOCTOU。canonical: pre-check を削除して `Read` error を停止条件にし、`allowed-tools` から `Bash(test *)` を drop する。例外: missing と other error を distinguish する用途なら残し、SKILL.md に意図を 1 行明記する。(ii) **Setup-mode pre-existence re-check (defensive race guard)** — config 不在を検出したあと Setup-mode template の `Write` 直前に **再度 `Read` で不在を再確認**する（race で既存 file を clobber するのを防ぐ）。canonical: 「Before writing: re-confirm `.claude/<config>.local.md` does not exist ... If it now exists, abort Setup mode and report the conflict — never overwrite」。(iii) **`Read` error semantics: default to stop-with-error** — error が missing か permission / encoding かを reliably distinguish できない場合、Setup-mode 分岐は判別可能なときだけ取り、判別不能なら stop-with-error を既定にする（誤分岐は既存 config を clobber する経路）
- **Pre-existing layout flag vs new-change regression discrimination**: TEST_FAILED のときは (a) change が導入した regression か (b) base-commit の pre-existing state かを必ず discriminate する。check: (i) `git stash` か base clone で同じ test を再実行、(ii) 同じ failures なら pre-existing、(iii) test agent が flag した plugin / skill 名と change set の path を grep で交差確認、(iv) Step 8 では「pre-existing failures (out of scope of this PR)」と明記する。pre-existing の修正は scope creep
- **Stall mitigation: callee-side wording (A) + orchestrator-side pre/return-point reminders (B) — 2-stage serial pair**: stall の解消には (A)+(B) の両方が要る（(A) なしの (B) は callee の prompt-injection に相殺される）。**(A) Callee-side schema-verb wording**: terminal-action 動詞（`End every invocation` / `Terminate` / `Do not produce any additional turn`）は orchestrator に「turn を閉じろ」と受け取られて stall する。canonical: (i) schema-verb form「`Emit a single fenced JSON block at the end of the response, matching the schema ...:`」（terminal-action は禁止）、(ii) 独立した `## Sub-skill caller directive` 節に 3 段落 —「fenced JSON は **return value** であって turn 境界ではない」「次の tool call を同じ agent が immediately issue する」「JSON と次の tool call の間に prose / 確認 /「shall I proceed?」を挿入しない」、(iii) uniqueness clause「Only one fenced JSON block」。複数 callee に置くときは byte-identical にする。新規作成・編集時は terminal-action verb を grep する。**(B) Orchestrator-side entry + return-point reminder**: return-point だけでは「決定の瞬間」を救えないので、**entry-side の `Pre-invocation reminder`** を dispatch 直前に挿入して return-point と直交させる。構造: (i) 次の tool call の named specification、(ii) JSON verdict as return value の framing、(iii) `See § No-Stall Principle.`。この duplication は意図的な reinforcement-by-repetition なので、削減しない rationale を 1 行残す

- **進捗カタログの派生数値ベースラインは一次情報源から再計測する**: 進捗管理用カタログ文書を編集する diff の中で、既に確定済みとして引用されている数値ベースラインを見つけた場合、カタログの記載値（二次情報源）を転記せず対象ファイル自体（一次情報源）から再計測する。同じ分解タスクの兄弟 subtask が既にその値の元になったファイルを変更してコミット済みの場合、キャッシュされた数値は陳腐化している可能性が高い
- **分類体系を跨ぐ具体例引用の自己矛盾チェック**: 文書が既に確立した分類体系を参照しつつ、数値レンジや形状の比較のために具体例を挙げる場合、引用する具体例がその分類体系上の反対側のカテゴリに属していないか確認する。属している場合は分類ラベルをそのまま使わず、カテゴリ中立な表現に置き換えるか、範囲がカテゴリを跨ぐ旨を一言添える
- **「別の場所に記録済み」を削除の根拠にする前に追跡下か確認する / コミット対象文書から gitignore 対象パスを名指ししない**: 内容を削除する・重複させない判断を「同じ内容が別の場所に既にある」で正当化する場合、その場所が git 追跡下にあることを先に確認する。`.claude/plans/` はディレクトリごと gitignore 対象なので、そこに設計根拠があることは削除の根拠にならない（fresh clone では解決しない）。あわせて、コミットされる成果物（`CHANGELOG.md`、配布される `SKILL.md` / `references/*.md`）から gitignore 対象パスを名指ししない — 参照が解決しないうえ、ローカル限定の構成を不必要に露出させる
- **CHANGELOG エントリの粒度**: 「何が変わったか」と「受け手が判断に使う理由」までを簡潔に書き、そこに至る検討経緯・不採用案との対比・内部的な導出過程は書かない。詳細な背景は計画文書や PR 本文に残す
- **共有 reference への切り出しは、全 caller を委譲ポインタまで畳んでから実行あたりの純読込量を再計測する**: 複数 caller に重複した手続きを共有 reference へ切り出すとき、caller 側に手続きの再記述を残すと二重管理になって実際に乖離する。また切り出しただけでは新ファイルの読込が全 caller に加算されるので、実行あたりの純読込量は増える方向に動く — 畳み込み後に `wc -m` で再計測し、増分が残るならそれを受容する判断として記録する
- **毎回読まれる reference には実行時に参照される内容だけを置く**: スキルが実行のたびに読み込む reference ファイル（hot path）に設計根拠のような散文を置かない。切り出す際は根拠専用の新しい reference を作らず、既存の追跡ファイル（`README.md` 等）へ寄せる — 新設すると同期対象が 1 箇所増え、bundle メンバーでは canonical と bundle copy の両方に増える
