# Step 2 Simplicity self-audit — express core

The tier-independent core of the `SKILL.md` Step 2 sub-step **Simplicity self-audit**. Audit the plan against every item below.

For each element that fails the audit, either (i) drop it from the plan, or (ii) add an explicit one-line rationale tying it to a concrete trigger (user requirement / bug / rule). Some items prescribe a **more specific remedy** (e.g. a binary Decisions Recommendation/Alternative item, or surfacing lighter alternatives); when such an item applies, its prescribed remedy supersedes this generic (i)/(ii) pair — the pair is the fallback only when the matched item names no more specific remedy. When more than one specific-remedy item matches the same element, apply the remedy of the item most narrowly scoped to that element's failure mode and treat the others as confirming — do not emit overlapping or contradictory remedies. This paragraph governs the items in both files.

**What the express lane defers, and why noticing it is an escalation signal.** On the express lane, noticing that an item held back in [`simplicity-self-audit.md`](simplicity-self-audit.md) would fire is itself the signal to raise the tier per [`tier-escalation.md`](tier-escalation.md) at Step 2's Confirm difficulty checkpoint — which rejoins the full lane and reads that file as part of the rejoin — rather than to reach for the file here.

## Checklist

- Each plan element must be traceable to one of: (a) an explicit user requirement, (b) a known bug or constraint, or (c) a documented project rule under `.claude/rules/`. "Future-proofing", "UX polish", "consistency with other projects", or "might be useful later" are not sufficient triggers on their own (for the intra-project "align with sibling implementations" rationale specifically, the **Consistency-with-siblings as primary rationale** item in [`simplicity-self-audit.md`](simplicity-self-audit.md) prescribes a more specific remedy — surface lighter alternatives in Decisions — which supersedes a plain drop per the (i)/(ii) precedence note above).
- **Inherited spec files** (`.claude/plans/*.md` — full-spec drafts, archived plans, or AI-authored details within a task-decomposition state file): treat the content as a prior-session draft, not as confirmed user requirements. Cross-check each inherited design decision against the user's original ask surfaced by Step 1.5 / the user message.
  - **Exception — task-decomposition state files**: subtask boundaries, order, `depends_on`, and purposes were user-approved in a prior Step 1.5 and must be honored as-is. Only AI-authored descriptions, verification hints, and design elaborations within each subtask are draft.
- **Root-cause provenance check**: if the plan leans on a root-cause claim from an AI-authored prior-session artifact, re-derive the root cause from the user's original ask before treating it as load-bearing. User-confirmed root causes are exempt.
- **Pre-existing-artifact existence verification**: when the plan's implementation steps, design rationale, or scope boundary rest on an **"already exists / already established / reuses an existing" premise** — a claim that a specific artifact (file, state variable, convention, step output, or canonical identifier) is already present in the codebase or already produced by an upstream step or a sibling code path — verify the claim from a **primary source** (read the actual file, grep for the identifier, or inspect the relevant step output) before finalizing the plan, rather than assuming it from structural analogy or recollection. Two companion obligations: (i) **conditional-path coverage** — when an existence claim is conditionally true (the artifact exists on one code path but is absent on another), the plan must explicitly address the absent case rather than treating the conditional as a universal assertion; (ii) **stable edit-site anchoring** — when an existence claim anchors a cited edit-site location (e.g. "the canonical definition is at sub-step N"), re-derive the location from a stable phrase anchor rather than a raw line number that drifts across edits.
- **Self-application live validation in Test plan**: when the change targets the **currently running skill** itself — the modified skill is the one driving this very workflow run, OR a callee skill the workflow will invoke later in the same run — identify the immediate-exercise path inside this same run and add a **live validation** item to the Test plan citing the specific Step / sub-step / hook where the new behavior is naturally exercised. When the target is **not** the running skill or a same-run callee (external skill, CLI tool, application code unrelated to this run) or the change has no in-run exercise path (e.g. a session-start-only path the current run already passed), this audit does not apply.
- **Plan-body technical concept names match current target file vocabulary**: when the plan body references technical concept names that already exist in the files the plan will touch — step / section / heading names, file or directory paths, config keys, callee names, identifiers — `grep` the cited names against the current target files before finalizing the plan, and reconcile any mismatch (renamed step, renamed config key, deprecated callee name, stale file path) in this same pass. Distinct from the Step 3 reviewer's `Internal convention citation verification`, which judges *claims of convention adherence*: this audit is a pure name-currency check. When the task is itself a rename / version-bump operation, the **Version/identifier string replacement tasks** bullet in `SKILL.md` § Step 2: Create Plan already enforces a repo-wide grep and this audit folds into that one; this bullet covers the non-rename case where stale vocabulary creeps in inadvertently.
- **Task-input-declared priority conflict check**: when the plan's approach **expands scope beyond what the task input literally requested** (adding a mechanism, a retrofit, or an implementation not explicitly asked for), and the task's own input material — a handoff document, a roadmap / improvement catalog, a `.claude/rules/` file, or any other source read while planning — **explicitly documents an active resource-constraint initiative or stated priority** that the added scope touches (a size / growth budget, a deprecation timeline, a "stop doing X" directive, or an equivalent named goal), treat the tension as a **required Decisions item** rather than resolving it silently. Do not let "this is cheap to revert later" reasoning substitute for surfacing it: reversibility of the code and the cost of the tension going unnoticed are different axes. When in doubt whether a documented priority actually applies to the scope being added, surface the tension rather than resolving it via reversibility alone.
- **Target-file constraint-and-invariant audit**: for each file the plan will modify, scan for explicitly stated constraints, exclusivity rules, or invariants — clauses of the form "only X may do Y here", "this must always be Z", "no other site should call W", mutual-exclusion flags, or single-writer enforcement prose. If any such clauses are found, verify before finalizing the approach that the plan does not contradict them. If a contradiction is found, the plan must either (a) narrow the approach to avoid the constraint, or (b) explicitly include revising the constraint as an in-scope Decisions item (with a rationale for why the invariant is being changed), rather than silently proceeding with an approach that violates a documented invariant.
- **Plan-level incrementality**: check whether the plan splits into independently verifiable units (e.g. hotfix vs refactor). If yes, propose the split now — PR-level splits restart via Step 1.5, intra-PR splits become staged commits. This is the only plan-level incrementality check before the Step 4 gate.
- **Deletion / no-duplication justified by an external reference — recipient-visibility check**: when the plan justifies **deleting** content, or **not duplicating** it, on the grounds that the same information already lives in another location, verify that the referenced location is **persistent and visible to the deliverable's recipient** before accepting the justification — tracked in version control when the project is version-controlled, and included in the distribution package when the deliverable is distributed. A pointer to a location outside the deliverable's own tree (a gitignored working document, a local-only generated artifact) does not satisfy the recipient.
