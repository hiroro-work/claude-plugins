# mobpro M6 Diff Review

Operational detail for `mobpro`'s **M6 diff review** display surface — the branch on `commit_review_gate`, the per-unit diff-range mechanics, and the crit fallback. `SKILL.md` M6 sub-step 2 (d) delegates here; [`learning-gates.md`](learning-gates.md) § A (M6 diff review) owns the question-handling discipline around it. **Read this file once at M6 loop entry**: § Per-unit review range's numbered steps apply at each unit, and its **M6-exit unstage** paragraph applies once at M6 exit. No rule here varies from one unit to the next, so one read covers the whole loop.

## Display surface (`commit_review_gate`)

Branch on the resolved `commit_review_gate` ([`configuration.md`](configuration.md) § Fallback keys), the same key M11 reads:

- **`diff`** (the default): render `git diff <m6_review_base>..<unit_obj>` in chat inside a fenced block, preceded by the opening line in [`learning-gates.md`](learning-gates.md) § A (M6 diff review).
- **`crit`**: launch crit on the same range (§ crit path), emitting [`learning-gates.md`](learning-gates.md) § A's opening line **in the same turn as the launch, before the junior opens the browser**, so it guides their reading (the same discipline `SKILL.md` M11 applies to its "point of this diff" note on its own crit path).

## Per-unit review range

M6 lands no commits, so each unit's review names a *range* built without moving a ref — the detached-review-object technique `../dev-workflow/references/crit-commit-review.md` § crit CLI contract documents under "Scoping mechanism — detached review object, no ref ever moves". Two deliberate differences from that file's use of it: the base is `m6_review_base`, not `HEAD`, and it **advances per unit** instead of being resolved once.

`m6_review_base` is M6-loop-local state, initialized to `base_commit` at M6 loop entry. Per unit:

1. **Stage this unit's edited paths**: `git add -- "<path-1>" "<path-2>" ...` (double-quote each path so spaces, quotes, and non-ASCII characters survive), minus the `SKILL.md` § Workflow artifacts set — never stage the plan document or the decomposition state file, which a run edits as it goes. (Staging is all this step controls: an artifact the *user* had already staged before M6 began still rides along, per the inherited property noted below.) Do **not** reset the index between units: it must accrue every earlier unit's content for the range below to carry only this unit's delta. Append every path staged here to `m6_staged_paths` — M6-loop-local like `m6_review_base`, initialized to `[]` at M6 loop entry and likewise not a `SKILL.md` § Cross-step state variables member — which the M6-exit unstage below consumes. It has to be accumulated as it goes: the index at M6 exit also holds whatever the user had staged before the run, and that staging is deliberately left alone.
2. `git write-tree`, then `git commit-tree <tree> -p <m6_review_base>` with a one-line message naming the unit (piped via stdin) → `<unit_obj>`, a dangling commit object: no ref moves and no hook runs.
3. **Present** `<m6_review_base>..<unit_obj>` on the resolved surface (§ Display surface).
4. **Advance** once the review resolves: `m6_review_base = <unit_obj>`. A mid-review code change does not resolve it — per [`learning-gates.md`](learning-gates.md) § A's "Change requests raised during the review" paragraph, re-run steps 1–2 against the unchanged `m6_review_base` to rebuild `<unit_obj>` from the now-edited files, then present again (the same rebuild § crit path's `approved: false` with comments disposition performs).

If a git call in steps 1–2 fails, this unit's review falls back to a chat rendering that needs no new object: tracked paths via `git diff <m6_review_base> -- "<path>" ...`, and untracked ones (`??` in `git status --porcelain=v1 --untracked-files=all -z` is the discriminator — `-z` keeps paths verbatim instead of C-quoting them) via `Read`, presented as a new-file hunk — `git diff` omits untracked paths by design, so a unit whose point is a new file would otherwise show the junior an empty diff (same tracked/untracked pairing as `../dev-workflow/references/interactive-commits.md` § Per-commit loop sub-step **a. Present**). `m6_review_base` stays put, so the next unit's range covers both units.

One inherited property worth knowing: `git write-tree` snapshots the whole index, so anything already staged when M6 began rides along in unit 1's tree and appears inside `base_commit..<unit_obj>`. Point it out if the junior asks about a file no unit touched.

**M6-exit unstage** — once at M6 exit, after the last unit's review (`SKILL.md` M6 sub-step 4 anchors this in the M6 step sequence): `git reset -- "<path>" ...` over `m6_staged_paths` returns those paths in the index to `HEAD`'s tree, so M11 still sees new files as untracked (`??`) rather than staged. Skip the call entirely when `m6_staged_paths` is empty (every unit fell back before staging, or M6 ran no units): a pathspec-less `git reset --` unstages the user's own pre-existing staging wholesale. Two notes. A path the user had already staged before the run loses that staging if a unit review touched it — its content is untouched in the working tree, and M11 re-stages by pathspec. And on failure, retry once after a 1–2 second sleep, then render a one-line note with `<reason>` (the last non-empty stderr line, ≤ 80 characters, or `(no stderr)` when empty) and proceed; leftover staged paths are harmless, since M11's own `git add --` and pathspec-scoped commit behave identically either way. Do **not** auto-recover (no `git reset --hard`, no manual index or ref manipulation).

## crit path

Read `../dev-workflow/references/crit-commit-review.md` and reuse the parts below, substituting this file's range endpoints for its own and reading its "Step 10 run" scope as **the M6 loop**:

- **§ crit CLI contract** — the CLI facts, the `--range` mode rationale, the read-both-streams `approved:` rule, and the no-`--no-open` / no-`--quiet` finding.
- **§ Procedure step 1's "Check availability and reachability" step** — the probes (`crit --version`, `printenv CLAUDE_CODE_REMOTE`), run **once for the whole M6 loop**. Cache the combined result as `m6_crit_available`, M6-loop-local like `m6_review_base` and likewise not a `SKILL.md` § Cross-step state variables member. The distinct name matters: M11 writes upstream's `crit_commit_review_available` when it re-runs both probes at its own gate (that step's own self-contained-check convention), so a shared name would have one gate overwrite the other's answer.
- **§ Procedure step 2's "If either check failed" disposition** — one informational note (here, one per M6 loop rather than per unit), its install-URL vs no-local-browser wording including the both-failed tie-break, and no re-attempt for the rest of the loop. This unit and every one after it render on the chat surface (§ Display surface's `diff` bullet) — the failing probe does not skip the unit that triggered it.
- **§ Procedure step 3's per-round launch** — launching `crit --range <m6_review_base>..<unit_obj>` as **background Bash**, never the `Agent` tool, so `SKILL.md` M12 sub-step 3's only-direct-`Agent`-use invariant holds. Skip its `git rev-parse HEAD` base resolution and its staging / `write-tree` / `commit-tree` sub-steps: § Per-unit review range owns both, and M6's base is `m6_review_base`, not `HEAD`.
- **§ Procedure step 4's "Read the decision, then unstage" step** — read the decision from both captured streams, but skip its unstage; § Per-unit review range defers that to M6 exit.
- **§ Procedure step 6's "No machine iteration cap" note** — each round blocks on a real browser submit, so the loop is human-paced.

**Decision mapping.** M6 substitutes its own for that file's **§ Procedure step 5's per-commit decision mapping**, whose `accept` / `adjust` / `cancel` dispositions have nothing to act on where no commit lands. The substitution also drops that step's per-round Step 7 / Step 7.5 re-verification mandate — M8 and M9 both run *after* the whole M6 loop, so there is nothing to re-run mid-loop. Evaluate in order, first match wins:

- **Non-zero exit, or no parseable `approved:` line** → this unit alone renders on the chat surface (§ Display surface's `diff` bullet). The cached availability answer is **not** cleared, so crit is used again for the next unit.
- **`approved: true`** → the review is done; advance and move to the next unit. Accompanying comments are advisory.
- **`approved: false` with comments** (either `scope`, or both in one round) → handle **every** comment the round carries, regardless of `scope`: `scope` says where the comment is anchored, not whether it asks for code to change, so a line-anchored question is as normal here as a review-level fix request. Apply the requested code edit for each comment that asks for one, and answer each that only asks a question — explaining every fix and every answer within [`learning-gates.md`](learning-gates.md) § D (explanation length discipline), the same split § A's "Change requests raised during the review" paragraph draws. Then rebuild `<unit_obj>` from the files as they now stand (a round that changed nothing rebuilds the same tree) and start a new round — on crit a new round is how the junior gets another turn.
- **`approved: false` with no comments** → start a new round from the unchanged files, communicating that the submit had no effect.
