# Step 5 — Implement (extracted sub-steps)

Deep reference for `SKILL.md` **Step 5: Implement**. The numbered list below holds sub-steps 1, 2 (delegation body), 3–8, 10, and 11, in numeric order; sub-step 2.5 follows that list as its own section.

1. **Plan entry self-check — user-side manual action extraction**: before issuing the first implementation tool call, scan the approved Plan body (Overview / Decisions / Build order / Test plan / Risks / Unknowns) for **embedded user-side manual actions** — environment-prerequisite probes the user must run themselves, configuration values the user must add to a config file outside the agent's write surface, external authentications / API keys / hook installations / OS-level changes the user must perform manually, manual verification steps the user must execute against external systems ("run `<command>` and confirm output", "edit `~/<config>` to set X=Y", "log in to the external dashboard and authorize Z"). When at least one such action is present, emit a **short independent block at the top of Step 5** — separately from any other implementation prose — listing each one verbatim with the Plan section it came from, before proceeding with the first implementation tool call, so the user sees them distinctly rather than buried inside long-running plan execution. When no manual actions are present, skip this block. The block is informational — Step 5 continues without waiting for user input on the actions themselves (sub-step 7's probe-observation gate handles the cases where the workflow needs to wait).

2. **Subagent delegation of a settled work unit (optional, guard-gated).** The default under `implementation_executor: "main"` is still main-thread implementation. As an exception you MAY delegate a unit of the implementation work to a subagent (via the `Agent` tool) **only when all three guards hold**: (a) **spec-completeness** — the unit's shape is settled enough to hand a context-less executor a complete spec — its transformation rule / decisions / expected outcome are fixed, not still being worked out; (b) the session exposes a subagent type or skill effective for that unit; (c) the unit is not judgment-heavy, context-dependent, or small (those stay in the main thread). When `implementation_executor` resolves to `subagent` or one of the external-CLI executor values, this same settled-unit path becomes the **default** route for each qualifying work unit rather than a rare exception: guards (a) and (c) still decide per unit, so judgment-heavy, context-dependent, small, or still-unsettled units stay on the main thread with a one-line note, and hybrid execution is normal. Build every delegated payload per [`references/executor-prompt.md`](executor-prompt.md). For `subagent`: (i) hand the subagent the settled rule, the already-decided facts, and the verification means; (ii) treat Step 7 (Check / Test) as the verification gate; (iii) **select the subagent type by capability first** — exclude any agent type that cannot perform the required `Edit` / `Write` (read-only `Explore` / `Plan`-class agents), then prefer the most task-effective of the remaining edit-capable types, falling back to `general-purpose` (tool set `*`) when none fits better; do not hardcode `general-purpose` as the sole target; (iv) this delegation is one of the sanctioned exceptions named in § Configuration's `Agent` tool usage bullet, and it propagates `subagent_model` like the fixed dispatch sites (pass `model: <subagent_model>` when it resolves to a model id, omit when `inherit`). For an external-CLI executor value, dispatch the work unit through the matching named skill (`Skill(ask-claude)`, `Skill(ask-codex)`, `Skill(ask-gemini)`, `Skill(ask-copilot)`, or `Skill(ask-agy)`) driving its CLI in workspace-write mode; Step 5's side-effecting external-tool launch warning fires before the run's **first** such launch and covers subsequent executor launches in the same run. Resolve executor availability once per run at the first Step 5 delegation point: `subagent` requires an edit-capable exposed subagent type; external-CLI values require a successful `Skill(<value>)` call after one retry per § Prerequisites. If the selected executor is unavailable, emit a one-line note and fall back to `main` for the rest of the run with no user gate. After each delegated unit returns, the main thread runs the Step 5 self-audit sub-steps against the delegated diff as post-delegation verification; Step 7 remains the verification gate.
3. **Respect prior in-session edits**: content the user explicitly removed earlier in this session (comments, guards, logs) must not reappear. Treat deletion as authoritative, not as a gap to fill. This discipline applies when applying plan steps, when applying Step 6 tidy output, and when applying Step 8 review fixes
4. **Late-stage scaffolding self-audit**: when implementation introduces a structural element that was **not present in the Step 2 plan** — a new sub-step, an additional enum value, a new branch arm, an additional call site that invokes the same callee at a new location, a new recovery / fall-through path, a newly added test or other new block — re-apply the same Step 2 § Simplicity self-audit rigor to the newly introduced element before moving on. Sub-checks (i)–(iv), (ix), and (x) fire only when a new structural element is introduced; sub-checks (v), (vi), (vii), and (viii) fire unconditionally for every diff edit: (i) **sibling symmetry** — when the new element parallels existing sibling elements, verify same fields / same disposition values / same error-class coverage; (ii) **error-path symmetry** — for any success path introduced, trace its corresponding failure path explicitly (counter increment vs. non-increment, success-only vs. failure-included); (iii) **boundary-value coverage** — for any predicate, threshold, or count introduced, trace the boundary cases (empty input, all-same-classification, mixed-classification) and verify the predicate truth value matches design intent; (iv) **reference-site sweep** — if the new element is referenced from prose elsewhere in the file, verify those references use stable phrase anchors (not raw sub-step numbers / branch letters); when a newly introduced or changed reference points at a heading or bold-prose label in a **different** file, verify the referenced label actually exists in that file's current content via a live `Grep` or `Read` before landing — do not rely on a secondary description (a rules document's paraphrase, a prior review comment's quote) of what the target file contains; if the label is not found, fix the reference (correct the target label, or update the label and sweep other referrers) before landing rather than leaving a dangling cross-reference; (v) **Markdown block-element structural integrity** — for each edited `.md` file, scan newly added or changed content for adjacent block elements (list items, paragraphs, code fences, headings, blockquotes) that lack a separating blank line; when a gap is found, insert the missing blank line immediately (in the same Edit call) before moving on; (vi) **comment conciseness** — for every inline comment introduced or changed in the diff, apply the rule-of-need test: a comment is justified only when the **why** is non-obvious (a hidden constraint, a subtle invariant, a workaround for a specific bug, behavior that would surprise a reader); a comment that restates what the adjacent code already expresses is a deletion candidate — two further recurring forms are (a) naming the library / API the call itself already names, and (b) explaining the **provenance** of a value rather than its **purpose**; multi-line background explanations belong in rule or design documents, not inline — when a verbose or redundant comment is found, delete or condense it, and sweep every comment added in the same change (not just the one instance spotted) before moving on; (vii) **newly-introduced cross-reference stable-anchor form** — for every cross-reference (Step / sub-step pointer) the diff newly introduces, verify it carries the stable descriptor alongside the number rather than a bare number alone; when a non-conforming form is found, add the stable descriptor before moving on; (viii) **closed-list / sibling-set stale-value sweep** — when the diff edits one or more entries of a closed list or a set of parallel sibling references (a decision-mapping table row, a numbered list with sibling rows, mirrored cross-references), re-read the entire list / sibling set and confirm no entry was left with a stale value inconsistent with its updated neighbors; grep the remaining entries for the old token before moving on; (ix) **block placement hierarchy** — when adding a new block (test case, list item, section, describe/context block, or any other structural element) to an existing file, verify whether its placement nests it inside a parent element's scope; if it is nested, confirm that the parent's setup / preconditions / before-hooks are intentionally applicable to the new block; when they are not (a new test exercising a different fixture context, a new section belonging at the top level), relocate the block outside the unintended parent before proceeding; (x) **test-behavior discrimination** — when the diff adds a test covering behavior the change modified that is interactive or dynamic rather than static output (a click / navigation / state change / async effect rather than a rendered attribute or return value — judge this by what the implementation changed, not by what the new assertion happens to inspect), verify the new assertion actually discriminates the fix: ask whether reverting the just-made implementation choice would make the new test fail. If it would not, retarget it at the effect the triggered behavior actually produces, following the codebase's established pattern for that behavior, before moving past implementation into review. This self-audit must run in the main thread at Step 5.
5. **Final-pass literal-value full-repo grep**: at Step 5 completion (after all planned edits are applied and before advancing to Step 6 Tidy), for each **literal value the plan replaced or introduced** — numeric constants (threshold values, version numbers, magic numbers), token strings (status enum values, config keys, identifiers), file path fragments, or any other literal whose semantics are tied to a specific value — `grep` the **entire repository** (not just the plan's enumerated sweep targets) for the **old value** and confirm zero hits. Multi-stage structure: (i) **enumerated sites** — the explicit list from the Plan's Test plan, verified one by one; (ii) **final-pass full-repo grep** — `git ls-files | xargs grep -l <old-value>` (or equivalent) for any residual hits outside the enumerated list, with each hit reviewed in context and either updated (if it carries the old value's semantics) or marked as out-of-scope (e.g. a different concept that coincidentally uses the same literal); (iii) **alias and derived-form sweep** — for rename and migration tasks, additionally grep for mechanically-derivable aliases and derived forms of the old value (abbreviated forms, synonyms, or alternate identifiers the codebase uses interchangeably to refer to the same concept); when the derived-form set can be enumerated upfront, list and grep each form before declaring the sweep complete. The sweep runs as a Step 5 completion gate in the main thread. **Authoritative-tool cross-check for load-bearing enumeration claims**: when the completeness of the enumeration is mechanically verifiable by a downstream authoritative tool — a compiler or type checker reporting all affected call sites for a changed type or interface, a language server returning all references for a renamed symbol, or (absent either) a structured manifest audit such as `jq` over a manifest file — cross-check the grep results against that tool's output; if the tool reports additional sites that grep missed, treat those as unresolved hits and apply the same two-option disposition defined above for the full-repo grep pass (update if it carries the old value's semantics; mark out-of-scope if it coincidentally uses the same literal for a different concept) before presenting the enumeration as confirmed. Search filter prefix/anchor errors can silently drop matches with no error signal, which is what this cross-check catches. When both grep and an authoritative tool are available, treat the tool output as the oracle; when no structured verification exists, the grep-only pass is sufficient. Non-literal-replacement tasks skip items (i)–(iii). **(iv) Coordinated prose-invariant multi-surface sweep**: when the planned change updates a design rule, behavioral constraint, or documented invariant expressed textually across multiple documentation surfaces rather than as a single swappable literal, enumerate all known surfaces where the invariant appears — sub-step paragraphs, reference table rows, reference prose body, README examples — as a closed list before starting edits; after all edits land, grep for the old description's key phrases and synonyms across the enumerated surfaces; for each hit, apply the same two-option disposition as the full-repo grep pass.
6. **Pre-write path scope check (Write / Edit / new-file path safety)**: before every `Write` / `Edit` / similar file-creation tool call whose `file_path` argument **does not match a path that already exists** in `git ls-files` output, run a **two-stage path verification** before issuing the tool call: (i) **repo-root containment** — verify the absolute resolved path sits under `git rev-parse --show-toplevel` (no `../` escape from the working directory, no absolute path leading outside the repo); (ii) **prefix sanity** — verify the path's leading directory matches an expected location for its content class (`.claude/plans/` for plan documents, `skills/<name>/` for skill content, `src/` or `tests/` or equivalent for code, `.triage/` or `tmp/` for staging, etc.). If either check fails, **abort the tool call** with a fail-loud diagnostic naming the resolved path and the expected prefix set, rather than silently creating the file. Then emit a one-line note naming that Build order step, leave the step unresolved, and carry on with the remaining steps — do not substitute a path of your own choosing, and do not open a user gate to obtain a corrected one (sub-step 7's probe-observation gate is the only user-side wait state permitted inside Step 5). The `allowed-tools` permission grant alone does not prevent parent-directory landing (`Write` accepts any string `file_path`), so this procedural pre-check is the only structural defense against typo-induced orphaned files. If a tool call has already created a file in the wrong location, instruct the user to delete it manually — the workflow cannot reach files outside the project scope.
7. **User-observable artifact protection gate at probe → real-implementation boundary**: when the Plan explicitly stages an implementation as **probe / intermediate-artifact → real-implementation replacement** (e.g. "first emit a debug-instrumented version for user to observe, then replace with the production implementation", "scaffold a placeholder file the user will manually inspect, then overwrite with the final content", "log expected probe output as a verification step, then remove the logging"), do **not** advance to the real-implementation step until the user has signaled observation completion. The probe-output observation gate is **the only user-side wait state permitted inside Step 5**. When the probe is committed to disk and the user has not yet acknowledged observation, hold the workflow at this boundary and emit a one-line wait prompt in the resolved `language` (e.g. `Probe artifact deployed at <path> — please observe its output before the workflow replaces it with the final implementation. Reply when ready to proceed.`). Resume the real-implementation step on any non-empty user reply. When no probe → real sequence is in the Plan, this gate does not fire. It exists to keep the probe artifact from being silently overwritten before the user has inspected it.

   **AskUserQuestion option design (applies to the probe gate above and any future user-state-query call in this workflow)**: when the workflow uses `AskUserQuestion` (or any equivalent multi-option user-query tool) to query the user about a plan-derived state — probe-execution outcome, manual-verification result, environment-prerequisite check, or any equivalent state confirmation — the options list MUST include a **meta-confusion branch** alongside the result enumeration. Concretely, do not present only outcome categories (e.g. `success / failure / skipped`); also include an option phrased as **"the procedure / expected outcome is not yet understood (please re-explain)"** in the resolved `language` (e.g. `language: ja`: `手順 / 期待結果がまだ把握できていない（要再説明）`; `language: en`: `the procedure / expected outcome is not yet clear (please re-explain)`).

8. **Derived-value claim deferral**: when deliverable prose embeds a value **derived from content that later phases can still change** — a size claim about a generated artifact, an item or step count, or any other body-derived figure — do not finalize that value during Step 5. Keep it as a clearly-marked provisional value (e.g. render the figure as `<provisional — finalized at Step 10 entry>`, grep-able at the application point). Apply the provisional marker to **every same-class derived value in the same edit — all-or-none, not one value at a time**: when a single sentence carries several figures of the same kind, marking one while hardcoding the rest is the exact failure this forbids. Right after marking, `grep` each file the edit touched for the class's unit token next to a numeric literal (e.g. `chars` / `k chars` for char-count claims, `steps` for step counts) to confirm none was left un-marked. Then compute + write the final figure **exactly once at the last gate where the source content is settled** — the plan-deferred bookkeeping application point at Step 10 entry (the deferred-bookkeeping paragraph at the top of `references/interactive-commits.md`, applied before its § Collect changes step collects the working tree), after Step 6 Tidy, Step 7.5 fixes, Step 8 review fixes, and any Step 9 `hooks.on_complete` working-tree modifications have all landed. Re-verifying and re-correcting the figure after every downstream phase that touches the body is the anti-pattern this item forbids. When `interactive_commits: false` (Step 10 is omitted and execution proceeds directly from Step 9 to Step 11 — see § Step 10: Interactive Commits), the Step 10 entry gate never occurs: finalize the figure at the same settledness point — immediately after Step 9 completes or is skipped, before proceeding to Step 11 — so the provisional marker never survives into the final tree.

10. **Side-effecting external-tool launch warning**: when a Step 5 tool call launches an external process or tool whose execution has a side effect observable outside the sandbox (opening an actual browser window, sending an external network request, starting a long-lived background process), warn the user in the resolved `language` before the first such launch and assign each launch a distinguishable identifier (e.g. a timestamp or sequence tag) reported alongside the warning, so a real-world artifact the launch produces can be attributed to the correct launch afterward. Ordinary sandboxed tool calls with no external-facing effect (`Read` / `Edit` / local `Bash` commands, or an `Agent` subagent dispatch that itself has no external-facing side effect) are unaffected.
11. **Tier escalation checkpoint**: once every planned edit has landed and sub-step 9's implementation diff snapshot is recorded, re-assess the finished change against [`tier-assessment.md`](tier-assessment.md) § Tier criteria. This is the **second of the two escalation checkpoints** in [`tier-escalation.md`](tier-escalation.md) § Tier-change sites. Act **only when the new assessment is strictly higher** than the current tier — then read [`tier-escalation.md`](tier-escalation.md) and follow it. When the assessment is unchanged or lower, this sub-step writes nothing; the tier never falls.

## Sub-step 2.5 — Build-order boundary chain

Applies inside sub-step 2's per-step progression, ahead of sub-step 3.

Record each Build order step's landing point as a dangling commit object, which Step 10 consumes to propose a commit grouping built from the approved Build order. The objects are the technique [`diff-presentation.md`](diff-presentation.md) § Detached review object owns, with `<base>` = `step5_boundary_base` and `<head>` = that step's boundary object per that file's § Caller endpoints.

**Entry condition**: run this sub-step only when `interactive_commits` resolves to `true`. When the key is `false`, skip the sub-step and leave `implementation_boundaries` at its `[]` init.

**Loop-local state**, initialized at Step 5 entry and read nowhere outside this sub-step: `step5_boundary_base` = `<base-commit>`, `step5_staged_paths` = `[]`.

Per Build order step, once that step's edits have landed:

- **(a) Build the boundary object** per [`diff-presentation.md`](diff-presentation.md) § Detached review object steps 1–3, with the paths in scope being **the paths this step edited minus the § Workflow artifacts set** (never stage the plan document or the decomposition state file, which a run edits as it goes) and a one-line message naming the step's bold heading verbatim. **With those paths staged, run `boundary_check_commands`** (§ Configuration — skipped entirely when the key resolves to none, which is its default): execute each entry in order, then re-run the same `git add` over that same path set. The re-add is what makes the key do anything at all — a command's rewrites land in the working tree, so without it `write-tree` below snapshots the pre-run content and this step's tree carries none of them. A non-zero exit is handled by the paragraph below rather than by the chain-abandon rule. **Immediately before `write-tree`, unstage any § Workflow artifacts entries the index carries** (`git reset -- "<artifact-path-1>" ...`, skipped entirely when none are staged): `write-tree` snapshots the whole index, not the paths staged above, so an artifact something *else* staged mid-Step-5 would otherwise ride into this and every later boundary tree and land inside a Step 10 commit. **Append those paths to `step5_staged_paths` immediately after the `git add` succeeds**, before `write-tree` — not in (b) below: a `write-tree` / `commit-tree` failure would otherwise leave them staged in the user's index with no record for the exit unstage to reset. **Skip this step's build entirely when the path set is empty** — a verification-only step, or one whose only writes were workflow artifacts, would otherwise record a boundary identical to its predecessor.
- **(b) Record it**: append `{heading, object}` to `implementation_boundaries`.
- **(c) Advance**: `step5_boundary_base` = this step's boundary object.

**On a `boundary_check_commands` non-zero exit**: this is not a chain failure. Record a one-line note naming the step and the command, with `<reason>` = the last non-empty line of stderr truncated to ≤ 80 characters, or `(no stderr)` when stderr is empty or whitespace-only. Then fix what the command reported and re-run that one command **once**. On a second non-zero exit, keep the note as the record and build the boundary from whatever the working tree now holds: `check_commands` at Step 7 is still the gate that stops the run, so abandoning the chain here would cost the whole run's commit grouping over one finding that gate will raise anyway. The chain-abandon rule below covers the `git add` / `write-tree` / `commit-tree` calls alone.

**Do not reset the index between steps** — each boundary's tree must carry every earlier step's content, so the index accrues across the whole of Step 5, and the reset owed for the paths staged here is deferred to the single exit unstage below.

**On failure**: on a non-zero `git add` / `write-tree` / `commit-tree`, a partial chain would label groups for some steps while silently folding the rest, so **abandon the chain rather than keeping it partial**: set `implementation_boundaries = []`, emit a one-line note naming the failing step, and skip the remaining steps' boundary builds for the rest of the run. Step 10 then takes its chain-absent path ([`interactive-commits.md`](interactive-commits.md) § Propose commit plan). Keep `step5_staged_paths` as it stands — the exit unstage below still owes those paths their reset.

**Step 5 exit unstage** — once, at Step 5 exit, before sub-step 9's diff snapshot: run [`diff-presentation.md`](diff-presentation.md) § Detached review object step 5's unstage over `step5_staged_paths`, returning the index to the state Step 5 found it in. Skip the call entirely when the set is empty. A path the user had already staged before the run loses that staging if a boundary build touched it — its content is untouched in the working tree. A failure follows that section's "On failure" paragraph.
