# mobpro M9 Rules + Code Review

Sub-steps 1–6 of the procedure `SKILL.md` **M9 — Rules + code review (quality gate)** delegates here; that step keeps its **Entry condition — this step always runs** paragraph inline. **Read this file once**, at M9. Unqualified `§ <Heading>` references resolve to `SKILL.md`, and a bare `sub-step N` is this step's own.

1. **Pre-review prediction narration**: before dispatching the reviews below, state where you expect findings to land and why, then cross-check that prediction against the actual results afterward (prompt + cross-check discipline in [`learning-gates.md`](learning-gates.md) § C (M9 pre-review prediction narration + cross-check)). Primary pass only — § Learning-Stop Principle's "Primary-pass rule" paragraph. When `code_review_enabled` is `false` the only dispatch to predict for is sub-step 2's — narrate for that one rather than skipping the narration.
   **Concurrent dispatch of both reviews**. Background dispatch counts as available when `Agent` is exposed and callable — detected as `rules-review` SKILL.md § 5. Review's "Detect availability by inspecting the current tool surface" paragraph describes — **and** the session offers `run_in_background`; default to parallel in an ordinary interactive session. When it is available, launch sub-step 2's `Skill(rules-review)` and — **only when `code_review_enabled`** — sub-step 3's `Skill(<reviewer>)` **together** right after the narration above — each as its own `Agent` dispatch with `run_in_background: true` and `subagent_type: general-purpose` (§ Direct Agent dispatch sites), passing no `model` parameter, since `mobpro` does not adopt `subagent_model` ([`configuration.md`](configuration.md) § Not-adopted keys) — then collect them in that order. Composing the code-review payload is a **prerequisite of the joint launch**, so do sub-step 3's payload work (its read of `../dev-workflow/references/code-review-payload.md` and the inputs that file lists) before launching rather than on arrival at sub-step 3; when `code_review_enabled` is `false`, skip that payload work and launch sub-step 2's alone. Both reviews are read-only; the main thread applies every fix. Tell each callee to run its `Skill()` on its own thread rather than wrapping it in a further `Agent` dispatch — a caller-imposed bound, not a claim that nested `Agent` is unavailable, and the trigger for each one's inline fallback.

   Sub-steps 2 and 3 then **collect** rather than dispatch. A launch that never fired, failed, or came back as an error counts as not-launched: that sub-step dispatches fresh on arrival, and the other launch is unaffected. Launching early has two consequences on the concurrent path. `m9_fix_files` is still empty when the payload is composed, so the payload's `.claude/rules/` weighting has no fix locations to point at and does not fire — on the sequential fallback it does fire, since sub-step 2's fixes have landed by the time the payload is built. And **a rules fix landing before the code-review collect does not send that review back**: dev-workflow discards a launched report in exactly that window (`code_review_stale`) and re-dispatches, and `mobpro` **deliberately does not adopt that flag** — a learning session's wall clock is set by the junior's turns, the fix is still covered by sub-step 5's aggregate cycle and the M11 commit gate, and re-dispatching would surrender the saving on every run where `rules-review` finds anything. Fall back to sequential dispatch when background dispatch is unavailable.

2. **Rules compliance**: collect sub-step 1's `rules-review` launch when it fired, else call `Skill(rules-review) --base-commit <base_commit>`. Violations → fix → explain each fix in 1–2 lines, appending every edited file to `m9_fix_files`. **Do not re-verify here**: the 2nd-cycle procedure and the persistent-violations user gate belong to sub-step 5, which runs them once over the aggregate — follow `../dev-workflow/references/step7.5-rules-compliance.md` for their bodies. Its "Who continues into (b)–(d)" paragraph routes by caller and names `mobpro`'s disposition: sub-step 5 always continues into them.
3. **Code review** (a single pass) — **skipped when `code_review_enabled` is `false`**, along with sub-step 4's unresolved-findings gate. On that path `m9_fix_files` carries sub-step 2's fixes alone. Otherwise collect sub-step 1's reviewer launch when it fired, else build the payload from `../dev-workflow/references/code-review-payload.md` § Sub-step 1 — reviewer report payload (the three review categories a/b/c — full rubric in `review-categories.md`, which the reviewer reads, as at M4 — untracked-file inclusion, `.claude/rules/` safety-net — its continuation item and scope instruction are escalation-pass-only upstream and never apply here) — payload definition only; the pass / stop discipline follows this procedure — and pass it to `Skill(<reviewer>)`. Judge → apply or reject-with-reason (files edited by an applied fix append to `m9_fix_files`) → explain each in 1–2 lines. Do not re-dispatch the reviewer; sub-step 4's gate is where anything still unresolved goes.
4. **Unresolved-findings gate**: if actionable findings remain after the pass, present them for a user decision (correspond / accept-and-continue / stop) — same shape as dev-workflow Step 8 sub-step 4.
5. **Post-pass aggregate re-verification (2 gates)**: once the review pass settles, if `m9_fix_files` is non-empty, (1) re-run check/test once (reuse M8 — its error narration fires here too, per [`learning-gates.md`](learning-gates.md) § B (M8 error narration)), and (2) run one `Skill(rules-review)` scoped to `m9_fix_files`, whose 2nd cycle and persistent-violations gate are the ones sub-step 2 deferred here — the same 2-gate structure as dev-workflow's Step 8.5 (Deferred Verification) (one cycle for both layers, no per-iteration re-runs). **Where its exits go**: every exit in the reused bodies falls through to marking M9 itself complete, and (d)'s wait gates that completion. Scope the (c) 2nd-cycle dispatch to `m9_fix_files` too, telling the reviewer that file-crossing / paired-change invariants sit outside this narrowed scope (verify those against the full `git diff <base_commit>`), so a fix applied here cannot be a spurious paired change.

   **`--fast` 1-pass cap**: when `fast_mode_active` (`SKILL.md` § Fast mode), `../dev-workflow/references/step7.5-rules-compliance.md`'s **`--fast` 1-pass cap** governs gate (2) — once its (a) fixes have landed and (b) has re-run check/test, take the **Caller-neutral exits** return without the 2nd-cycle dispatch or the persistent-violations gate. That cap writes its ledger record in `dev-workflow` vocabulary and M13 renders `fast_mode_skipped_steps` verbatim, so **substitute the whole record string rather than only its `<site>` slot**: append `M9 rules re-verification skipped (fast mode; <site>)`, taking `<site>` = `M9 aggregate re-verification` here and `M11 crit round` at the M11 `crit` re-entry that also continues into (b)–(d). The two sites are independent, so one run may carry both strings; each appears at most once however often its site fires. Gate (1)'s check/test re-run is **not** capped — it runs whenever `m9_fix_files` is non-empty. The remaining safety net is the M11 commit gate.
6. **Deliberately not adopted**: dev-workflow Step 8's Critical-triggered escalation pass — a second automated review round would land after the junior has already read the diff, so M6's per-unit reviews and sub-step 4's gate carry that weight instead. Also not adopted: overlapping the two dispatches with **M8** the way dev-workflow's Step 7 does. Launching them there would move sub-step 1's prediction narration into the check/test phase, where the junior has no review to predict against yet. Keeping both launches inside M9 buys less — the two reviews overlap only each other, not the check/test run — but it buys it without moving the narration.
