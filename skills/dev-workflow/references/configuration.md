# Configuration — per-key detail

Deep reference for `SKILL.md` **§ Configuration**. `SKILL.md` keeps the **`Agent` tool usage** bullet inline; this file holds the full per-key detail for every other setting. Inbound `§ Configuration's <key> bullet` references resolve to `SKILL.md`'s bold-label summary bullet; the detail is here. Unqualified `§ Step N` / `§ Prerequisites` / `§ No-Stall Principle` references and `sub-step N` references resolve to `SKILL.md`.

- **reviewer**: Reviewer skill name (default: `ask-peer`). Choose from: ask-peer, ask-claude, ask-codex, ask-gemini, ask-copilot, ask-agy. Unsupported values fall back to `ask-peer`
- **plan_review**: Whether Step 3 (Plan Review) runs, and in what shape. A closed set of three values, default `true`; **this bullet is the authority for that set**, and `skills/mobpro/references/configuration.md` § Fallback keys mirrors it under its own keep-in-sync directive.
  - `true` — the phase runs as a **single pass** covering review categories a–d, served by three reviewers dispatched in parallel.
  - `"rules-only"` — the phase runs as that same single pass, narrowed to one reviewer covering category (a)'s `.claude/rules/` compliance leg alone, with its inputs enumerated up front and every other tool barred (`references/step3-plan-review.md` § Rules-only single unit). Design, approach, and completeness go unreviewed, so `references/plan-format.md` § Step 4 guidance lines substitutes a review-status sentence saying so.
  - `false` — the phase is skipped entirely: Step 1 sub-step 7's registration burst marks `Step 3: Plan Review` `completed` up front, and Step 4's plan-approval gate becomes the plan's sole review (see Step 3's Disabled-phase exception).

  A present value outside the three warns and falls back to `true`. Neither `false` nor `"rules-only"` is recorded in `difficulty_skipped_steps` or `fast_mode_skipped_steps`, and neither raises a [`finish-phase.md`](finish-phase.md) § Completion reminder — both are the user's own declaration. Resolved into the pair `plan_review_enabled` / `plan_review_scope` at Step 1 sub-step 4's review-phase resolution; `references/step1-load-settings.md` § Sub-step 4 — review-phase resolution holds both lifecycles and the monotonic-lowering invariant. Set the value in `.claude/dev-workflow.md` or `.claude/dev-workflow.local.md`
- **code_review**: Whether Step 8 (Code Review) runs at all (default: `true`). When it runs it is a **single review pass plus one deterministic escalation pass**, the latter taken only when the review pass reports at least one Critical finding (Step 8's escalation-pass paragraph). When `false`, Step 8 is skipped entirely: Step 1 sub-step 7's registration burst marks the `Step 8: Code Review` and `Step 8-1` rows `completed` up front, and Step 7's concurrent code-review launch is suppressed (see Step 8's Disabled-phase exception). A configured `false` raises no [`finish-phase.md`](finish-phase.md) § Completion reminder. A present non-boolean warns and falls back to `true`. Resolved into `code_review_enabled` at Step 1 sub-step 4's review-phase resolution; `--fast` leaves it alone. To opt out, set `code_review: false` in `.claude/dev-workflow.md` or `.claude/dev-workflow.local.md`
- **subagent_model**: Optional. A map from difficulty tier (`trivial` / `simple` / `moderate` / `complex`) to the model the workflow's `Agent`-tool subagent dispatches run on — one of the model ids the current `Agent` tool's `model` parameter accepts (`sonnet` / `opus` / `haiku` / `fable` as of this writing; check the tool's live schema loaded in the current session rather than this fixed list), or `inherit` (use the session model). It governs (i) the workflow's **direct `Agent` dispatches** (Step 7's two background launches, the shared session scan — one dispatch performed at Step 11 / Step 11.5 / Step 11.6, see `references/session-scan.md` — and the conditional Step 5 delegation when it fires, see Step 5's sub-step 2 delegation guidance) and (ii) the model **propagated via the `Model:` argument** to the named callees the workflow dispatches (Step 7.5 `rules-review`; Step 6's `tidy` fallback dispatch — the bundled `Skill(tidy)` cleanup callee; the built-in `simplify` primary path takes no model and is unaffected; Step 6.5's and Step 4's `prose-polish` file-mode callees likewise receive no propagated model — `prose-polish` keeps its own `sonnet` default; the Step 3 / Step 8 inline reviewer when the resolved reviewer is Claude-family — see Step 1's reviewer-family classification; external-CLI reviewers are not affected). **The conditional Step 2 research delegation** (see Step 2 sub-step 3's "Codebase-research delegation" guidance) is a direct `Agent` dispatch and is governed like the rest. **Resolved once at Step 1.5's tier resolution** from the assessed tier, and re-resolved only when a tier escalation changes the tier (see `references/tier-assessment.md` § Resolution procedure step 5 and `references/tier-escalation.md`). **Built-in default = `{trivial: sonnet, simple: sonnet}`** (moderate / complex inherit). To opt out (restore all-inherit on the low tiers), set `subagent_model: {trivial: inherit, simple: inherit}` in `.claude/dev-workflow.md` or `~/.claude/dev-workflow.local.md`. Invalid values / unknown tier keys warn and fall back to the built-in per-tier default. **`hooks.on_complete` skill entries' models are independent of this key** — the workflow never passes `Model:` to `hooks.on_complete` callee skills. **Per-subagent `effort` is out of scope**.
- **implementation_executor**: **Experimental**. Selects who executes Step 5 implementation work units — `main` (default), `subagent`, `ask-claude`, `ask-codex`, `ask-gemini`, `ask-copilot`, or `ask-agy`. `ask-peer` is unsupported here. When the resolved value is not `main`, Step 5's sub-step 2 delegation guidance becomes the default route for each **settled** work unit, but the same spec-completeness guard still decides per unit: judgment-heavy, context-dependent, small, or still-unsettled units stay on the main thread with a one-line note, and hybrid execution is normal. Availability is resolved once per run at the first Step 5 delegation point: `subagent` requires an edit-capable `Agent` subagent type; the external-CLI values require a successful `Skill(<value>)` call after one retry per § Prerequisites. If the selected executor is unavailable, emit a one-line note and fall back to `main` for the rest of the run with no user gate. The main thread always retains user gates, the Step 5 self-audit sub-steps (run as post-delegation verification against the delegated diff), Step 7+ verification, and Step 10 commits. `subagent_model` propagation applies only to the `subagent` value; external-CLI executors keep their CLI-side model configuration. The canonical dispatch payload lives in [`references/executor-prompt.md`](executor-prompt.md). Can be overridden per invocation with `--executor <value>` (same closed value space; an invalid or unsupported flag value warns and is ignored, leaving the config-resolved value in effect). To opt in for a specific project, set `implementation_executor: "subagent"` (or another supported value) in `.claude/dev-workflow.md` or `.claude/dev-workflow.local.md`. Unsupported values fall back to `main` with a warning
- **interactive_commits**: Whether Step 10 (Interactive Commits) runs after `hooks.on_complete` (default: `true`). When `true`, after Step 9 (Completion Hooks) the workflow proposes commit groupings and messages, then iterates per-commit with the user; it **additionally** proposes committing the updates that Step 11 (Update Rules) writes across extract-rules' output directories (rule files under `output_dir`, `.examples.md` files under `examples_output_dir`, and staged candidates under `staging_output_dir`) — see Step 11's "Commit rule updates" sub-step — decline that gate and every rule change stays uncommitted for the Completion manual-commit reminders to cover. It also gates **Step 5's Build-order boundary chain** (sub-step 2.5): when `true`, Step 5 stages each Build order step's edited paths and records a dangling commit object per step. When `false`, Step 10 is omitted from the task list and never executes, no boundary objects are recorded, and the Step 11 rule-update commit is likewise never proposed — the workflow ends with an uncommitted tree and the manual-commit reminder fires. Non-boolean values fall back to `true` with a warning. To opt out, set `interactive_commits: false` in `.claude/dev-workflow.md` or `~/.claude/dev-workflow.local.md`
- **commit_review_gate**: Which surface a **code-diff review** renders on — `diff` / `crit` (default: `diff`). Step 10 (Interactive Commits) applies it to each commit's diff, but it is one consumer rather than the key's whole scope. `Source of truth for this key's semantics: this bullet. Beyond the SKILL.md index bullet this file's preamble already governs, every site that describes which surfaces the key governs is swept with it — currently this skill's own README.md (the settings-table row and the #### commit_review_gate section), mobpro references/configuration.md § Fallback keys, and mobpro README.md § Configuration. Keep in sync — widen the scope wording here before adding a consumer anywhere.`
  - `diff` (default) is the workflow's existing per-commit presentation: the Subject / Body / Files / Verification / Diff text rendered in chat (verbatim / condensed / skeleton depending on size — see `references/diff-presentation.md` § Rendering ladder, which `references/interactive-commits.md` § Per-commit loop sub-step **a. Build the candidate, then present it** applies to each commit), gated by the existing accept/adjust/cancel per-commit accept gate.
  - `crit` (opt-in, experimental) launches the external **crit** CLI (<https://github.com/tomasz-tomczyk/crit>) scoped to just that commit's files, so the user reviews the actual code diff in the browser (inline comments, approve / request-changes) before the commit lands. That view opens on a story built from the commit message — a prologue plus chapters over the diff's hunks — and falls back to the plain diff when crit rejects the story or is too old to carry one. See `references/crit-commit-review.md` for the full contract. Availability (`crit --version`) and local-browser reachability (`printenv CLAUDE_CODE_REMOTE`) are each checked once per run and cached — independently of Step 4's own reachability probe. When either check fails, Step 10 falls back to `diff` mode for the entire run with a one-line note. When a specific commit's crit launch itself ends non-zero (e.g. the user closed the tab), only that commit falls back to the `diff` gate — crit stays in use for the remaining commits in the run.
  - Invalid values fall back to `diff` with a warning.
- **polish_prose**: Whether the workflow's two `prose-polish` passes — Step 6.5 (Polish Prose, file-mode polish of the changed files) and the Step 4 plan-body polish (file-mode polish of the plan document before it is presented, joined by the decomposition state file on the run that created it) — run (default: `true`). When `true` (the default), both passes run: the Step 4 plan-body polish runs on every difficulty tier, and Step 6.5 is still subject to the difficulty-skip matrix, so it runs only on Moderate / Complex. When explicitly set to `false`, both passes are skipped: Step 6.5 marks itself `completed` and proceeds to Step 7 (emitting a one-line note on Moderate / Complex; on Trivial / Simple the difficulty-skip matrix already owns the skip, so no `polish_prose` note fires), and the Step 4 plan-body polish is skipped silently (the un-polished plan is presented). Non-boolean values fall back to `true` with a warning. To opt out for a specific project, set `polish_prose: false` in `.claude/dev-workflow.md` or `.claude/dev-workflow.local.md`.
- **custom_instructions**: Free-form development instructions applied as guiding principles across planning, implementation, review, and tidy phases (e.g., "Always use TDD", "Prefer functional style"). Optional. `.claude/rules/` and explicit user requests take precedence if they conflict
- **language**: Optional. Output language code (e.g. `ja`, `en`) for user-facing prose produced by this skill — Step 4 plan body (Overview / Decisions / Build order / Test plan / Risks / Unknowns content), user-gate preambles (Step 4 / Step 7.5 / Step 8 / Step 11.6), violation / finding lists, difficulty log line (`references/tier-assessment.md` § Difficulty log line), the visual plan-review gate's URL line (`references/visual-plan-review.md` § Procedure's "Surface the gate URL in chat" paragraph — the URL itself stays verbatim), Step 10 commit-plan / per-commit gate output and the Step 11 "Commit rule updates" gate output (subjects, body, diff blocks framed in the resolved language; verbatim git output and file paths remain English), Completion summary, and Step 11.5 finding `Description` / `Suggested fix direction` paragraphs. Resolution: merged skill config → Claude Code settings (`~/.claude/settings.json` → `language` field) → default `ja`. `null` / empty string / non-string values fall through to the next resolution step. For the localization boundary between translated concepts and verbatim identifiers, see [`references/localization.md`](localization.md) § Localization granularity. Its **Self-application** paragraph applies here too; a site with no language note of its own is **not** exempt. See `references/self-retrospective.md` §2.1 Language handling / §5 Contract note for the Step 11.5 scope contract. No Step 11.5 output unless `self_retrospective.feedback` is also configured
- **check_commands**: Static checks (lint, format, typecheck, etc.). Always run all in order
- **test_commands**: Defaults to `["Skill(run-tests)"]`. Each entry must be a `Skill(<name>)` string (no shell commands). Entries run sequentially during Step 7. Run `--init` to generate or update `run-tests`; additional structural-check skills can be appended in project config
- **hooks**: Execute skills/commands at specific workflow timing points
  - **on_complete**: Runs as Step 9 (immediately after Step 8.5 Deferred Verification). Entry format: `Skill(<name>)` or shell command string
  - Entries not covered by allowed-tools require user approval
- **self_retrospective**: Optional. Emits sanitized improvement signal for the `dev-workflow-bundle` skills (`dev-workflow`, `ask-peer`, `extract-rules`, `rules-review`) at Step 11.5 (between Step 11 and Completion). Raw conversation stays in-session; only abstracted text leaves
  - **feedback**: Destination string. Auto-detected:
    - Starts with `/`, `~/`, `./`, or `../` → local directory path → retrospective written as a markdown file under that directory
    - Matches `^[\w.-]+/[\w.-]+$` → GitHub `owner/repo` → retrospective submitted via `gh api` POST to `/repos/<feedback>/issues`
    - Any other string (including empty) → warn and skip Step 11.5
  - If `feedback` is unset, Step 11.5 is not registered as a task and never executes
  - Step 11.5 runs whenever `self_retrospective.feedback` is configured, **regardless of the assessed tier**. Even Simple / Trivial tasks emit a retrospective when `feedback` is set; when nothing notable surfaced, the retrospective is simply short

- **workability_retrospective**: Optional. Detects this session's project-tooling workability improvements at Step 11.6 (between Step 11.5 and Completion) and offers a per-candidate disposition gate. Like `self_retrospective`, it is a nested map merged as a scalar/map key (a higher layer replaces the lower layer's map wholesale; no per-key cross-layer merge)
  - **enabled**: Whether Step 11.6 runs (default: `false`). The detection + 4-way disposition feature is **experimental**. When `false` (the default), Step 11.6 is not registered as a task and never executes. To opt in for a specific project, set `workability_retrospective.enabled: true` in `.claude/dev-workflow.md` or `.claude/dev-workflow.local.md`. Non-boolean values fall back to `false` with a warning
  - **backlog_dir**: Directory for the "save to backlog" disposition's markdown files (default: `.claude/improvements`). A project that enables this feature should add its `backlog_dir` to `.gitignore`. Non-string / empty values fall back to the default with a warning
  - Step 11.6 runs whenever `workability_retrospective.enabled` is `true`, **regardless of the assessed tier**. The Step 11.6 detection is served by the **shared session scan** (see `references/session-scan.md`): Step 11.6 dispatches that scan when no earlier participating step did (Step 11 abstained because `rule-extraction-active` was false, and Step 11.5 was unregistered or pre-flight-aborted), otherwise it consumes the workability block from the already-dispatched scan — see `SKILL.md` § Configuration's **`Agent` tool usage** bullet
