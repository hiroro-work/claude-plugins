## Sub-step 1 — Overlay / merge procedure

1. Read settings from up to three layers and merge (type-aware):
   ```
   merged = {}
   if ~/.claude/dev-workflow.local.md exists:  overlay its frontmatter onto merged
   if .claude/dev-workflow.md exists:          overlay its frontmatter onto merged
   if .claude/dev-workflow.local.md exists:    overlay its frontmatter onto merged
   ```
   "Overlay" = for each key, evaluate the rules below in order and stop at the first match.
   - `null` or empty (`[]`, `{}`) explicitly clears the key — lower-layer value is discarded, not inherited, whatever type class the key falls under below
   - Key absent from the file: left untouched (inherit from lower layers)
   - Scalar keys: `merged[key] = file[key]` (replace) — this includes `subagent_model`, whose value is a map (`{<tier>: <model>}`): the whole map replaces the lower layer's value with no per-key cross-layer merge (a map key absent from the higher layer is not back-filled from the lower layer)
   - List keys (`check_commands`, `boundary_check_commands`): append `file[key]` items after `merged[key]`, then deduplicate (keep first occurrence)
   - List-replace keys (`test_commands`): `merged[key] = file[key]` — the higher layer's whole list replaces the lower layer's (no item-level merge or dedup)
   - `hooks`: deep-merge — for each sub-key (e.g. `on_complete`), append and deduplicate the list
   If a file's YAML frontmatter is malformed (parse error), warn the user naming the file, skip that layer, and continue with remaining layers.

## Sub-step 8 — Context-compaction recovery

8. **Context-compaction recovery**: if the session context was compacted (prior turns summarized) before reaching this step in the current turn, re-read the configuration files from disk rather than relying on the summary — verify each step's skip conditions (e.g. whether `self_retrospective.feedback` is set, whether `workability_retrospective.enabled` is `true`, whether `hooks.on_complete` is configured, whether `polish_prose` is `true`, what `plan_artifact` resolved to from config) from the actual merged config, not from compacted context. Where neither task surface is available, also read the progress file § Sub-step 7's neither-surface paragraphs define, and take from it which phases have already run. `run_mode` and an `--artifact` override cannot be recovered from disk this way. For `run_mode`, a `fast` run is inferable after the fact from the pre-completed Step 3 / Step 6.5 rows, the `fast_mode_skipped_steps` ledger, and the difficulty log line's fast-mode annotation, and, when the plan phase ran, a `deep` run from `plan_review_scope` being `full` in the difficulty log line's scope clause. An `--artifact` override leaves no such trace, so recover it from the invocation line while the compacted context still carries it and let the config-resolved `plan_artifact` stand otherwise.

## Sub-step 9 — Interruption re-anchoring

9. **Interruption re-anchoring**: if this invocation is a user-prompted continuation of a prior session that was interrupted (connection error, browser refresh, or similar — distinguished from compaction by the user explicitly asking to resume or continue rather than context being summarized in the same session), **and `--resume <state-file>` was not provided** (that path is handled by Step 1.5 Resume sub-mode), re-establish the run's current position before proceeding: (i) read the task list (`TaskList` / `TodoWrite` read) to identify the step currently marked `in_progress` — or, where neither surface is available, the progress file § Sub-step 7's neither-surface paragraphs define, taking the position that section derives and confirming from the header that the file belongs to the run being resumed, (ii) re-read the configuration files from disk (same as the "Context-compaction recovery" sub-step's procedure), and (iii) announce the resumption point to the user ("Resuming from Step N — <step description>") and proceed immediately from the `in_progress` step — do not wait for user confirmation. Do not re-execute already-`completed` steps.

## Sub-step 3 — reviewer availability probe

**Probe the resolved reviewer's availability immediately, regardless of whether it is the default `ask-peer` or a configured alternative**: attempt `Skill(<reviewer>)` with a one-word probe request (e.g., `ping`); if the call fails, retry once. Failure is the criterion § Prerequisites' **Cleanup skill** bullet states for every callee: a `Skill()` call that returns is a pass, and the probe does not additionally verify that a review would run. ## Sub-step 7 — registration mechanics

**Tool availability (Task tools vs `TodoWrite`)**: these steps name the Task tools (`TaskCreate` / `TaskUpdate` / `TaskList`). Where the Task tools are unavailable (e.g. the VSCode extension, or Claude Code before v2.1.142), use the equivalent `TodoWrite` operations instead — the status values (`pending` / `in_progress` / `completed`) and the register-all-upfront semantics are identical, and a `TaskList`-by-subject status read becomes a read of the `TodoWrite` list. **When neither surface is available**, the run's rows live in a **progress file** at the fixed path `.claude/plans/dev-workflow.run-progress.md`, and the phase naming in prose at each top-level Step transition continues alongside it. Treat every later instruction that marks a row, registers one, or resolves one by subject as satisfied by a line in that file.

**Registration.** `Read` the path first, and **decide here** which of three states the path is in. **No file** — register into a new one. **A file whose last line is a run-end line** (the run's own completion, or the gate or error that ended it) — that run is over and nothing needs its rows: report that line in one chat sentence and overwrite. **A file with no run-end line** — an earlier run stopped without writing one, and this file is the only record § Sub-step 9 — Interruption re-anchoring has to recover a position from: report its last line, then take the continuation arm when § Sub-step 9's own condition holds — the user asked to resume an interrupted session — keeping the file as found, appending to it, and registering nothing further; otherwise overwrite it. § Sub-step 8 — Context-compaction recovery never reaches this decision: a compaction happens inside a run whose registration is already behind it.

**Write and append with `Write`**, carrying the file's whole content each time — the content this run has held since it wrote the header, or, on the continuation arm, what the `Read` above returned plus what has been appended since. `Edit` is the wrong tool here: it needs a `Read` in the same conversation, which is exactly what the re-read rule below removes. Write a header carrying the effective task in one sentence and today's date, then one line per phase the list above registers, with conditionally-omitted phases left out and disabled-phase rows written as already complete. Step 5's optional implementation sub-tasks join them once its Build order is known. Every line naming a phase — a disabled-phase row written complete here, and every phase line appended later — takes one of three forms: `<phase name>: completed`, `<phase name>: skipped (<cause>)`, or `<phase name>: reopened (<cause>)`. Those are what the readers below match on, and **a phase's last such line is the one that counts** — a reopened row is unsettled again until a later line settles it. A line belonging to no phase takes whatever form says what happened.

**Append a line for a phase's completion, and for a row [`tier-assessment.md`](tier-assessment.md) § Row marking skips.** A phase merely beginning gets none. Reopening a row — [`tier-escalation.md`](tier-escalation.md) turns a tier-skipped row back to `pending` — earns the `reopened (<cause>)` line above rather than a free-form one. Two further lines belong to no phase: a phase newly added to the set, naming it; and the run's own completion, or, where the run ends anywhere other than Completion, the gate or error that ended it. A gate merely waiting for the user is not an end.

**The current position is the first registered phase whose last status line is neither `completed` nor `skipped`** — one never written to, or one last reopened. § Sub-step 8 — Context-compaction recovery and § Sub-step 9 — Interruption re-anchoring recover it that way, and [`completion.md`](completion.md) § Completion reminders' **Unfinished-phase reminder** reports every phase still in that state once the run ends.

**Re-read the file only when the last append has left context.** An append still in context answers § Step 1 registration mechanics' **Phase-boundary self-audit** without a `Read`.

**One run at a time.** The path is fixed per skill, so two concurrent runs in one repository would write over each other.

**A failed write is non-fatal.** Record it in one line and carry on. From that point the prose trail governs, and the file is not read again — a file missing an unknown number of lines answers a status check worse than not consulting it at all. Tell [`completion.md`](completion.md) § Completion reminders' **Unfinished-phase reminder** that a write failed, so it stands down rather than naming phases its gaps invented.

**A check that reads a row's status passes rather than failing closed where the file carries no line for it**, Step 4 sub-step 1's Step-3-completion check included.

**Registration mechanics (Task tools)**: issue every `TaskCreate` in a single upfront burst (one tool-call batch). Two conditional cases: (i) **conditionally-omitted phases** (the list items carrying a condition) are omitted by **not issuing their `TaskCreate`**; (ii) **a review phase already disabled at sub-step 4** (the plan phase under `run_mode == "fast"` — § Configuration's **Run mode** bullet; the code phase under `code_review: false` — § Configuration's `code_review` bullet) has its rows `TaskCreate`d directly with `status: "completed"` — the top-level `Step 3: Plan Review` / `Step 8: Code Review` row and, for the code phase, `Step 8-1`. Mark each task `in_progress` (via `TaskUpdate {taskId, status}`) when starting and `completed` when done.
